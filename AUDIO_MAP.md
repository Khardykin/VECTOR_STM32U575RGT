# Карта аудио-подсистемы: что где хранится и что как переключается

Документ отвечает на три вопроса: **где лежат звуки**, **как они попадают в устройство**
и **какой строкой кода что переключается**. Актуален для состояния после фазы 2
(`audio_player.c` + внешняя flash).

---

## 1. Два хранилища. Рабочее — только внешняя flash

| Хранилище | Объём | Что там сейчас | Роль |
|---|---|---|---|
| Внутренняя flash STM32 (1 МБ) | 1 МБ | прошивка (код ThreadX/HAL/приложения) | **звуков больше нет**. Раньше здесь жил C-массив `sound_gas_warning[]` (`audio_samples.c`) — это наследие фазы 0/1, сейчас мёртвый код |
| Внешняя flash MX25K6435F (DD2, SPI1) | 8 МБ | образ `sounds.img` со **всеми** звуками | **рабочее хранилище** |

Почему так: 1 МБ внутренней флеш хватило бы на ~5 коротких сигналов и ни одной голосовой
фразы, а внешние 8 МБ дают ~8.7 минут PCM 8 кГц. Плюс звуки можно обновлять, не трогая
прошивку.

`Core/Src/audio_samples.c` и `Core/Inc/audio_samples.h` в текущем коде **не участвуют**:
массив никем не читается, старый поток, который его играл, усыплён
(`audio_thread_entry` → `tx_thread_sleep(TX_WAIT_FOREVER)`). Единственная ссылка —
осиротевший `#include "audio_samples.h"` в `app_azure_rtos.c`.
Файлы удалены из проекта (см. раздел 6): они сжигали ~29 КБ внутренней флеш впустую.

## 2. Жизненный цикл звука (полная цепочка)

```
   ВАШ КОМПЬЮТЕР                         УСТРОЙСТВО
┌──────────────────────┐
│ голос/эффект .wav    │  TTS (Silero/SpeechKit) или библиотека, или диктор
└──────────┬───────────┘
           │  tools/pack_sounds.py  (сводит в моно, 8 кГц, считает CRC)
           ▼
┌──────────────────────┐
│ sounds.img           │  заголовок 24 Б + таблица по 36 Б/звук + PCM-блоки
└──────────┬───────────┘
           │  производство: программатор / factory-режим прошивки / позже OTA по LTE
           ▼
┌──────────────────────┐     sf_read()      ┌─────────────────┐
│ внешняя flash 8 МБ   │ ─────────────────► │ RAM-буфер 128 КБ│  + громкость
│ MX25K6435F, SPI1     │   (SPI1, 20 МГц)   │ ap_buf[]        │
└──────────────────────┘                    └────────┬────────┘
                                                     │ HAL_SAI_Transmit_DMA (одна транзакция)
                                                     ▼
                                            ┌─────────────────┐   I2S    ┌──────────────┐
                                            │ SAI1_Block_A    │ ───────► │ MAX98357A    │──► динамик
                                            │ Master TX, 8 кГц│  PA8/9/10│ DD4, 12 дБ   │
                                            └─────────────────┘          └──────────────┘
```

Ключевое: звук читается из внешней флеш **целиком в RAM**, затем отдаётся в SAI **одной**
DMA-транзакцией. Во время звучания CPU не участвует вовсе; щелей между кусками нет.

Ограничение такой схемы: длина одного звука ≤ 65535 сэмплов = **8.19 с** при 8 кГц
(размер RAM-буфера и предел `uint16_t Size` в HAL). Для голосовых подсказок хватает с
запасом. Длинные записи потребуют стриминга с circular DMA — это отдельный этап.

## 4. Где что переключается

### Какой звук играть

| Хочу | Строка кода |
|---|---|
| проиграть звук №N в очередь | `audio_play(N);` — индекс = позиция звука в таблице образа (порядок файлов в команде `pack_sounds.py`) |
| проиграть по имени | `audio_play_name("a_gas");` — имена берутся из имён WAV-файлов |
| **сменить режим** (прервать текущий) | `audio_set_state(st);` — текущий звук обрывается, играется звук нового состояния или тишина |
| остановить всё | `audio_stop();` |

Индексы и имена можно посмотреть двумя способами: `pack_sounds.py tools/sounds.img --check`
печатает таблицу, либо в отладчике `audio_count()` / `audio_name(i)`.

### Соответствие «состояние → звук»

Таблица живёт в `audio_player.c`, массив `ap_state_map[]`:

```c
static const uint16_t ap_state_map[3] = { 0u, 1u, AUDIO_STATE_SILENT };
/*          состояние 0 -> звук #0
            состояние 1 -> звук #1
            состояние 2 -> ТИШИНА            */
```

Хотите другое соответствие или больше состояний — правите этот массив (и делитель `% 3u`
в обработчике кнопок, если меняете число состояний). `AUDIO_STATE_SILENT` = «звука нет».

### Тестовый вход (без перекомпиляции логики)

`HAL_GPIO_EXTI_Rising_Callback()` в `audio_player.c`:

| Кнопка | Действие |
|---|---|
| BUTTON1 (PB1) | цикл состояний 0→1→2→0: звук #0 → звук #1 (прервал первый) → тишина |
| BUTTON2 (PB2) | следующий звук образа по кругу (`audio_play`) |
| BUTTON3 (PB3) | `audio_stop()` |

Антидребезг 200 мс. Прерывания EXTI1..3 включены в `main.c` (USER CODE 2) + обработчики в
`stm32u5xx_it.c` (USER CODE 1), потому что CubeMX их в NVIC не включил.

### Громкость

| Уровень | Где |
|---|---|
| фиксированная калибровка образа | `pack_sounds.py --gain 3.0` |
| регулировка в работе | `audio_set_volume(0..100)` — домножается при копировании в RAM |
| аппаратное усиление 12 дБ | резистор R9 (GAIN_SLOT) на MAX98357A — только перепайкой |

### Частота и формат на шине

CubeMX → SAI1: `AudioFrequency = 8K`, `MonoStereoMode = MONO`, `FIFOThreshold = 1QF`;
Clock Configuration → PLL3 = HSE/2×64/125 = 4.096 МГц (даёт ровно 8000.00 Гц при MCKDIV=2
и ровно 16000.00 Гц при MCKDIV=1, если вернётесь на 16 кГц). Код это не трогает.

### Состав и порядок звуков

Порядок файлов в команде = индексы в таблице:

```bat
python tools\pack_sounds.py tools\a_gas.wav tools\b_click.wav tools\c_voice.wav --out tools\sounds.img
```

Добавили файл в середину списка — сдвинулись индексы всех следующих. Поэтому в коде
лучше обращаться по имени (`audio_play_name`) либо держать порядок зафиксированным.

### Где в flash лежит образ

`AUDIO_IMG_BASE_ADDR` в `Core/Inc/audio_image.h` = `0x00000000` (начало внешней флеш).
Хотите отвести под образ не весь чип, а область — меняете эту константу и адрес записи
на производстве.

## 5. Потоки RTOS и синхронизация (кто чем владеет)

| Поток | Приоритет | Чем занимается |
|---|---|---|
| `Audio Player` (`audio_player.c`) | 10 | **единственный** владелец SAI/DMA: берёт команды, читает флеш, запускает DMA, ждёт завершения |
| `Audio Task` (`app_azure_rtos.c`) | 10 | усыплён навсегда, оставлен как заглушка |
| `LVGL Task` (`app_azure_rtos.c`) | 15 | спит, ждёт подключения графики |

Синхронизация: команды приходят в `tx_queue` (`audio cmd`), поток будит семафор
`audio wake`, который взводят **и** команды, **и** ISR завершения DMA
(`HAL_SAI_TxCpltCallback`). Поэтому поток не опрашивает ничего в цикле и просыпается
ровно по событию.

Правила, которые важно не сломать:
- `HAL_SAI_Transmit_DMA` / `HAL_SAI_Abort` вызывать **только** из потока плеера;
- из ISR (колбэки SAI, кнопки) — только `tx_semaphore_put` / `tx_queue_send`;
- текущий звук доигрывает до конца для `audio_play`; прерывает его только
  `audio_stop` и `audio_set_state`.

## 6. Что сделано с `audio_samples.*` и почему

Удалены из проекта вместе с осиротевшим `#include`:

- массив `sound_gas_warning[]` (29536 слов ≈ 29 КБ) никем не читался после перехода на
  внешнюю flash, но продолжал занимать внутреннюю;
- единственный потребитель (`audio_thread_entry`) усыплён в фазе 2;
- оставшаяся строка `#include "audio_samples.h"` в `app_azure_rtos.c` удалена.

Если захотите **аварийный писк**, который работает даже при мёртвой внешней flash:
сгенерируйте короткий (~0.15 с, 3 КБ) массив тем же `wav2c.py` и запускайте его напрямую
из `audio_player.c` в ветке `AUDIO_ERR_NO_IMAGE`. Скажите — добавлю.

## 8. Шпаргалка частых операций

**Добавить звук:** положить WAV (16 бит, любой_rate/каналы — конвертер сам сведёт) →
добавить его в команду `pack_sounds.py` → прошить `sounds.img`. Код не менять, если
обращаетесь по имени.

**Назначить звук на состояние:** править `ap_state_map[]` в `audio_player.c`.

**Поменять громкость всем звукам:** `--gain` при сборке; в рантайме `audio_set_volume`.

**Пересобрать образ:** `python tools\pack_sounds.py tools\*.wav --out tools\sounds.img`
(маски раскрываются самим скриптом, работает в cmd).

**Проверить образ:** `python tools\pack_sounds.py tools\sounds.img --check`.

**Вернуться на 16 кГц:** CubeMX → SAI1 `AudioFrequency = 16K` (PLL3 трогать не надо) +
пересобрать образ без `--rate` (по умолчанию pack_sounds.py использует 8000 — передать
`--rate 16000`).

# ДОПОЛНЕНИЕ (фаза 3): карта флеш, потокобезопасность, писк, мост UART

## 9. Внешняя flash: что где лежит и кто имеет право писать

Весь чип 8 МБ поделен на три непересекающиеся области (`Core/Inc/sfmap.h`); границы
выровнены на сектор 4 КБ, рассинхрон ловится compile-time assert'ом:

| Область | Адрес | Размер | Что там | Кто пишет |
|---|---|---|---|---|
| SOUNDS | `0x000000` | 4 МБ | `sounds.img` целиком | производство/OTA (прошивка не трогает) |
| CONFIG | `0x400000` | 128 КБ | кольцо из 32 секторов по 4 КБ, в секторе одна запись конфигурации с `seq` и CRC | `cfg_save()` |
| LOG | `0x420000` | 3.875 МБ | кольцевой журнал: сектор = заголовок `LOGS`+`seq`, далее записи с CRC | `log_append()` |

Конфигурация пишется всегда в **следующий** сектор по кругу, поэтому свежая и
предыдущая копии живы одновременно — сбой питания не убивает конфиг, плюс это
выравнивание износа. Журнал при заполнении сектора стирает следующий и увеличивает
`seq`; чтение записей по одной — `log_next()`.

### Потокобезопасность: единая точка входа

Все обращения к внешней flash из любых потоков идут **только** через
`Core/Src/extstore.c` (`ext_read / ext_write / ext_erase_sector / cfg_* / log_*`).
Внутри — мьютекс `sf bus` на всё время операции, включая стирание: SPI-шина одна,
NOR-чип допускает одну операцию за раз, а последовательность WREN→PP→wait-WIP
нельзя прерывать чужой транзакцией.

Правила, которые нельзя нарушать:
- прикладной код **не вызывает** `sf_read/sf_program/sf_sector_erase` напрямую;
- исключение одно: ранняя инициализация до старта планировщика (`audio_init()`
  читает заголовок и таблицу образа через `sf_read`), когда потоков ещё нет и
  мьютекс брать нельзя;
- цена сериализации: операция стирания (~50–100 мс) может отложить старт звука на
  это же время. Для логов/конфига это приемлемо; если станет мешать — выносить
  стирание в фоновый поток.

Отладочные переменные: `ext_dbg_log_sector`, `ext_dbg_log_offset`, `ext_dbg_cfg_seq`.

## 10. Аварийный писк (фолбэк при мёртвой внешней flash)

`Core/Src/audio_beep.c` — 240 мс, два тона 1.2 кГц, ~3.5 КБ **внутренней** flash.
Не зависит от внешнего чипа вообще.

Управление:
- `audio_beep()` — явный вызов из любого потока/ISR-безопасного контекста;
- **авто-фолбэк**: если `audio_play()` вызван, а образ не найден или бит
  (`audio_image_ok() == 0`), плеер вместо звука играет писк и ставит
  `audio_dbg_last_err = AUDIO_ERR_NO_IMAGE`;
- в отладчике писк виден как `audio_dbg_cur_idx == -2`.

## 11. Прозрачный мост UART4 <-> USART2

`Core/Src/uart_bridge.c`: всё, что пришло в UART4 (LoRa), уходит в USART2 (LTE) и
обратно, без разбора протокола. Приём — побайтовое прерывание в кольцо 1 КБ,
передача — поток бриджа (приоритет 12) чанками до 64 байт.

Направления отключаются независимо макросами `UART_BRIDGE_DIR_4_TO_2` /
`UART_BRIDGE_DIR_2_TO_4` в заголовке. Пока мост включён, он единственный владелец
приёма этих UART'ов: если LTE/LoRa-драйвер начнёт читать свой UART сам, мост для
этой линии выключается.

Комфортно до ~230400 бод. Для 460800/921600 побайтовые прерывания дороги — туда
нужен DMA-вариант моста (следующий этап).

Счётчики: `ub_rx4_bytes / ub_rx2_bytes / ub_tx4_bytes / ub_tx2_bytes / ub_ovf4 /
ub_ovf2 / ub_err`. Переполнение кольца (`ub_ovf*`) растёт, если поток-приёмник
не успевает за передатчиком.

## 12. Порядок инициализации (важно)

В `tx_application_define()` (`app_azure_rtos.c`), до создания потоков приложения:

```
1) ext_init();         мьютекс шины flash + сканирование журнала (до планировщика!)
2) audio_init();       читает sounds.img, создаёт поток плеера
3) uart_bridge_init(); мост UART4<->USART2
```

Менять порядок нельзя: `audio_init` до `ext_init` оставит рантайм-чтения флеш без
мьютекса, а любой из них после старта планировщика рискует взять мьютекс/создать
объекты в недопустимом состоянии.
