# Разбор: «завис в первом же `tx_semaphore_get(&ap_wake, TX_WAIT_FOREVER)`»

Дата: 2026-09-24. Коммит, после которого воспроизводится: `9fb6e4f "up"`
(перераскладка `Core/VectorLib/**/{Inc,Src}` + регенерация из CubeMX).

---

## 1. Коротко

Поток плеера **не завис** — он честно ждёт событие, которое не приходит.
Причин две, обе найдены в коде:

1. **`audio_init()` перестал вызывать `load_image()`** — регрессия последнего
   коммита. `ap_img_ok` остаётся 0, плеер считает, что образа во внешней flash
   нет, и на **каждом** старте уходит в заводскую перезапись 195 544 байт
   (48 стираний секторов + 764 записи страниц + верификация ≈ секунды), а если
   перезапись не удалась — навсегда остаётся на аварийном писке, а `BUTTON2`
   не делает вообще ничего (`audio_count() == 0`).
2. **Кнопки сконфигурированы не так, как ждёт демо-логика**: куб генерирует
   `GPIO_MODE_IT_RISING` + `GPIO_NOPULL`, а `audio_demo.c` написан под «ловим
   ОБА фронта и сами решаем по уровню пина». Плавающий вход + один фронт =
   события до плеера не доходят. Отсюда и «висит в первом же get».

Плюс три вещи, которые не являются причиной, но мешают жить и уже исправлены:
ожидание было `TX_WAIT_FOREVER` без таймаута (любое потерянное событие выглядит
как смерть), `STOP`, пришедший сразу за `PLAY`, откладывался до конца длинного
звука (до 8 с), и потерянный колбэк завершения SAI-DMA останавливал плеер
навсегда (теперь watchdog).

**Минимальная правка, если хотите проверить прямо сейчас одной строкой** —
в `audio_init()` после `tx_thread_create(...)` добавить `load_image();`.
Остальное в этом отчёте — диагностика и SPI-DMA.

## 1.5. ДОПОЛНЕНО ПОСЛЕ: причина «образа нет» при живых данных

Патч вернул `load_image()` в `audio_init()`, образ стал читаться на старте, но
`image ok=0` оставался — и заводская запись 195 КБ продолжала идти на каждом
старте. Лог устройства (`docs/log.md`) показал парадокс:

```
[3.390] 2/F: factory: done, 195544 b written and verified   <- данные во flash ВЕРНЫЕ
[3.396] 2/A: image ok=0 sounds=0                            <- а проверка их бракует
[3.402] 2/A: boot: state 0, sound #0, loop=1 pause=500 ms
```

Верификация побайтовая (`sf_verify` сравнивает flash с const-образом), значит
записано правильно. Бракует именно `load_image()`, и вот почему:

```c
static uint8_t raw[24 + 32*36];                       /* ОДИН буфер */
sf_read(BASE, raw, sizeof ap_hdr);                    /* заголовок -> raw[0..23]  */
const audio_img_header_t *h = (void *)raw;            /* h указывает ВНУТРЬ raw   */
...
sf_read(BASE + 24, raw, tbl_bytes);                   /* таблица -> ТОТ ЖЕ raw!   */
if (crc == h->table_crc32)                            /* а это уже raw[20..23] =
                                                         байты таблицы, не CRC    */
```

Второе чтение перезатирало заголовок, поэтому `h->table_crc32` к моменту
сравнения содержал кусок первой записи таблицы и CRC не сходился **никогда**.
Итог: `ap_img_ok = 0` навсегда → factory-запись на каждом старте → вместо
звука аварийный писк → «в `start_now` не заходит» / «звука не слышно».

**Исправлено:** заголовок читается сразу в `ap_hdr`, таблица — в `raw`; на
каждый вариант отказа своя строка лога (magic / version / count / CRC /
ошибка чтения), чтобы в следующий раз причина была видна сразу:

```
image header bad: magic=... want 49444e53, ver=... want 1, count=... max 32
image CRC mismatch: got <crc> want <crc> (table <n> b)
```

## 1.6. «Память всё равно прошивается на каждом старте» — почему так и где доказательство, что запись работает

**Коротко: стирание и запись работают идеально, это доказывает ваш же лог.
Ломалась только ПРОВЕРКА образа после чтения — см. раздел 1.5.**

Из `docs/log.md` (ваш запуск):

```
[0.066] 2/F: erase @0 ok, 37 ms          <- 48 стираний, все ok
[1.868] 2/F: write 4096 b @0 ok, 27 ms   <- 48 записей по 4 КБ, все ok
[3.390] 2/F: factory: done, 195544 b written and verified   <- ВЕРИФИКАЦИЯ
[3.396] 2/A: image ok=0 sounds=0                            <- а проверка образа не прошла
```

Верификация (`sf_verify`) читает flash обратно и сравнивает **побайтово** с
const-образом во внутренней flash. Она прошла — значит в микросхеме лежит ровно
то, что нужно. Значит и стирание, и запись, и чтение работают.

Дальше `load_image()` читал заголовок и таблицу **в один и тот же буфер** и
сравнивал CRC заголовка, который к этому моменту был уже затёрт таблицей. CRC не
сходился никогда → `ap_img_ok = 0` → на следующем старте снова «образа нет» →
снова 195 КБ записи. Круг замкнулся: **память исправна, браковал её код
проверки.**

Проверено на вашем образе (`audio_factory_image.c`, тот самый массив, который
пишется во flash):

```
crc32(таблица 144 байта) = 0x4784304e
table_crc32 из заголовка = 0x4784304e     -> СОВПАДАЕТ
magic=0x49444e53 version=1 count=4 table_off=24 data_off=168 total=195544
```

То есть после исправления (заголовок читается в `ap_hdr`, таблица — в `raw`)
образ валидируется с первого раза, `image ok=1 sounds=4`, и factory-запись на
старте больше не запускается вовсе.

Если патч ставить не хочется, правка руками — три строки в
`Core/VectorLib/Audio/Src/audio_player.c`, функция `load_image()`:


### Заодно: сравнение с `docs/ext_flash_mem.c` (ваш драйвер из другого проекта)

Посмотрел. Логика та же, что в `spiflash.c`: CS вручную, `WREN` перед
записью/стиранием, команда+3 байта адреса, ожидание WIP по таймауту, чтение
потоком. Отличия и почему у нас так:

| Место | `ext_flash_mem.c` | `spiflash.c` | Комментарий |
|---|---|---|---|
| команда чтения | `FASTREAD 0x0B` + dummy-байт | `READ 0x03` | оба верны; 0x0B нужен на высоких SCK, у нас 20 МГц — хватает 0x03 |
| запись | `write_data_memory(len)` одним куском | `sf_program` **режет по страницам 256 Б** | у NOR page program заворачивается внутри страницы: кусок, пересекающий границу 256 Б, без разбиения запишется неправильно. Наш вариант безопаснее |
| ожидание готовности | `while(!wait_status_busy(...));` | `wait_busy()` возвращает `HAL_TIMEOUT` | бесконечный цикл при мёртвой flash = полное зависание потока; у нас таймаут 500 мс и код ошибки |
| стирание | проверка `(page_addr & 0x0F) == 0 && byte_addr == 0` | проверка `addr % 4096 == 0` | эквивалент |
| блокировка шины | `__disable_irq()`/`__enable_irq()` (местами закомментировано) | мьютекс ThreadX `ext_mtx` | под RTOS глобальное `__disable_irq()` вокруг операции на 30 мс уронило бы системный тик и приём UART — именно то, чего вы опасаетесь. Мьютекс блокирует только поток |
| большие чтения | опрос | опрос **или DMA** (≥1 КБ) | см. раздел 6 |

Вывод: ваш старый драйвер не «правильнее», он просто другой; по надёжности
(страницы, таймауты, мьютекс вместо `__disable_irq`) текущий строже. Менять
нечего, кроме уже исправленной проверки образа.

## 1.7. Лог от 10:08 — фикс сработал, и видно две новые вещи

```
[0.016] 2/S: tick: PCLK1=160000000 Hz TIM6 PSC=159 ARR=999 -> 1000 us   <- таймер настроен верно
[0.024] 4/A: image header bad: magic=ffffffff want 49444e53, ver=65535 want 1, count=65535 max 32
[0.025] 3/A: no image -> factory program (takes seconds)
...
[3.467] 2/F: factory: done, 195544 b written and verified
[3.473] 2/A: image ok=1 sounds=4          <- ПРОВЕРКА ОБРАЗА ЗАРАБОТАЛА
[3.500] 2/A: play #0 'a_gas' 14768 samples @8000 Hz
[3.922] 2/A: play #1 'b_click' ...        <- кнопки BUTTON2 работают, звуки идут по кругу
[4.491] 2/A: play #3 'd_myvoice' 64839 samples @8000 Hz
```

### (а) `magic=ffffffff` на старте = flash в этот момент была стёрта

`0xFFFFFFFF` — это состояние **стёртой** NOR-ячейки, а не ошибка чтения:
`sf_probe` в той же строке лога отработал (`jedec=c2 28 17`), чтение после
записи тоже (`image ok=1`). Значит на момент старта область SOUNDS была пуста.

Откуда: со старым `load_image()` factory-запись запускалась **на каждом**
старте и первые ~40 мс стирала сектор 0. Любой сброс/перепрошивка в этом окне
оставляли образ стёртым → следующий старт снова видел `0xFF` → снова стирал.
Самоподдерживающийся цикл, который рвал именно фикс проверки заголовка.
Теперь проверка проходит, factory отрабатывает один раз и больше flash не
трогается. Проверка: после удачного старта сделать сброс (не перепрошивку) и
убедиться, что в логе есть `image ok=1 sounds=4` и НЕТ строк `erase @...` /
`write 4096 b @...`.

### (б) Тик HAL отстаёт от реального времени примерно в 34 раза

Часы терминала: 10:08:04.880 → 10:10:42.088 = **157 с**. Счётчик устройства:
`[0.009]` → `[4.659]` = **4.65 с**. Нажатия кнопок разнесены на 4–20 реальных
секунд, а тик между ними сдвинулся на десятки миллисекунд. Конфигурация
таймера при этом верная (`PSC=159 ARR=999 -> 1000 us`), значит прерывание
TIM6 обслуживается в разы реже, чем приходит.

Самая вероятная причина — **остановка ядра отладчиком**: TIM6 как периферия
продолжает считать под halt, но прерывание не обслуживается, и за всю
остановку засчитывается один тик. Лечится одной строкой (добавлена,
`VECTOR_DBG_FREEZE_TICK 1`):

```c
DBGMCU->APB1FZR1 |= DBGMCU_APB1FZR1_DBG_TIM6_STOP;
```

Это же объясняет все «странные» тайминги: антидребезг 50 мс идёт секундами,
пауза цикла 500 мс — 20–40 с, `HAL_Delay(5)` — дольше. Подробности и полный
набор приборов — `CODE_MAP.md` разделы 7.1–7.3.

Косвенное подтверждение из того же лога: стирание сектора показывает
«32–50 мс», а для MX25R6435F (JEDEC `C2 28 17` — именно она, а не MX25K6435F,
как написано в комментарии `spiflash.c`) sector erase заметно дольше. Умножьте
показанное на дефицит тика — получится паспортное значение.

| Замечание | Сделано |

## 2. Причина №1: потерянный `load_image()` (доказательство)

До коммита `9fb6e4f` в `audio_player.c` было **вложенное определение функции** —
`static void load_image(void) { ... }` внутри тела `audio_init(void)`. GCC такое
не компилирует вообще, то есть предыдущее состояние файла было нерабочим.
Последний коммит «починил компиляцию», перенеся заголовок `audio_init()` ниже
`load_image()` — и вызов чтения образа при этом потерялся:

```diff
-/* =============================================================== публичное */
-void audio_init(void)
-{
-  uint8_t  raw[AUDIO_IMG_HEADER_SIZE + AP_MAX_SOUNDS * AUDIO_IMG_ENTRY_SIZE];
-  uint32_t tbl_bytes;
-
 /* Читает заголовок и таблицу образа из внешней flash в RAM. ... */
 static void load_image(void)
 ...
+/* =============================================================== публичное */
+void audio_init(void)
+{
   /* --- RTOS-объекты и поток --- */
   (void)tx_semaphore_create(&ap_wake, "audio wake", 0);
```

Проверка: `grep -n "load_image()" audio_player.c` до правки давал **единственный**
вызов — из `audio_reload_image()`, а её, в свою очередь, зовёт только поток, и
только если `!ap_img_ok`. Круг замкнулся: образ не читается → `ap_img_ok == 0` →
factory-запись → (если удалась) `audio_reload_image()` → образ прочитан.

### Что это давало на железе

| Шаг | Было | Стало |
|---|---|---|
| `audio_init()` | таблица образа НЕ читается | `load_image()` → `ap_img_ok = 1` |
| старт потока | всегда factory-запись 195 КБ (≈3–10 с, износ flash) | factory только если образ реально бит/отсутствует |
| `BUTTON2` | `audio_count() == 0` → ничего | играет следующий звук |
| `BUTTON1` | `start_now()` → `!ap_img_ok` → аварийный писк | играет звук состояния |

### Заодно в этой же функции

* скратч-буфер `raw[1176]` в `load_image()` сделан `static`: вызов идёт из
  `audio_init()` **на стеке MSP до старта планировщика**, где зарезервировано
  всего `_Min_Stack_Size = 0x400`;
* `ap_img_ok = 1` стоял **внутри** цикла по записям таблицы — перенесён после
  цикла (иначе «образ годен» выставлялся бы после первой же записи);
* добавлены стадии старта `audio_dbg_boot_stage` и лог в USART1.

## 3. Причина №2: кнопки

`Core/Src/gpio.c` (генерация куба):

```c
GPIO_InitStruct.Pin  = BUTTON1_Pin|BUTTON2_Pin|BUTTON3_Pin;
GPIO_InitStruct.Mode = GPIO_MODE_IT_RISING;   /* только ОДИН фронт */
GPIO_InitStruct.Pull = GPIO_NOPULL;           /* вход плавает      */
```

а `audio_demo.c` устроен так: ловим оба фронта, читаем уровень пина и событием
считаем только тот фронт, где пин в активном уровне (`VECTOR_KEY_PRESSED_LEVEL`).
При `IT_RISING` + активном высоком это ещё как-то работает, при активной низкой
кнопке (замыкание на GND) — не работает никогда: нажатие даёт **падающий** фронт,
который не настроен, а на отбое уровень уже неактивный и обработчик выходит.
Без подтяжки уровень в момент отбоя вообще случаен.

**Сделано:** `audio_demo_buttons_init()` (в `audio_demo.c`, вызывается из
`main.c`, `USER CODE BEGIN 2`) переконфигурирует PB1/PB2/PB3 в
`GPIO_MODE_IT_RISING_FALLING` с подтяжкой из `vector_config.h` и чистит
флаги EXTI. Правка живёт в USER CODE — перегенерация из куба её не убьёт.

Что нужно выставить под вашу схему (два макроса в `vector_config.h`):

| Кнопка замыкает пин на | `VECTOR_KEY_PRESSED_LEVEL` | `VECTOR_KEY_PULL` |
|---|---|---|
| +3.3V (внешний pulldown или внутренний) | `1` | `2` (pulldown) ← сейчас по умолчанию |
| GND | `0` | `1` (pullup) |
| есть внешние резисторы на плате | любой | `0` |

**Отдельно про `BUTTON3`:** в `.ioc` пин называется `PB3 (JTDO/TRACESWO)`. Если в
настройках отладчика включён SWO-трейс, PB3 занят отладкой и третьей кнопки
фактически нет. Либо выключите SWO, либо перенесите `BUTTON3`.

### Как проверить за 30 секунд

В Expressions: `demo_dbg_edges`, `demo_dbg_press`, `demo_dbg_level0`,
`demo_dbg_debounce`.

| Картинка | Вывод |
|---|---|
| все нули при нажатии | EXTI не приходит: NVIC/пины/схема (или PB3 = SWO) |
| `edges` растёт, `press == 0`, `level0` растёт | не та полярность/подтяжка — поменяйте пару макросов выше |
| `edges` растёт, `debounce` растёт | дребезг больше 200 мс или «фантомные» фронты с плавающего входа |
| `press` растёт, звука нет | кнопки ни при чём, идём в `audio_dbg_*` (см. раздел 5) |

## 4. Что проверено и причиной НЕ является

Чтобы не ходить по второму кругу:

* **Тик ThreadX есть.** В `tx_user.h` блок `TX_NO_TIMER` / `TX_TIMER_PROCESS_IN_ISR`
  **закомментирован** (`/* … */`), поэтому `_tx_timer_initialize()` вызывается,
  порт сам настраивает SysTick (100 Гц) и сам же предоставляет `SysTick_Handler`
  → `tx_thread_sleep()` и таймауты работают. (Если когда-нибудь раскомментируете
  `TX_NO_TIMER` — обязаны вызывать `_tx_timer_interrupt()` из периодического ISR,
  иначе все `tx_thread_sleep`/таймеры умрут.)
* **Приоритет 0 у EXTI/SPI/GPDMA не ломает ThreadX.** Порт Cortex-M33 маскирует
  критические секции через PRIMASK (`TX_PORT_USE_BASEPRI` не определён), поэтому
  `tx_queue_send`/`tx_semaphore_put` из ISR допустимы с любым приоритетом.
* **Имена колбэков GPIO верные** для U5 HAL: `HAL_GPIO_EXTI_Rising_Callback` /
  `HAL_GPIO_EXTI_Falling_Callback` реально существуют и вызываются из
  `HAL_GPIO_EXTI_IRQHandler`.
* **RAM и DMA.** `.bss` лежит в `RAM = 0x20000000, 768K` (SRAM1/2/3, доступны
  GPDMA1). DCache на U5 нет → когерентность буфера `ap_buf[]` не требуется.
  `ap_buf` = 131 070 Б, суммарно RAM ~150 КБ из 768 КБ — запас есть.
* **Каналы DMA не конфликтуют:** SPI1_RX = GPDMA1_Channel10, SPI1_TX =
  GPDMA1_Channel9, SAI1_A = GPDMA1_Channel11; NVIC включён на все три.
* Дублирующего определения `HAL_SAI_TxCpltCallback` нет (старый поток
  `audio_thread` в `app_azure_rtos.c` просто усыплён).

## 6. SPI теперь по DMA — что с этим делать (ваш вопрос №4)

### Что было на самом деле

Куб в последнем прогоне привязал к SPI1 два канала GPDMA1 (ch9 = TX, ch10 = RX)
и включил `SPI1_IRQn`, но **драйвер `spiflash.c` ходил блокирующим опросом**
(`HAL_SPI_Transmit` / `HAL_SPI_Receive`). То есть DMA была настроена и
простаивала: не ломала ничего, но и не работала.

Цена опроса именно в этом месте: подкачка звука тянет до 131 070 байт, при
SPI1 = 160 МГц / 8 = 20 МГц это **≈52 мс**, и всё это время поток плеера
(приоритет 10) **крутится в опросе**, не отдавая CPU. LVGL (приоритет 15) на
это время встаёт — будущий интерфейс будет дёргаться на каждом старте звука.

### Что сделано

`sf_read()` теперь сам выбирает режим:

* блоки < `VECTOR_SPI_DMA_MIN_LEN` (1024 Б) — по-прежнему опрос: команды,
  статус, заголовки журнала/конфига, там 1–256 байт и настройка DMA дороже обмена;
* блоки ≥ порога — `HAL_SPI_Receive_DMA()` кусками по `VECTOR_SPI_DMA_CHUNK`
  (32 768 Б = 13 мс), поток **спит на семафоре** `sf_dma_sem`, который взводит
  `HAL_SPI_RxCpltCallback`;
* CS держится низким на всё чтение, паузы SCK между кусками для NOR допустимы;
* **любой** сбой DMA (таймаут `VECTOR_SPI_DMA_TMO_MS`, `HAL_SPI_ErrorCallback`,
  `HAL_BUSY`) → `HAL_SPI_Abort()` → чтение **повторяется с начала опросом**,
  `sf_dma_failed = 1` до следующего старта. Дочитывать хвост после обрыва
  нельзя: внутренний счётчик адреса во flash сдвинут неизвестно как;
* DMA доступна только из контекста потока: `tx_thread_identify() == NULL` до
  старта планировщика, поэтому `sf_probe()` и `ext_init()` автоматически
  остаются опросными (спать там некому).

Итог: 52 мс спина CPU на старте звука превращаются в 52 мс сна потока,
корректность данных при этом не зависит от исправности DMA.

### Два требования к конфигурации (уже выполнены, но проверьте после куба)

1. `SPI1_RX` → `GPDMA1_Channel10`, `Mode = DMA_NORMAL`, байт/байт, `SrcInc = FIXED`
   (в `spi.c`, `HAL_SPI_MspInit`).
2. Включены **оба** прерывания: `GPDMA1_Channel10_IRQn` (данные) **и**
   `SPI1_IRQn`. Колбэк `HAL_SPI_RxCpltCallback` HAL вызывает не из DMA, а из
   прерывания EOT самого SPI — без `SPI1_IRQn` семафор не взведётся и чтение
   уйдёт в таймаут (затем откатится на опрос, то есть «просто» станет медленно).

Запись (`sf_program`) и стирание намеренно оставлены на опросе: страница 256 Б
пишется ~0.3 мс, а дальше всё равно ждём WIP — DMA там ничего не выигрывает.

## 8. Порядок проверки на железе

1. Подключите USART1 (TX) к терминалу 115200 8N1. После сборки должно быть:
   ```
   [audio] init...
   [audio] image ok=1
   [audio] sounds=4
   ```
   `image ok=0` → во внешней flash нет валидного образа: смотрите `sf_jedec`
   (должно быть `C2 ?? 17`) и `sf_probe_rc`. Если `sf_probe_rc != 0`, чип не
   отвечает — дальше можно не смотреть, это SPI1/CS/питание.
2. Нажмите `BUTTON1`. Ожидание: `demo_dbg_press` +1, `audio_dbg_keys` +1,
   `audio_dbg_last_cmd == 3`, `audio_dbg_started` +1, через ~8 с `played` +1.
3. Если `started` растёт, а звука нет: `audio_dbg_errors`, `audio_dbg_last_err`
   (`0x1000|ErrorCode` — ошибка SAI), и проверьте `SD_MODE` (PC9 = 1) —
   усилитель выключен, пока там 0.
4. `audio_dbg_stuck > 0` — звук стартовал, но `HAL_SAI_TxCpltCallback` не
   пришёл: проверьте `GPDMA1_Channel11_IRQn` в NVIC и `audio_dbg_last_err`.
   Плеер при этом сам разблокировался, следующий звук пойдёт.
5. `sf_dbg_dma_chunks > 0` и `sf_dbg_dma_fallback == 0` — DMA-чтение работает.
   `fallback` растёт → DMA не взлетела, данные всё равно читаются опросом;
   смотрите `sf_dbg_dma_tmo` (нет `SPI1_IRQn`?) и `sf_dbg_dma_err`.
6. Старт должен занимать доли секунды, а не 3–10 с. `audio_dbg_boot_stage == 5`
   и `factory_dbg_sector == 0` при `image ok=1`. Если `boot_stage == 4` —
   factory-запись провалилась, причина в `sf_probe_rc` / `factory_dbg_sector`.
