# Формат журнала событий (внешняя flash, слот 40 байт)

> **Статус:** рабочая спецификация. Заменяет прежний формат журнала (слот 64 байта,
> `EVENT_LOG` в `Config_save_read.h`). Назначение журнала — локальный
> «чёрный ящик» трекера VECTOR: всё важное, что уходит по LoRa (координата,
> концентрации газа, СИЗ, состояния), плюс системные события. Читается через
> COM/Modbus; на сервер штатно уходит по LoRa v4 (`Mirax-Lora-protocol-v4.md`)
> — журнал является локальной страховочной копией и материалом для разбора
> инцидентов.

---

## 1. Принципы

1. **Все записи одной длины — 40 байт** (слот кольца): поиск и чтение —
   чистой арифметикой указателей, без разбора содержимого.
2. **Время в записи = время СОБЫТИЯ**, а не момент записи во flash: запись
   целиком формируется (снимок) в момент события и попадает в RAM-очередь;
   писатель переносит её во flash, когда шина доступна (п. 6).
3. **Два источника записей:**
   - **периодические** (heartbeat) — по архивному тику (настраивается,
     по умолчанию 10 минут, диапазон 10–15): набор «важное состояние»;
   - **событийные** — МГНОВЕННО в момент события: сработка/сброс газовых
     порогов, изменение маски СИЗ, включение/выключение/перепрошивка.
4. Маяки в периодический набор **не входят** (выключены решением автора):
   на сервер они и так уходят каждым LoRa-uplink (`BLEBeacons`); в журнале
   тип зарезервирован для ручного снимка (п. 4.6).
5. Номер записи (`CurrentAddrFile`, u32, монотонный) хранится **в каждом
   слоте** — абсолютная нумерация восстанавливается сканом кольца даже после
   многих переполнений и потери указателей (п. 7.3).

---

## 2. Геометрия flash

Область LOG — **2 МБ** (`sfmap.h`: 0x402000..0x602000), без расширения.

| Параметр | Значение |
|---|---|
| Слот | 40 байт |
| Записей в секторе 4 КБ | **102** (4080 Б; хвост 16 Б сектора не используется) |
| Секторов в области | 512 |
| Ёмкость кольца | 512 × 102 = **52224 записи** |
| Адрес записи | `addr(ptr) = SF_LOG_BASE + (phys / 102) × 4096 + (phys % 102) × 40`, где `phys = ptr mod 52224` |
| Указатели | `CurrentAddrFile` (куда писать), `BegginAddrFile` (самая старая) — монотонные u32, в `Config_archive` + зеркало-кольцо LOG_PTR (0x602000) |
| Переполнение | при записи на границу сектора (кольцо полное или слот не пустой): erase сектора, `BegginAddrFile += 102` |
| Пустой слот | байты `0xFF`; валидность: `Fmt_ver = 1`, известный `Type_log`, `Payload_len ≤ 28` |

`Fmt_ver` отличает записи нового формата (40 Б) от старых (64 Б, прежний
формат).
**Миграция не нужна** (решение автора): при первом старте прошивки с новым
форматом кольцо LOG переинициализируется, старые записи не выгружаются и не
разбираются.

## 3. Формат слота (40 байт)

```
+0   +1       +2            +3       +4                +8                  +12
┌────┬────────┬─────────────┬────────┬─────────────────┬───────────────────┬──────────────┐
│Type│Fmt_ver │Payload_len  │Flags   │ working_hours   │ CurrentAddrFile   │ Payload 28 Б │
│ u8 │ u8     │ u8 (≤28)    │ u8     │ u32, секунды    │ u32, номер записи │ по Type_log  │
└────┴────────┴─────────────┴────────┴─────────────────┴───────────────────┴──────────────┘
```

```c
typedef struct {
    uint8_t Type_log;        // +0 тип записи — селектор payload (п. 4)
    uint8_t Fmt_ver;         // +1 версия формата слота (= 1)
    uint8_t Payload_len;     // +2 значимых байт payload (≤ 28)
    uint8_t Flags;           // +3 бит0 = «продолжение» (части записи), ост. rfu
    uint32_t working_hours;   // +4  ВРЕМЯ СОБЫТИЯ, с (offset + working_hours)
                              //     — ключ поиска, смещение фиксировано
    uint32_t CurrentAddrFile; // +8 номер записи (абсолютная нумерация кольца)
} log_hdr_t;                  // 12 байт

typedef struct {
    log_hdr_t H;
    uint8_t   Pl[28];         // интерпретируется по Type_log
} __attribute__((packed)) EVENT_LOG;   // РОВНО 40 байт (assert sizeof == 40)
```

`working_hours` — суммарные секунды (как в прежнем формате): монотонны
благодаря зеркалу
часов, пригодны для бинарного поиска и для восстановления нумерации.

## 4. Типы записей

| Type | Имя | Payload | Триггер |
|------|-----|---------|---------|
| `0x00` | TURN_ON | power (п. 4.4) | событие, мгновенно |
| `0x01` | TURN_OFF | power | событие, мгновенно («предсмертная» — bounded-ретрай) |
| `0x02` | FW_UPDATE | power | событие, мгновенно |
| `0x04` | READINGS | полные показания (п. 4.2) | архивный тик (10–15 мин) |
| `0x08` | PARAM | обновление параметра (п. 4.7) | событие (COM/Modbus/LoRa) |
| `0x10` | GAS | полный срез AVIS (п. 4.3) | **событие: сработка/сброс порога**, мгновенно |
| `0x20` | BEACONS | срез маяков (п. 4.6) | зарезервирован (периодика ВЫКЛЮЧЕНА) |
| `0x30` | PPE | срез СИЗ (п. 4.5) | архивный тик + **изменение маски**, мгновенно |
| `0x40` | SNAPSHOT | «где был + чем дышал» (п. 4.1) | архивный тик (10–15 мин) |

Периодический набор на тик = **SNAPSHOT + READINGS + PPE** (3 записи, общее
`working_hours` — при разборе склеиваются в один «срез момента»).

### 4.1 SNAPSHOT (0x40) — важный минимум, 28/28

```c
typedef struct {
    int32_t lat, lon;         // 8   GPS ×1e7; (0,0) = нет фикса
    uint8_t battery_pct;      // 1   заряд трекера, %
    uint8_t active_sensors;   // 1   маска каналов AVIS
    uint16_t conc[8];          // 16 концентрации (pass-through, единицы
                               //     отправителя); индекс массива = номер канала
    uint8_t chan_thr_bits;    // 1   маска порогов на момент тика:
                               //     бит k = канал k за порогом (см. примечание)
    uint8_t motion;           // 1   MOTION_BITS: поза (биты 0-1), падение (2),
                               //     удар (3), отсутствие активности (4) — LIS3DH
} __attribute__((packed)) log_pl_snapshot_t;   // 28 байт
```

**Примечание про `chan_thr_bits`:** пороговые события и так пишутся мгновенно
полными записями GAS (п. 4.3); маска в периодическом срезе — независимая
картина тревожности: по ней видны тревожные интервалы, даже если событийные
записи утрачены (дребезг, перезапись кольца), и журнал быстро сканируется на
«маска ≠ 0» без восстановления истории из событий.

### 4.2 READINGS (0x04) — полная телеметрия трекера, 28/28

```c
typedef struct {
    uint32_t state;            // 4   Config_common.State
    uint32_t state_err;        // 4   Config_common.StateErr
    uint8_t battery_pct;      // 1   MAX17048
    uint16_t battery_mv;       // 2   MAX17048
    uint16_t aqi;              // 2   индекс качества воздуха — задел: позже
                               //     будет отдельная микросхема-датчик (пишем 0)
    int16_t temperature;      // 2   °C×100 — BME280
    uint16_t humidity;         // 2   %×100 — BME280 (драйвер отдаёт %×1024)
    uint16_t pressure;         // 2   гПа×10 — BME280
    uint8_t motion;           // 1   MOTION_BITS: поза (биты 0-1), падение (2),
                               //     удар (3), отсутствие активности (4) — LIS3DH;
                               //     активность отдельным полем не нужна — она
                               //     выражена битом MOTION_BIT_INACTIVE
    uint8_t rfu[8];           // 8
} __attribute__((packed)) log_pl_readings_t;   // 28 байт
```

### 4.3 GAS (0x10) — полный срез AVIS, событийная, 28/28

Пишется **мгновенно** при изменении состояния любого канала (сработка или
сброс порога) — направление видно по `chan_state` в сравнении с предыдущей
записью GAS/SNAPSHOT. Антидребезг: не чаще одной записи в 10 с (серия
колебаний у порога схлопывается; итоговое состояние всё равно фиксируется).

```c
typedef struct {
    uint8_t slot;             // 1   слот AVIS в MAC-таблице (протокол BLE)
    uint8_t dev_charge;       // 1   заряд газоанализатора, %
    uint8_t active_sensors;   // 1   маска каналов
    uint16_t conc[8];          // 16 концентрации (pass-through)
    uint8_t chan_state[8];    // 8   StateErr каждого канала
    uint8_t rfu[1];           // 1
} __attribute__((packed)) log_pl_gas_t;        // 28 байт
```

### 4.4 TURN_ON / TURN_OFF / FW_UPDATE (0x00/0x01/0x02), 28/28

```c
typedef struct {
    uint16_t fw_version;       // 2   версия прошивки (здесь, а не в общем
                               //     заголовке — периодическим записям не нужна)
    uint8_t hw_version;       // 1
    uint8_t brand;            // 1   MIRAX/BACS
    uint32_t reset_reason;     // 4   флаги причины сброса / счётчик включений
    uint32_t state;            // 4
    uint32_t state_err;        // 4
    uint8_t battery_pct;      // 1
    uint16_t battery_mv;       // 2
    uint8_t rfu[9];           // 9
} __attribute__((packed)) log_pl_power_t;      // 28 байт
```

### 4.5 PPE (0x30) — срез СИЗ, самодостаточная, 28/28

```c
typedef struct {
    uint8_t presence_mask;     // 1   бит k = СИЗ позиции k присутствует/надета
    uint8_t charge[8];         // 8   заряд каждой позиции (0/1/2)
    uint8_t ppe_type[8];       // 8   тип каждой позиции (каска/привязь/...)
    uint8_t serial[8];         // 8   заводские идентификаторы (1 байт, протокол BLE)
    uint8_t rfu[3];            // 3
} __attribute__((packed)) log_pl_ppe_t;        // 28 байт
```

Позиция k = k-я запись СИЗ в MAC-таблице (как в LoRa `PresenceMask`). Запись
самодостаточна (тип и серийник внутри) — отдельные события «изменение заряда»
или «появление метки» не нужны. Триггеры: архивный тик + мгновенно при
изменении `presence_mask`.

### 4.6 BEACONS (0x20) — зарезервирован, периодика выключена

```c
typedef struct {
    uint8_t count;             // 1   маяков в этой записи (≤ 6)
    uint8_t total;             // 1   всего видимых (одинаков в частях)
    struct {
        uint16_t short_id;     // 2
        int8_t   rssi;         // 1
        uint8_t battery;      // 1   0/1/2
    } __attribute__((packed)) b[6];   // 24
    uint8_t rfu[2];            // 2
} __attribute__((packed)) log_pl_beacons_t;    // 28 байт
```

В архивный набор НЕ входит (решение автора): маяки уходят на сервер каждым
LoRa-uplink. Больше 6 видимых — части с `Flags.бит0` = «продолжение». Запись
может формироваться по ручной команде (сервис/отладка).

### 4.7 PARAM (0x08) — обновление параметра (задел)

```c
typedef struct {
    uint16_t param_id;         // 2   идентификатор параметра
    uint8_t source;           // 1   0 = COM, 1 = Modbus/BLE, 2 = LoRa downlink
    uint8_t old_v[8];         // 8   прежнее значение (по формату параметра)
    uint8_t new_v[8];         // 8   новое значение
    uint8_t rfu[9];           // 9
} __attribute__((packed)) log_pl_param_t;      // 28 байт
```

Формат уточняется вместе с протоколами COM/Modbus.

## 5. Периодичность и бюджет ёмкости

**Архивный тик** — `Archiveinterval` в конфиге, формат как в Avis: **старший
байт — минуты, младший — секунды**. Период ОДИН на весь периодический набор
(SNAPSHOT + READINGS + PPE пишутся на одном тике). По умолчанию **10 мин
0 с** (диапазон 10–15 мин). Событийные записи — сверх тика, в обычном
состоянии редки.

| Режим | Записей/сутки | История (52224 записи) |
|---|---|---|
| Тик 10 мин, событий нет | 3 × 144 = 432 | **~121 сутки (≈ 4 месяца)** |
| Тик 15 мин, событий нет | 3 × 96 = 288 | **~181 сутки (≈ 6 месяцев)** |
| Тик 10 мин + ~100 событий/сут | ~532 | ~98 суток |
| Авария: пороги непрерывно (антидребезг 10 с → до 8640 событий/сут) | ~9000 | ~6 суток (всё параллельно уходит на сервер аварийным ритмом LoRa) |

Требование «≥ месяц в обычном состоянии» выполняется с запасом ≥ 3×.

**Износ:** erase — раз в 102 записи; при 432 записях/сут это ~4 стирания в
сутки, сектор стирается раз в ~4 месяца → ~3 цикла/год на сектор при ресурсе
100 000 — пренебрежимо.

## 6. Очередь записей (RAM) и политика записи во flash

Между моментом события и записью во flash — **кольцевая очередь в RAM**:

```
Событие (порог / выключение / архивный тик)
   │  В МОМЕНТ СОБЫТИЯ: снимок времени, State/StateErr, данных →
   │  готовая 40-байтная запись
   ▼
RAM-очередь (кольцо, 16 × 40 Б = 640 байт)
   │  писатель — Measure Task, каждый проход (~50 мс)
   ▼
шина SPI свободна? ──нет──► запись ждёт, повтор на следующем проходе
   │ да
   ▼
взять старейшую → program слота (1–6 мс) → следующая; LOG_PTR — ОДИН РАЗ
на всю пачку записей (износ страницы указателей не зависит от частоты)
```

Правила:

- **снимок на момент события**: `working_hours`, State/StateErr и данные
  фиксируются при постановке в очередь — задержка записи время не искажает;
- **всплески не теряются**: несколько событий подряд (каскад порогов, снятие
  СИЗ, выключение) становятся в очередь и записываются по порядку (FIFO
  сохраняет хронологию — бинарный поиск по времени остаётся корректным);
- **program разрешён под звуком** (1–6 мс поглощаются 93-мс запасом
  дозагрузки плеера) — обычная задержка записи ≤ 50 мс;
- **erase — только в «окно тишины»** (пауза повтора плеера 500 мс или конец
  звука): при сирене сдвигается не дальше ближайшей паузы;
- переполнение очереди (16 событий за одно окно — практически невозможно):
  перезапись старейшей + счётчик потерь + LOG_E — потеря видна;
- потеря питания: теряется только содержимое очереди (≤ 50 мс в норме,
  ≤ 0,5 с под сиреной); «предсмертная» запись TURN_OFF/FW_UPDATE —
  bounded-ретрай ~0,5 с.

## 7. Чтение и поиск

### 7.1 Чтение по указателю
`log_read(ptr)` → слот 40 Б; валидность: `Fmt_ver`, известный `Type_log`,
`Payload_len ≤ 28`.

### 7.2 Поиск по времени
Журнал упорядочен по `working_hours` (FIFO-очередь + монотонные часы) →
бинарный поиск по u32 на смещении **+4** (единообразно для всех типов,
payload не разбирается). Записи одного тика разделяют одну секунду — поиск
`>= / <=` это корректно обрабатывает.

### 7.3 Восстановление нумерации после переполнений
Абсолютный номер каждой записи лежит в самом слоте (`CurrentAddrFile`, +8).
При утрате/порче указателей (`Config_archive`, LOG_PTR) кольцо сканируется:
валидные слоты → максимальный `CurrentAddrFile` = свежая запись, по нему и по
границе валидных слотов восстанавливаются `cur/beg`. Позиция в кольце сама по
себе номера не даёт (кольцо перезаписывается многократно) — поэтому номер
хранится в каждой записи.

## 8. Принятые решения

1. **Слот 40 байт, все типы одной длины** — поиск/чтение арифметикой;
  payload 28 Б интерпретируется по `Type_log`.
2. **`CurrentAddrFile` (u32) в каждом слоте** — абсолютная нумерация,
   восстановление после любых переполнений и потери указателей.
3. **Область LOG 2 МБ без расширения** — при 40 Б ёмкость растёт сама:
   52224 записи (102/сектор, 16 Б хвоста сектора не используются).
4. **Периодика — только важное**: SNAPSHOT (координата + концентрации +
   пороги + заряд + поза) + READINGS (полная телеметрия) + PPE — по тику
   10–15 мин (конфиг). **Маяки выключены** (тип зарезервирован, ручной
   снимок); на сервер они уходят LoRa-uplink'ами.
5. **Особые события — мгновенно**: сработка/сброс порога (полная запись GAS
   с `chan_state[8]`, антидребезг 10 с), изменение маски СИЗ (запись PPE),
   включение/выключение/перепрошивка.
6. **Очередь в RAM (16 × 40 Б) со снимком на момент события** — время записи
   не искажается задержкой flash; всплески не теряются; program под звуком,
   erase в окне тишины; LOG_PTR — один раз на пачку.
7. **`Firmware_version` — только в записях питания/прошивки** (в общем
   заголовке его нет); `Fmt_ver` в заголовке — версия формата слота.
8. **FIFO-очередь сохраняет хронологию** — бинарный поиск по времени
   остаётся корректным; записи тика склеиваются общим `working_hours`.
9. **`Archiveinterval`** — формат как в Avis: старший байт минуты, младший
   секунды; период ОДИН на весь периодический набор; по умолчанию 10 мин.
10. **Миграции нет** — при первом старте с новым форматом (40 Б) кольцо LOG
    переинициализируется, старый журнал не выгружается.
11. **Источники полей READINGS/SNAPSHOT** — существующие датчики: BME280
    (температура/влажность/давление), LIS3DH (motion-байт в раскладке
    MOTION_BITS: поза/падение/удар/**отсутствие активности** — отдельное поле
    activity не нужно), MAX17048 (заряд), GPS (координата). Полей `altitude`
    и `activity` в слоте нет (решение автора); `aqi` — задел под будущую
    микросхему-датчик качества воздуха (пишем 0).

## 9. Открытые вопросы

- **PARAM (0x08)**: состав полей — по мере готовности протоколов COM/Modbus.
- **`aqi`** — поле-задел: позже в комплект добавляется микросхема-датчик
  качества воздуха (до её появления пишем 0).
- **SNAPSHOT при отсутствии AVIS в комплекте** — `active_sensors = 0`,
  `conc[] = 0`, `chan_thr_bits = 0` (запись всё равно несёт координату/заряд/
  позу).
