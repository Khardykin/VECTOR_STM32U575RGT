# Протокол обмена MIRAX BLE v1

> **Статус:** рабочая спецификация (единственная версия протокола — до
> достижения конечного результата версии не плодим).
> LoRa здесь **не описывается** — только маппинг «данные BLE → блоки LoRa v4»
> (п. 7); сам LoRa — `Mirax-Lora-protocol-v4.md`.

---

## 1. Общие положения

Протокол описывает три уровня обмена комплекта **VECTOR**:

1. **Эфир (реклама)** — устройства комплекта (маяки, метки СИЗ, браслет,
   газоанализатор AVIS) вещают advertising-пакеты; полезная нагрузка — в
   manufacturer data; маяки — в service data (Eddystone, п. 3.1), их данные
   модуль упаковывает в НАШ формат до передачи в MCU. **MAC-адрес в payload НЕ передаётся** — он находится в
   PDU рекламы и читается приёмником автоматически;
2. **UART (MCU ↔ BLE-модуль MK01 трекера)** — AT-команды: передача таблицы
   MAC-фильтра модулю при каждой инициализации, чтение последних принятых
   данных **по порядковому номеру (слоту) записи таблицы**, прозрачный мост
   для кадров Modbus RTU внешнего конфигуратора;
3. **BLE конфигуратора** — внешний конфигуратор (приложение) подключается к
   модулю трекера и обменивается с MCU кадрами **Modbus RTU** (содержимое
   кадров — карта регистров — вне рамок этого протокола); модуль — прозрачный
   мост, кадры не интерпретирует.

**Ключевые свойства:**

- фильтр эфира — **по MAC-адресам** из таблицы слотов; что это за устройство,
  MCU определяет **по своей таблице MAC-адресов** (DevType) и по ней же
  выбирает парсер; в payload нет ни MAC, ни байта типа/версии (Header);
  контроль целостности — по длине payload;
- модуль **не агрегирует** списки: он хранит кэш «последняя реклама + RSSI +
  возраст» **по слоту таблицы**, а MCU читает кэш (bulk или по слотам) и
  **сам** собирает блоки LoRa v4.

**Основные принципы:**

- все многобайтные поля — **little-endian**;
- **лимит одного ПАКЕТА ДАННЫХ — 256 байт**: эфирный payload, кадр ответа
  `msdget_resp_t`, кадр Modbus RTU. Строки AT-команд — отдельная сущность, их
  ограничивают буферы UART (п. 8): `MACSET` полной таблицы (493 символа) в
  них помещается;
- **заводские идентификаторы устройств — 1 байт** (Serial метки СИЗ, Serial
  браслета); пакет AVIS — `str_ble_data_set_t` (п. 3.4): `active_sensors` +
  `sensors[8]` с `SensorIndex`, максимум 54 байта;
- состав комплекта: **маяки 1..16**, **СИЗ ≤ 8** (может быть меньше; «не
  поймали — значит отсутствует»), **браслет ≤ 1**, **газоанализатор AVIS ≤ 1**;
  всего слотов ≤ 26 рабочих (ёмкость таблицы — 32 с запасом);
- сканирование модуля — **непрерывное**; опрос кэша MCU — **bulk-транзакцией
  `MSDGETALL`** (по умолчанию каждые 5 с) либо **по одному слоту `MSDGET=<i>`**
  с индивидуальной периодичностью: устройства вещают с разной частотой и разной
  критичностью (AVIS — учащённо, газовые пороги должны быстро попадать на
  сервер; маяки/СИЗ — реже). Оба режима равноправны (п. 4.3, 4.6);
- свежесть данных определяет **MCU** (TTL, п. 7.3): модуль отдаёт последний
  принятый пакет слота **и очищает кэш** — данные, прочитанные MCU, всегда
  «новые с прошлого опроса»;
- все устройства **могут подключаться** (соединение используется для сервиса/
  конфигурации — запись ShortID в маяк при монтаже и т.п.), но телеметрия
  ходит **только рекламой**; модуль трекера в рабочем режиме соединения с
  устройствами не устанавливает — только сканирует.

## 2. Состав и топология

```
 [ Маяк 1..16 ] ─┐
 [ СИЗ 1..8   ] ─┤  BLE-реклама (advertising)
 [ Браслет    ] ─┤  (MAC в PDU, manufacturer data — payload)
 [ AVIS       ] ─┘
        │
        ▼
 ┌──────────────────────┐      [ Конфигуратор ]  (внешнее приложение)
 │   BLE-модуль (MK01)  │◄─────── BLE GATT ───────  Modbus RTU (регистры —
 │   - сканер/приёмник  │      (соединение)        таблицы и прочие данные)
 │   - MAC+тип-фильтр   │
 │   - Eddystone→наш    │
 │     формат (маяки)   │
 │   - кэш по слотам:   │
 │     payload+RSSI+    │
 │     возраст          │
 │   - реклама (имя     │
 │     VEC…, для        │
 │     конфигуратора)   │
 └──────────┬───────────┘
            │ UART 115200 8N1 (AT-команды + URC "+MBUS:", п. 4)
            ▼
 ┌──────────────────────┐
 │   MCU (STM32U575)    │   трекер VECTOR, Modbus-слейв
 │   - таблица MAC →    │   ← энергонезависимая память (внешняя flash),
 │     DevType+Param    │     при КАЖДОМ включении передаётся модулю (MACSET)
 │   - кэш данных       │   ← значения по слотам + свежесть (п. 7)
 │   - LoRa v4 пакеты   │   ← формирование uplink (вне этого документа)
 └──────────┬───────────┘
            │ UART (LoRa-модуль S7678S)
            ▼
      [ Сервер LoRaWAN ]
```

| Устройство | Кол-во | DevType (п. 5) | Телеметрия (payload, п. 3) | Что нужно LoRa v4 |
|---|---|---|---|---|
| Маяк | 1..16 | 1 | эфир — **Eddystone**: UID (20 Б) + TLM (14 Б), чередуются; модуль упаковывает в наш формат {ShortID, Vbatt} (4 Б) | `BLEBeacons`: ShortID + Rssi + Battery (Vbatt→0/1/2, пороги на MCU) |
| Метка СИЗ | 0..8 | 2 | PpeType + Serial + State, 3 байта | `PPE`: присутствие + заряд; `TYPE_STATIC`: Type + Serial |
| Браслет (пульсометр) | 0..1 | 3 | Serial + заряд % + пульс + SpO2 + Flags, 5 байт | секция `SUB_TYPE_PULSE`: заряд %, пульс, SpO2 (задел) |
| Газоанализатор AVIS | 0..1 | 4 | `str_ble_data_set_t`, 6+6N ≤ 54 байта | секция `SUB_TYPE_GAS`: заряд, каналы (концентрация/StateErr/Setting) |

## 3. Эфир: реклама устройств

### 3.0 Общие правила

Каждое устройство вещает connectable-рекламу (ADV_IND); телеметрия — в
Manufacturer Specific Data. Раскладка AD-структуры (формат Bluetooth Core
Spec):

```
┌──────┬────────────┬─────────────────────┬────────────────────────────┐
│ Len  │ AD Type    │ CompanyID (2 байта) │ payload (наши данные, п.3.1+)│
│ 1 Б  │ = 0xFF     │ little-endian       │                            │
└──────┴────────────┴─────────────────────┴────────────────────────────┘
 Len = число байтов, следующих за Len (1 + 2 + длина payload)
```

**CompanyID** — обязательный по формату рекламы двухбайтовый код производителя,
которым Bluetooth SIG наделяет компании (например, у STMicroelectronics —
`0x0483`). Он ставится ПЕРЕД нашими данными и к логике протокола отношения не
имеет: у всех устройств комплекта значение одно, согласуется один раз при
производстве (предварительно — внутренний/тестовый `0xFFFF`, п. 11). Модуль-
сканер фильтрует эфир **только по MAC**, CompanyID вырезает и отдаёт MCU один
payload.

Модуль отдаёт MCU содержимое AD **без двухбайтового идентификационного поля**:
Manufacturer Specific Data (тип `0xFF`) — без CompanyID, как есть (метки СИЗ,
браслет, AVIS); **маяки (Eddystone, Service Data тип `0x16`, UUID `0xFEAA`) —
модуль разбирает UID/TLM САМ и упаковывает в наш формат** (п. 3.1): MCU не
видит сырой Eddystone. Тип устройства модуль знает из таблицы фильтра — он
привязан к слоту при записи `MACSET` (п. 4.1).

Прочие правила:

- **в payload нет ни MAC, ни байта типа/версии (Header)**: что это за
  устройство, MCU знает из таблицы MAC-адресов (DevType, п. 5) — по нему и
  выбирается парсер. Контроль — по длине payload: у каждого типа она фиксирована
  (СИЗ 3, браслет 5, маяк 4 — нормализованная запись от модуля, п. 3.1)
  либо вычислима (AVIS: 6+6N по маске `active_sensors`);
  длина не сошлась с DevType записи → пакет отбрасывается, счётчик ошибок
  (защита от перепутанных записей таблицы);
- устройства вещают **публичными (public) MAC-адресами**, назначаемыми при
  производстве; если понадобится random static — запись таблицы расширяется
  байтом типа адреса (п. 11);
- периоды рекламы (настраиваются при производстве/монтаже): маяк — UID
  1000 мс + TLM 1:10 (п. 3.1), метка СИЗ — 1000 мс, браслет — 500 мс,
  AVIS — 300 мс (как в действующей прошивке AVIS).

### 3.1 Маяк — Eddystone (UID + TLM)

Маяки вещают в формате **Google Eddystone** (решение автора: нужна
совместимость со сторонними маяками). Используются два типа кадров, они
чередуются в рекламе одного маяка; передаются в Service Data (AD type `0x16`,
UUID `0xFEAA`). Все многобайтные поля Eddystone — **big-endian** (в отличие
от остального протокола; конвертация — на MCU).

**Eddystone-UID (20 байт)** — идентификация:

```
смещение поле            значение
0         Frame Type      0x00
1         Ranging Data    калиброванный TX power на 0 м, дБм (signed)
2..11     NID[10]         namespace — один на объект/комплект
12..17    BID[6]          instance; у НАШИХ маяков BID[4..5] = ShortID (BE) —
                          записывается конфигуратором при монтаже
18..19    RFU             0x00 (старые реализации усекают до 18 байт —
                          принимаем и 18, и 20)
```

**Eddystone-TLM (14 байт)** — телеметрия маяка, чередуется с UID
(рекомендуемое соотношение у наших маяков 1:10):

```
смещение поле            значение
0         Frame Type      0x20
1         Version         0x00
2..3      VBATT           напряжение батареи, мВ, BE (0 = питание без батареи)
4..5      TEMP            температура маяка, 8.8 fixed-point °C, BE
                          (0x8000 = не поддерживается)
6..9      ADV_CNT         счётчик реклам с включения, u32 BE
10..13    SEC_CNT         аптайм, u32 BE, единицы 0.1 с
```

**Упаковка модулем в наш формат (решение автора).** MK01 знает из таблицы
фильтра, что слот — маяк (тип привязан к слоту при записи `MACSET`, п. 4.1),
разбирает UID/TLM и отдаёт MCU нормализованную запись — сырой Eddystone до
MCU не доходит:

```c
typedef struct {              // маяк в НАШЕМ формате (модуль -> MCU)
    uint16_t ShortID;         // LE; из BID[4..5] (конверсию BE->LE делает
                              // модуль); 0xFFFF = кадров UID с прошлого
                              // чтения не было
    uint16_t Vbatt;           // напряжение батареи, мВ, LE; из TLM;
                              // 0xFFFF = кадров TLM с прошлого чтения не было
} ble_beacon_norm_t;          // 4 байта
```

Модуль в пределах кэша слота копит ОБА типа кадров; чтение
(`MSDGET`/`MSDGETALL`) выдаёт то, что пришло с прошлого чтения ( part не
пришла — `0xFFFF`), Rssi/AgeSec — по последнему кадру любого типа.

Правила:

- **ShortID** (нужен LoRa `BLEBeacons`): у наших маяков — `BID[4..5]`,
  назначается при монтаже вместе с instance; у сторонних маяков instance
  произвольный и может быть заблокирован — для них ShortID **назначает
  конфигуратор и хранит в таблице MCU** (поле `ShortID`, п. 5). Приоритет:
  значение из таблицы (если ≠ 0), иначе из payload; `0xFFFF` в payload —
  сохранить прежнее значение (MCU мержит части между чтениями);
- **Battery** (0/1/2 для LoRa) — из `Vbatt` (мВ) пороговой конверсией **на
  MCU** (пороги — в конфиге трекера, под тип батареи; `Vbatt = 0` → питание
  без батареи → Battery = 2 «норма»). TLM не принят ни разу → Battery =
  `0xFF` «неизвестно» (п. 11);
- **TLM не содержит идентификатора** — спецификация Eddystone предписывает
  связывать его с UID по адресу устройства (MAC): ровно это наш MAC-фильтр и
  делает, кэш слота в модуле объединяет оба кадра;
- присутствие (`last_seen` на MCU) обновляет любая запись со Status 1 (UID
  или TLM);
- кадры URL/EID игнорируются (парсятся только UID/TLM);
- наши маяки connectable, конфигурируются при монтаже (namespace/instance/
  соотношение TLM:UID/период — стандартным Eddystone-Config GATT или своим
  конфигуратором, п. 11); реестр `ShortID → (координата/зона/этаж, MAC)` ведёт
  сервер.

### 3.2 Метка СИЗ

```c
typedef struct {
    uint8_t PpeType;    // тип СИЗ (приложение LoRa v4: 0 каска, 1 привязь, ...)
    uint8_t Serial;     // заводской идентификатор единицы, 1 байт
    uint8_t State;      // биты 0..1 = заряд (0/1/2), бит 7 = надето/присутствует,
                         // биты 2..6 — резерв (0)
} ble_pkt_ppe_adv_t;     // 3 байта
```

Присутствие СИЗ для LoRa определяется **двумя уровнями**: метка не поймана
(нет в кэше / устарела по TTL) → бита в `PresenceMask` нет вообще («отсут-
ствует»); поймана → бит выставляется по `State.7` (признак «надето» от датчика
ношения — задел; до его появления метка ставит бит 7 всегда, когда она на
человеке в зоне приёма, см. п. 11). Позиция бита (0..7) — порядковый номер
записи СИЗ в таблице MCU (п. 5), не из payload.

### 3.3 Браслет / пульсометр

```c
typedef struct {
    uint8_t Serial;     // заводской идентификатор, 1 байт
    uint8_t Battery;    // заряд браслета, % (0..100)
    uint8_t HeartRate;  // пульс, уд/мин (0 = нет измерения)
    uint8_t SpO2;       // сатурация, % (0 = нет измерения; задел)
    uint8_t Flags;      // бит 0 = надет (задел, датчик ношения), биты 1..7 — 0
} ble_pkt_bracelet_adv_t;// 5 байт
```

Соответствие LoRa v4 `SUB_TYPE_PULSE`: `Battery` → блок Battery (%),
`HeartRate` → блок HeartRate, `SpO2` → блок SpO2 (опциональный бит SubMask —
включается, когда `SpO2 ≠ 0`). `Serial` → `sub_descr_t.Serial` в `TYPE_STATIC`
(старший байт u16 = 0).

### 3.4 Газоанализатор AVIS

Прибор AVIS вещает пакет `str_ble_data_set_t` (в свой модуль записывается
командой `ADVMSDDATASET`):

**РЕВИЗИЯ (решение автора, 23.10, PLAN п.65):** `Setting_channel` — **2 байта**:
в них живут биты `DEVICE_SETTING_CHAN` (8..12: EC/OXYGEN/FID/UART/TK) и маски
`MEASURE_*` (единицы/дискретность BASIC+DISP) — в u8 биты 8..12 не помещались.
Раскладка канала — как в реализации (Ble_vector.h): позиция записи = номер
канала (состав задаёт маска `active_sensors`), отдельного байта `SensorIndex`
нет (задел ниже сохранён как целевой). Текущая версия пакета
`data_struct_ver = 3`; **ver 2 (legacy: 5 байт/канал, Setting u8) принимается**
трекером и конвертируется в ver 3 (биты 8..12 у старых приборов отсутствуют).

```c
typedef struct {                 // канал, 6 байт (ver 3; ver 2 — 5 байт, Setting u8)
    uint8_t Type_gas;           // код газа/канала (num_formula_gas)
    uint16_t Concentration;      // концентрация LE (единицы отправителя);
                                 // на проводе 2 байта, little-endian
    uint8_t State_channel;      // состояние канала отправителя (StateErr & 0x7F)
    uint16_t Setting_channel;   // установки канала LE: DEVICE_SETTING_CHAN (биты 8..12) + MEASURE_*
} __attribute__((packed)) ble_sensor_data_t;

typedef struct {                 // пакет AVIS
    uint8_t data_struct_ver;     // = 3 (ver 2 — legacy 5 байт/канал, принимается)
    uint8_t dev_id;              // НОМЕР МОДЕЛИ прибора (тип прибора),
                                 // НЕ серийный номер
    uint8_t dev_hw_ver;          // версия железа
    uint8_t dev_fw_ver;          // версия прошивки
    uint8_t charge;              // заряд батареи отправителя, %
    uint8_t active_sensors;      // битовая маска включённых каналов (бит0 = канал0)
    ble_sensor_data_t sensors[7];// COUNT_CHAN_BLE = 7 (реализация; целевые 8 — задел)
} __attribute__((packed)) str_ble_data_set_t;
                                 // шапка 6 байт; передаётся
                                 // 6 + 6×popcount(active_sensors), макс. 48 (ver 3)
```

Передаются записи только включённых каналов (`active_sensors`), каждая запись
несёт свой `SensorIndex` — порядок каналов в пакете не значим. MCU знает по
таблице, что источник — AVIS, и читает структуру как есть; первый байт
`data_struct_ver` ничего не диспетчеризует. Концентрации — **pass-through**
(отправитель уже применил свою дискретность и коэффициент), трекер повторно не
масштабирует. **Серийный номер пакет не несёт**: `dev_id` — это номер модели
(тип прибора), а не серийник; способ получения серийника AVIS для
`sub_descr_t.Serial` в LoRa `TYPE_STATIC` — открытый вопрос (п. 11).

> **Совместимость:** действующая прошивка AVIS (`Ble_mk01.h`) вещает пакет
> БЕЗ `SensorIndex` — 5-байтовые записи каналов, максимум 7 каналов
> (`6 + 5×popcount ≤ 41`). Формат выше отличается длиной записи канала; если
> обратная совместимость со старым парком нужна — для нового формата
> инкрементируется `data_struct_ver` (= 3), парсер выбирает раскладку по
> версии (п. 11).

## 4. UART-протокол MCU ↔ модуль MK01 (AT-команды)

**Транспорт:** USART 115200 8N1, обмен синхронный: команда завершается
`0x0D`, до 4 попыток на команду, контроль ответа `OK`/`ERROR`, 3 серии ошибок
подряд → флаг ошибки подсистемы BLE.

> **Статус раздела:** внешней спецификации на модуль нет — сканерская
> прошивка MK01 реализуется **строго по этому разделу** (норматив); сама
> прошивка модуля разрабатывается **вне проекта трекера** (решение автора).
> Сервисные и рекламные команды наследуются из действующей прошивки MK01.

**Форматы ответов:**

- без данных: `OK` / `ERROR`;
- с данными (hex-вариант): `эхо(2 байта) + hex-ASCII двоичного кадра + "OK"` —
  hex удваивает объём; буфер приёма MCU — **640 байт** (одиночные ответы
  ≤ 124, ответ `MSDGETALL` для комплекта ≤ ~612, п. 4.3);
- **URC (unsolicited result code)** — сообщения, которые модуль выдаёт сам
  (без команды MCU); начинаются с `+`. В этом протоколе один URC: `+MBUS:`
  (п. 4.4). MCU отличает URC от ответов на свои команды по префиксу `+`.

**MAC-адрес в командах** — 12 hex-символов, старший байт первым (порядок
отображения, как в ответе `BLEADDR?`), регистр не важен: `AABBCCDDEEFF`.
**Пустой слот** — 12 нулей: `000000000000` (п. 4.1).

### 4.0 Сводка команд

| Команда | Ответ | Назначение | Происхождение |
|---------|-------|------------|---------------|
| `AT` | `OK` | проверка связи | база MK01 |
| `AT+MODINFO?` | hex(ModInfo) | информация о модуле | база MK01 |
| `AT+BLEADDR?` | hex(MAC[6]) | MAC своего модуля | база MK01 |
| `AT+ADVBLENAMESET=<имя>` | `OK` | имя модуля (`VEC` + `%04d%04d` серийника) | база MK01 |
| `AT+ADVSTART=0/1`, `AT+ADVPERIODMS=n`, `AT+ADVPOWER=n` | `OK` | своя реклама (видимость для конфигуратора) | база MK01 |
| `AT+SLEEP`, `AT+SYSTEMOFF`, `AT+DFU` | `OK` | сервис | база MK01 |
| `AT+MACSET=<N>,<mac1>,<t1>,...,<macN>,<tN>` | `OK` | **записать всю таблицу фильтра: MAC + тип на каждый слот** (тип привязывается к индексу — нужен модулю для нормализации Eddystone); ЕДИНСТВЕННАЯ команда таблицы (любое изменение = полная перезапись); пустой слот = `000000000000,0` | новая |
| `AT+MSDGETALL?` | hex(`Count` + TLV-записи слотов) | **основная команда опроса: все слоты одним сообщением** (п. 4.3); кэш выданных слотов **очищается** | новая |
| `AT+MSDGETALL=<от>,<кол-во>` | hex(то же, диапазон) | то же, частью таблицы (ограничение буфера/диагностика) | новая |
| `AT+MSDGET=<i>` | hex(запись `msd_slot_rec_t`) | **прочитать кэш одного слота i** — режим опроса с индивидуальной периодичностью по устройствам; кэш слота **очищается** при выдаче (п. 4.3) | новая |
| `+MBUS:<len>` (URC, модуль → MCU) | — | **кадр Modbus RTU от конфигуратора** (п. 4.4) | новая |
| `AT+MBUSRSP=<len>` + raw | `>` … `OK` | **ответ MCU конфигуратору** (кадр Modbus RTU → notify) | новая |
| `AT+SCANSTART=0/1` | `OK` | включить/выключить сканирование | новая |
| `AT+SCANPARAM=<int_ms>,<win_ms>` | `OK` | параметры скана (дефолт в прошивке модуля) | новая |
| `AT+MACGET?` | hex(кадр таблицы) | прочитать таблицу модуля (сверка после записи) | новая |
| `AT+CONNSTATE?` | hex(1 байт: 0/1) | есть ли подключение конфигуратора | новая |

Отдельных команд добавления/удаления записи (`MACADD`/`MACDEL`) и ручной
очистки кэша (`MSDCLR`) **нет**: таблица всегда перезаписывается целиком одной
`MACSET`, кэш слота очищается автоматически — при чтении (`MSDGET`) и при
перезаписи таблицы.

Требование к прошивке модуля: **одновременная работа сканера и рекламы**
(приём устройств комплекта + видимость для конфигуратора).

### 4.1 Таблица MAC-фильтра — одна команда, полная перезапись

Таблица модуля — список слотов **MAC + тип** (тип привязывается к индексу при
записи: модулю он нужен, чтобы знать, где ждать Eddystone и нормализовать его
в наш формат; для остальных типов — отдавать manufacturer data как есть).
Ёмкость — **≥ 32 слотов** (рабочий максимум комплекта 26: 16 маяков + 8 СИЗ +
браслет + AVIS).

```
AT+MACSET=<N>,<mac1>,<t1>,<mac2>,<t2>,...,<macN>,<tN>\r    N = 0..32
```

`<t>` — DevType записи (п. 5): `1` маяк, `2` СИЗ, `3` браслет, `4` AVIS,
`0` пустой слот (MAC — 12 нулей). Тип вне диапазона 0..4 → `ERROR`.

- **слот (порядковый номер) записи = её позиция в списке MACSET** (0..N−1);
  MCU знает MAC↔слот, т.к. шлёт таблицу сам и хранит её в том же порядке;
- **любая операция с таблицей — это новая полная `MACSET`**: добавление,
  удаление, замена записи — MCU собирает новый образ таблицы и перезаписывает
  ею модуль целиком; инкрементальных команд нет — нечему
  рассинхронизироваться;
- **пустой слот** — MAC из 12 нулей (`000000000000`): конфигуратор назначает
  устройствам свои порядковые номера, и если какой-то номер не заполнен, MCU
  всё равно шлёт его в `MACSET` нулевым MAC — **нумерация слотов не ломается**.
  Пустой слот неактивен: модуль не добавляет его в фильтр сканера и не ведёт
  по нему кэш (`MSDGET` такого слота → Status 0);
- `N` = число слотов **включая пустые**, до последнего занятого; `N=0` —
  очистить таблицу;
- MCU передаёт команду **при каждой инициализации** (каждое включение
  трекера, п. 4.5) — таблица модуля энергонезависимой НЕ предполагается;
- дубликат **ненулевого** MAC в списке — `ERROR` (нулей-заглушек может быть
  сколько угодно); номер слота вне таблицы в `MSDGET` — `ERROR`.

**Помещается ли таблица в одно сообщение — да.** Длина строки
`AT+MACSET` = `11 + strlen(N) + 15×N` символов (включая `\r`):

| N (слотов) | Длина строки | Комментарий |
|---|---|---|
| 1 | 27 | пример п. 9.2 |
| 26 | 403 | рабочий максимум комплекта |
| 32 | 493 | ёмкость таблицы — влезает в буферы |

Буфер передачи MCU — 560 байт; **буфер приёма строки модуля — ≥ 512 байт**.
Лимит 256 байт на строки AT-команд не распространяется — он только для
пакетов данных (п. 8).

Ответ `MACGET?` (hex-кадр): `[Count u8][Count × (MAC[6] + Type u8)]` (порядок
= слоты, пустые — нулевой MAC и тип 0).

#### 4.1.1 Кэш модуля — слотовый алгоритм, самоочистка при чтении

У каждого **непустого** слота таблицы — свой кэш:
`{valid, payload, RSSI, момент приёма}`.

- сканирование **непрерывное** (п. 4.6): реклама от MAC слота i принята →
  кэш слота i **обновляется сразу, без участия MCU** (в кэше всегда последняя
  реклама; для слота-маяка модуль копит ОБА кадра — UID и TLM — и выдаёт их
  одной нормализованной записью, п. 3.1);
- `MSDGET=<i>` со Status 1 → модуль выдаёт кадр и **очищает кэш слота**:
  следующее чтение вернёт Status 0, пока не придёт новая реклама. Так MCU
  всегда точно знает: Status 1 = «устройство вещало с прошлого опроса»,
  Status 0 = «за период ничего не поймано»;
- `MACSET` → таблица перезаписывается, **все кэши сбрасываются**;
- ручной очистки кэша нет — она не нужна при таком алгоритме; по времени
  модуль кэш тоже не стирает (возраст отдаётся в `AgeSec`, бракует данные MCU
  по TTL, п. 7.3).

**Почему кэш+опрос, а не live-поток:** live-режим (URC на каждую принятую
рекламу) — это до ~80 кадров/с по UART при 26 устройствах с периодами
0.3–1 с и постоянный парсинг на MCU; дубли рекламы бесполезны — нужна только
последняя. Потребительский ритм — **bulk-опрос кэша одной транзакцией
`MSDGETALL` каждые 5 с** (~612 символов ≈ 53 мс UART, ~1 % загрузки): вместо
непрерывного потока — одна короткая сессия на период. Live-режим может
понадобиться только для сервисных задач (поиск устройства по RSSI) —
отдельный режим прошивки модуля, в базовый протокол не входит.

### 4.2 Сканирование

```
AT+SCANSTART=1\r        — запуск сканера (после записи таблицы)
AT+SCANPARAM=<interval_ms>,<window_ms>\r   — опционально
```

Сканер работает **непрерывно** — без пауз и сна между опросами MCU: кэш
должен пополняться постоянно, в первую очередь по AVIS (газовые пороги,
п. 4.6). Рекомендация по параметрам: duty скана ≥ 50 % (например, interval
200 мс / window 100 мс) — при периодах рекламы устройств 300..1000 мс каждый
пакет принимается устойчиво.

### 4.3 Чтение данных — два равноправных режима

Оба режима отдают ОДИНАКОВЫЕ записи слотов `msd_slot_rec_t` — парсер у MCU
один. **Запись самоограничивающая (TLV)**: поле `Len` задаёт число байтов
после него, поэтому payload переменной длины (AVIS: 6+6N) не мешает разбору —
следующая запись начинается строго через `2 + Len` байт от начала текущей,
никаких разделителей между слотами не требуется.

```c
typedef struct {
    uint8_t Slot;       // номер слота (0..N−1)
    uint8_t Len;        // число байтов ПОСЛЕ Len (= 4 + длина payload)
    uint8_t Status;     // 0 = новых данных нет (с прошлого чтения реклама
                         //     слота не принималась / слот пуст / кэш сброшен),
                         //     1 = есть данные (после выдачи кэш слота
                         //     очищается)
    int8_t   Rssi;       // RSSI принятой рекламы, дБм (0x7F — нет значения)
    uint16_t AgeSec;     // сколько секунд назад реклама была принята (на
                         //     момент выдачи); LE; 0xFFFF — насыщение;
                         //     поле информативное (диагностика)
    uint8_t Payload[];  // Len−4 байта: СИЗ/браслет/AVIS — manufacturer data
                         // КАК ЕСТЬ (без CompanyID); маяк — нормализованная
                         // запись ble_beacon_norm_t (4 Б, п. 3.1)
} msd_slot_rec_t;        // всего 2 + Len байт; пустой слот: Len = 4 (6 байт)
```

Правило разбора: прочитать `Slot` и `Len` → тело записи = `Len` байтов →
адрес следующей записи = текущий + 2 + Len. Максимальная запись — AVIS:
2 + 4 + 54 = 60 байт.

**Режим 1 — bulk: чтение ВСЕЙ таблицы одним сообщением.** Слоты пронумерованы
общим `MACSET`, поэтому модуль отдаёт весь кэш за одну транзакцию:

```
AT+MSDGETALL?\r                 — все слоты 0..N−1
AT+MSDGETALL=<от>,<кол-во>\r    — диапазон слотов (при ограничении буфера)
```

Ответ — hex-кадр:

```
[Count u8]                       — число записей
repeat Count (по возрастанию номеров слотов):
    [msd_slot_rec_t]             — запись слота (TLV, выше)
```

- отдаются **все** слоты диапазона, включая пустые и не принятые с прошлого
  чтения (Len=4, Status 0) — структура ответа детерминирована;
- кэш всех выданных слотов со Status 1 **очищается** (то же правило, что и
  для одиночного чтения);
- размер: комплект (16 маяков + 8 СИЗ + браслет + AVIS, все с данными;
  маяки — нормализованные по 4 Б) — 304 байта binary → ~612 символов hex
  ≈ 53 мс по UART 115200; буфер приёма MCU **640 байт**. Теоретический
  максимум (32 слота × AVIS-размер) недостижим составом комплекта; если
  понадобится — чтение диапазоном `=<от>,<кол-во>`.

**Режим 2 — по одному слоту** — когда устройствам нужна разная периодичность
опроса (периоды рекламы/критичность разные: AVIS — каждые 5 с, маяки/СИЗ —
каждые 60 с и т.п.), а также для диагностики:

```
AT+MSDGET=<i>\r         i = 0..N−1 (порядковый номер слота таблицы)
```

Ответ — та же одна запись `msd_slot_rec_t` (hex). `i` вне таблицы → `ERROR`.
Потеря ответа по UART не страшна: кэш уже очищен, но реклама устройств
повторяется каждые 0.3–1 с — к следующему опросу данные накопятся заново;
пропуск одного опроса перекрывается TTL (п. 7.3).

### 4.4 Мост конфигуратора — Modbus RTU

Кадры конфигуратора — **Modbus RTU**: MCU — слейв, конфигуратор — мастер;
содержимое кадров (карта регистров) вне рамок этого протокола (п. 6).
BLE-модуль кадры не интерпретирует — он **прозрачный мост** с идентификатором
`+MBUS:`.

**Модуль → MCU (кадр от конфигуратора).** Получив GATT-write от подключённого
конфигуратора, модуль сразу выдаёт в UART:

```
"+MBUS:<len>\r\n" + <len raw-байтов кадра Modbus RTU> + "\r\n"
```

- `<len>` — десятичное число байтов кадра (Modbus RTU: адрес + функция +
  данные + CRC16, максимум 256);
- идентификатор канала — префикс **`+MBUS:`**: по нему MCU отличает кадр
  конфигуратора от ответов на свои AT-команды (ответы не начинаются с `+`);
  границы кадра сохраняет GATT-write (один write = один кадр Modbus), модуль
  передаёт его одним URC;
- если MCU занят AT-транзакцией, кадр ждёт в очереди модуля (**≥ 8 кадров**);
  переполнение — теряется старейший;
- кадр без подключения конфигуратора появиться не может (источник — только
  GATT-write).

**MCU → модуль (ответ конфигуратору).** MCU обрабатывает кадр как
Modbus-слейв и возвращает ответ:

```
AT+MBUSRSP=<len>\r
  → ">" \r\n            — модуль готов принять len байт
  → MCU шлёт len raw-байтов (кадр ответа Modbus RTU)
  → "OK"                — отправлено notify конфигуратору (при необходимости
                          модуль дробит по MTU; приложение собирает кадр целиком)
  → "ERROR"             — конфигуратор не подключён / ошибка
```

Ответ должен уйти, пока мастер ждёт (таймаут Modbus-мастера с учётом моста —
п. 6). Broadcast-кадры (адрес 0) — без ответа.

### 4.5 Инициализация (каждое включение трекера)

```
1. AT ×2                        — проверка связи
2. AT+ADVBLENAMESET=VEC%04d%04d — имя модуля (метка VECTOR + серийник)
3. AT+BLEADDR?                  — MAC своего модуля
4. AT+MACSET=<N>,<mac>,<тип>,...— ВСЯ таблица из энергонезависимой памяти
                                  (п. 5): MAC + тип на слот, пустые слоты —
                                  нулевым MAC с типом 0
5. AT+SCANSTART=1               — запуск сканера (непрерывный)
6. AT+ADVPERIODMS=300, AT+ADVPOWER=8, AT+ADVSTART=1
                                  — своя реклама: видимость для конфигуратора
```

При N=0 шаги 4–5 выполняются формально (пустая таблица) — трекер остаётся
видимым для конфигуратора, который и заполнит таблицу.

### 4.6 Штатный ритм обмена

| Ритм/событие | Действия |
|--------|----------|
| непрерывно | сканирование модуля включено (`SCANSTART=1` после инициализации), кэш слотов пополняется с каждой принятой рекламой — **без пауз и сна между опросами** |
| 5 с (по умолчанию, настраивается) | **схема А: `AT+MSDGETALL?` — одна транзакция на всю таблицу**: разбор payload каждого слота по DevType → обновление кэша MCU (п. 7). Газовые пороги видны MCU в пределах 5 с — превышение переводит LoRa-обмен в аварийный ритм/события (логика LoRa — вне этого документа) |
| индивидуальные ритмы | **схема Б: `AT+MSDGET=<i>` по слотам** — у каждого устройства своя периодичность (периоды рекламы/критичность разные): например AVIS каждые 5 с, маяки/СИЗ/браслет каждые 60 с. Схемы А и Б равноправны, правило самоочистки кэша общее (п. 4.1.1) |
| URC `+MBUS:` (по прибытии) | кадр конфигуратора → обработка Modbus-слейвом → ответ `AT+MBUSRSP` |

Обработка ошибок: 4 попытки на команду, 3 серии ошибок подряд → флаг ошибки
подсистемы BLE. `AT+SLEEP` в штатном ритме не используется (сканер должен
работать непрерывно) — только сервисные сценарии (выключение, DFU).

## 5. Таблица устройств на MCU

MCU хранит **свою** таблицу «MAC → что за устройство» в энергонезависимой
памяти (внешняя flash, область CONFIG); заполняется конфигуратором (п. 6),
при каждом включении передаётся модулю целиком (п. 4.5).

> **Владелец таблицы — основная программа; доступ — только BLE и основная
> программа (поправка автора, PLAN п.66). По LoRa таблица MAC-адресов не
> передаётся и не обслуживается** — LoRa несёт только `ShortID`
> (Mirax-Lora-protocol-v4.md §4.7).

```c
#define BLE_MAC_TABLE_MAX   (32u)   // ёмкость (рабочий максимум 26)

typedef enum {
    DEV_TYPE_NONE     = 0,          // ПУСТОЙ СЛОТ (MAC нулевой, неактивен)
    DEV_TYPE_BEACON   = 1,          // маяк
    DEV_TYPE_PPE      = 2,          // метка СИЗ
    DEV_TYPE_BRACELET = 3,          // браслет (пульсометр)
    DEV_TYPE_GAS      = 4           // газоанализатор AVIS
} ble_dev_type_t;

typedef struct {
    uint8_t Mac[6];    // MAC устройства, старший байт первым;
                        // пустой слот — 00:00:00:00:00:00
    uint8_t DevType;   // ble_dev_type_t — определяет ПАРСЕР payload (п. 3)
    uint8_t Param;     // смысл ЗАВИСИТ ОТ DevType (Slot и PpeType объединены
                        // в один байт — они применяются к разным типам):
                        //   СИЗ     → PpeType (0 каска, 1 привязь, ...);
                        //   маяк/браслет/AVIS/пустой → 0 (резерв; порядок
                        //             маяков в списке = порядок в таблице)
    uint16_t ShortID;   // ТОЛЬКО маяк (LE): 0 = взять из Eddystone BID[4..5]
                        // (наши маяки); !=0 = назначен конфигуратором
                        // (сторонние маяки). Остальным типам: 0
} __attribute__((packed)) ble_mac_entry_t;   // 10 байт
```

Правила:

- **слоты назначает конфигуратор**: у каждого устройства комплекта свой
  порядковый номер; незаполненные номера остаются **пустыми слотами**
  (`DEV_TYPE_NONE`, нулевой MAC) — нумерация не уплотняется и не ломается.
  MCU передаёт таблицу модулю **всегда целиком, по порядку**, пустые слоты —
  нулевыми MAC (`MACSET`, п. 4.1);
- **порядок записей таблицы MCU = нумерация слотов модуля** (таблица модуля —
  зеркало нашей, передаётся вместе с типами: `MACSET=<N>,<mac>,<тип>,...` —
  тип привязан к индексу слота): слот i ↔ запись i; опрос — bulk-командой
  `MSDGETALL` (п. 4.3), пустые слоты возвращаются со Status 0 и пропускаются;
- **DevType выбирает парсер** payload из `MSDGET`: 1 → маяк (нормализованная
  запись `ble_beacon_norm_t` 4 байта — Eddystone разбирает модуль, п. 3.1),
  2 → метка СИЗ (3 байта), 3 → браслет (5 байт), 4 → AVIS (6+6N, п. 3.4).
  Контроль — по длине payload (п. 3.0): не сошлась → пакет отбрасывается,
  счётчик ошибок;
- **позиция СИЗ в масках LoRa** (бит `PresenceMask`/`PPEEnabledMask`, порядок
  `ppe_descr_t[]` в `TYPE_STATIC`) = **порядковый номер записи СИЗ в таблице,
  считая только записи СИЗ и пропуская пустые слоты** (k-я запись СИЗ = бит k).
  Таблица пишется конфигуратором атомарно (п. 6), порядок стабилен; отдельного
  поля Slot для СИЗ не нужно — байт `Param` у СИЗ несёт PpeType;
- **серийников в таблице нет**: заводские идентификаторы приходят из payload
  устройств (Serial метки СИЗ, Serial браслета). Пакет AVIS серийника
  не несёт (`dev_id` — номер модели прибора, не серийник) — п. 11. Исключение —
  `ShortID` маяка: у наших берётся из BID[4..5] рекламы, у сторонних (instance
  заблокирован/произволен) — назначается конфигуратором в это поле таблицы.
  `PpeType`
  для `TYPE_STATIC` — из `Param` (известен сразу) и сверяется с payload при
  приёме; `Serial` для `TYPE_STATIC` — из payload: до первого приёма
  устройства = 0 (неизвестен), сервер уточнит по следующему `TYPE_STATIC`;
- таблица меняется только конфигуратором (п. 6); после изменения MCU
  сохраняет её в энергонезависимую память и **немедленно** перезаписывает
  таблицу модуля одной `MACSET` (кэши всех слотов при этом сбрасываются,
  п. 4.1.1);
- фиксированные SubID LoRa v4: браслет = 1 (`SUB_TYPE_PULSE`), AVIS = 2
  (`SUB_TYPE_GAS`) — как в примере v4 п. 8.2.

## 6. Внешний конфигуратор (BLE)

Конфигуратор (приложение на телефоне/планшете) подключается к модулю трекера
по имени рекламы `VEC%04d%04d` и обменивается с MCU кадрами **Modbus RTU**:
MCU — слейв, конфигуратор — мастер. Содержимое кадров (карта регистров —
таблицы и прочие данные трекера) — вне рамок этого протокола; здесь закреплён
транспорт — как кадры проходят по BLE и UART.

**GATT (значения предварительные, п. 11):** сервис `0xFFE0`; характеристика
`0xFFE1` (Write / Write w/o response) — мастер → MCU; `0xFFE2` (Notify) —
MCU → мастер. **Один GATT-write = один кадр Modbus RTU целиком** (границы
кадра сохраняются записью, тайминговая пауза 3.5 символа RTU не используется).

**Транспорт через модуль** — п. 4.4: модуль → MCU — URC `+MBUS:<len>` + raw
кадр; MCU → модуль — `AT+MBUSRSP=<len>` + prompt `>` + raw кадр → notify.

**Поведение MCU (Modbus-слейв) в части таблицы устройств:**

- регистры таблицы (слоты: MAC/DevType/Param/ShortID) ведутся в RAM-образе;
  у каждого
  устройства свой номер слота, незаполненные слоты остаются пустыми;
- применение таблицы — по записи регистра **«применить/commit»**: MCU
  валидирует образ → сохраняет в энергонезависимую память (внешняя flash,
  CONFIG) → `AT+MACSET` модулю (целиком, пустые слоты — нулями); до commit
  изменения не действуют — сессия атомарна, обрыв связи оставляет прежнюю
  таблицу;
- чтение таблицы мастером — обычные чтения регистров (контроль после записи).

**Тайминги:** таймаут ответа Modbus-мастера должен учитывать мост
(GATT-write → очередь/URC → обработка MCU → notify): рекомендуется ≥ 1 с на
транзакцию, повторы при таймауте — на стороне мастера.

Состав комплекта (какие MAC, типы, PpeType, номера слотов) знает монтажная
организация; ShortID маяков и Serial устройств в таблицу НЕ входят — они
приходят из эфира (п. 3.1–3.3).

## 7. Кэш данных MCU и маппинг в LoRa v4

### 7.1 Кэш MCU

MCU разбирает `Payload` записи `msd_slot_rec_t` по DevType слота
(контроль — по длине, п. 3.0) и хранит в своём кэше по каждому слоту:
последние значения полей + момент подтверждения приёма (`last_seen`).
Состав хранимых полей — п. 7.2; свежесть и «отсутствие» — п. 7.3. По маякам
модуль выдаёт нормализованную запись `{ShortID, Vbatt}` с маркерами `0xFFFF`
(«кадров этого типа с прошлого чтения не было») — MCU мержит части между
чтениями и конвертирует `Vbatt` → Battery 0/1/2 по порогам из конфига.

### 7.2 Соответствие «BLE → LoRa v4»

| Источник | Из payload | Из ответа MSDGET | Из таблицы MCU | Блоки LoRa v4 |
|----------|-----------|------------------|----------------|----------------|
| Маяк (DevType 1, Eddystone) | нормализованный: ShortID (из BID[4..5]), Vbatt мВ → Battery 0/1/2 (пороги в конфиге MCU); 0xFFFF — сохранить прежнее | Rssi, AgeSec | ShortID (≠0 — приоритет, сторонние маяки); порядок = порядок таблицы | `BLEBeacons` (бит 8): `ble_beacon_t` байт-в-байт |
| Метка СИЗ (2) | PpeType, Serial (u8), State.7 (надето), State.0..1 (заряд) | AgeSec | № записи среди СИЗ → бит маски; Param → PpeType (до приёма) | `PPE` (бит 7): `PresenceMask` + `Charge[]`; `TYPE_STATIC`: `PPEEnabledMask` + `ppe_descr_t{Type, Serial}` (Serial u16: старший байт 0) |
| Браслет (3) | Serial (u8), Battery %, HeartRate, SpO2 | AgeSec | SubID = 1 (фикс.) | секция `SUB_TYPE_PULSE`: Battery / HeartRate / SpO2; `TYPE_STATIC`: `sub_descr_t.Serial` |
| AVIS (4) | charge, каналы (SensorIndex/Type_gas/Concentration/State_channel/Setting_channel), active_sensors, версии, dev_id (номер модели) | AgeSec | SubID = 2 (фикс.) | секция `SUB_TYPE_GAS`: Battery + Sensors (`StateErr`); `TYPE_STATIC`: `sub_descr_t` (Serial — п. 11) + `channel_cfg_t[]` |

Сборка списков для LoRa — на MCU: `BLEBeacons.Count` и биты `PresenceMask`
формируются из **свежих** записей кэша (п. 7.3); контейнерный `EventLog`
(события `0x20/0x21/0x22` по маске СИЗ) — по LoRa v4 п. 4.8.
Пороговые состояния газовых каналов AVIS (`StateErr`) — в секции
`SUB_TYPE_GAS`; обнаружение порога на учащённом опросе (п. 4.6) — основание
для аварийного ритма LoRa.

### 7.3 Свежесть (TTL) и «отсутствие»

**Правило включения в LoRa-пакет (решение автора):** данные с BLE попадают в
пакет LoRa, только если они **свежие**. Данные **не обновились** (с прошлого
чтения реклама не приходилась), **не готовы** (устройство никогда не
принималось) или устройство **не отвечает** (TTL истёк) → соответствующего
блока/секции в пакете LoRa **нет** (а не «нули»):

Кэш модуля очищается при чтении (п. 4.1.1), поэтому логика MCU простая:

- `MSDGET` вернул **Status 1** → устройство вещало с прошлого опроса →
  обновить данные слота и поставить `last_seen = now`;
- **Status 0** → за период ничего не поймано → `last_seen` не меняется;
- слот считается присутствующим, пока `now − last_seen ≤ TTL = 5 минут`
  (60 циклов bulk-опроса при ритме 5 с — одиночные пропуски приёма и потери
  ответов UART перекрываются с огромным запасом). Устарел:
  - **СИЗ** → бит позиции в `PresenceMask` = 0 («отсутствует» — ровно то, что
    ждёт LoRa v4: не поймали — нету);
  - **маяк** → не включается в список `BLEBeacons`;
  - **браслет / AVIS** → секция под-устройства в кадр не включается
    (`SubCount` уменьшается); `TYPE_STATIC` состав комплекта описывает всегда
    (из таблицы MCU), независимо от приёма.

## 8. Бюджет размера

**Два разных лимита:**

1. **пакет данных ≤ 256 байт** — эфирный payload, двоичный кадр ответа
   (`msdget_resp_t`), кадр Modbus RTU;
2. **строка AT-команды** ограничена буферами UART, не 256 байтами: передача
   MCU — 560 байт, приём строки модулем — **≥ 512 байт** (`MACSET` полной
   таблицы = 493 символа помещается в оба).

| Пакет/строка | Максимум | Лимит |
|-------|----------|-------|
| маяк в эфире: Eddystone-UID / TLM | 20 / 14 | 256 |
| маяк в ответе MSDGET (нормализованный) | 4 | 256 |
| payload метки СИЗ (эфир) | 3 | 256 |
| payload браслета (эфир) | 5 | 256 |
| пакет AVIS (эфир) | 54 (6 + 6×8) | 256 |
| запись `msd_slot_rec_t` (слот с AVIS) | 60 (2 + 4 + 54) | 256 |
| hex-ответ `MSDGET` (один слот) по UART | 2 + 120 + 2 = 124 | буфер 640 |
| hex-ответ `MSDGETALL` (весь комплект) по UART | ≈ 612 (304 binary × 2 + обрамление) | буфер 640 |
| строка `AT+MACSET` (32 слота, MAC+тип) | 493 | буферы 560/512 |
| кадр Modbus RTU (мост, raw) | 256 (+≈14 байт обрамление `+MBUS:`) | 256 / буферы |
| таблица MCU (энергонезависимая память) | 32 × 10 = 320 байт | — |
| кэш всех устройств на MCU | 26 × 59 ≈ 1.5 КБ RAM | — |

AD-структура СИЗ — 7 байт, браслета — 9: влезает в legacy advertising 31 байт.
Маяк (Eddystone-UID) занимает полные 31 байт (Flags + список UUID 0xFEAA +
Service Data 24) — по спецификации Eddystone; TLM — 18 байт. Пакет AVIS с полным набором каналов — до 2 + 2 + 54 = 58 байт AD:
требуется extended advertising либо scan response на стороне прибора/модуля
(п. 11).

### 9.1 Реклама в эфире (СИЗ/браслет/AVIS — Manufacturer Data `[Len][FF][CID][payload]`; маяк — Eddystone Service Data)

| Устройство | Байты AD | Разбор payload |
|---|---|---|
| Маяк, Eddystone-UID, ShortID 0x0207 | `02 01 06 03 03 AA FE 17 16 AA FE 00 C7 A0 B1 C2 D3 E4 F5 06 17 28 39 00 00 00 01 02 07 00 00` | полные 31 байт: Flags; список UUID `0xFEAA`; Service Data (Len `0x17`): Frame Type `0x00` (UID), Ranging `0xC7` = −57 дБм, NID `A0…39` (10 Б), BID `00 00 00 01 02 07` → **ShortID = BID[4..5] = 0x0207** (BE), RFU |
| Тот же маяк, Eddystone-TLM | `11 16 AA FE 20 00 0B B8 19 00 00 00 00 2A 00 00 03 E8` | Frame `0x20`, ver 0; VBATT `0x0BB8` = 3000 мВ → Battery 2 «норма»; TEMP `0x1900` = +25.0 °C; ADV_CNT 42; SEC_CNT 1000 (100.0 с); поля BE |
| СИЗ каска, Serial 0x11, надета, заряд норма | `06 FF FF FF 00 11 82` | PpeType 0 (каска); Serial 0x11; State `0x82` = бит7 (надето) + заряд 2 |

### 9.2 Запись таблицы модулю

Один слот (маяк):

```
→ AT+MACSET=1,112233445566,1\r          (27 символов; тип 1 = маяк)
← OK
```

Четыре слота, из них слот 1 — ПУСТОЙ (конфигуратор не заполнил номер 1 —
шлём нулевой MAC с типом 0, чтобы нумерация не поехала):

```
→ AT+MACSET=4,112233445566,1,000000000000,0,AABBCCDDEEFF,2,010203040506,4\r
← OK                    слот 0 = 11:22:33:44:55:66, тип 1 (маяк — модуль
                        ждёт Eddystone и нормализует в {ShortID, Vbatt})
                        слот 1 = пустой (нулевой MAC, тип 0 — не сканируется)
                        слот 2 = AA:BB:CC:DD:EE:FF, тип 2 (СИЗ)
                        слот 3 = 01:02:03:04:05:06, тип 4 (AVIS)
→ AT+SCANSTART=1\r
← OK
→ AT+MACGET?\r
← \r\n + "041122334455660100000000000000AABBCCDDEEFF0201020304050604" + OK
   кадр: Count 4; далее (MAC[6] + Type): маяк / пустой / СИЗ / AVIS
```

### 9.3 Чтение данных (таблица из п. 9.2)

**Bulk-опрос всей таблицы одной транзакцией** (штатный режим, каждые 5 с):

```
→ AT+MSDGETALL?\r
← \r\n + "04000801C403000702B80B0104007FFFFF020701B501000011820304007FFFFF" + OK
   кадр (32 байта binary), разбор по TLV (Slot + Len + Len байтов):
   04                                Count = 4 записи
   00 08 | 01 C4 0300 0702B80B       слот 0, Len 8: Status 1; Rssi −60;
                                     AgeSec 3; payload 4 Б — наш формат:
                                     ShortID 0x0207 (LE), Vbatt 0x0BB8 = 3000 мВ
                                     → следующая запись через 2+8 = 10 байт
   01 04 | 00 7F FFFF                слот 1 (пустой), Len 4: Status 0
   02 07 | 01 B5 0100 001182         слот 2, Len 7: Status 1; Rssi −75;
                                     AgeSec 1; payload 00 11 82 (каска,
                                     Serial 0x11, надета, заряд 2)
   03 04 | 00 7F FFFF                слот 3 (AVIS), Len 4: Status 0 — не принят
   → кэши слотов 0 и 2 очищены модулем
```

Если с прошлого чтения пришёл только UID (TLM не было), payload слота 0 был бы
`07 02 FF FF` — MCU сохранит прежний Vbatt (мерж частей, п. 3.1).

**Одиночное чтение** (режим 2, тот же формат записи). Слот 0 — до новой
рекламы пуст (кэш очищен предыдущим чтением):

```
→ AT+MSDGET=0\r
← \r\n + "0004007FFFFF" + OK
   запись: Slot 0; Len 4; Status 0; Rssi 0x7F (нет); AgeSec 0xFFFF
```

Слот 2 (СИЗ) за период не пойман:

```
→ AT+MSDGET=2\r
← \r\n + "0204007FFFFF" + OK        → Status 0
   → PresenceMask: бит этой СИЗ = 0 (по истечении TTL — «отсутствует»)
```

Слот 1 — пустой: всегда Status 0.

### 9.4 Мост конфигуратора (Modbus RTU через `+MBUS:`)

Мастер (конфигуратор) пишет один регистр слейву трекера (адрес 0x01):
функция 0x06, регистр 0x0010, значение 0x0002, CRC16 Modbus `0xCE09`
(пример условный — карта регистров вне рамок этого протокола):

```
кадр Modbus RTU (8 байт): 01 06 00 10 00 02 09 CE

GATT-write (0xFFE1):      01 06 00 10 00 02 09 CE        — кадр целиком

модуль → MCU (UART, URC): "+MBUS:8\r\n" 01 06 00 10 00 02 09 CE "\r\n"

MCU (Modbus-слейв) обрабатывает кадр, формирует ответ (эхо записи) и шлёт:
MCU → модуль:             "AT+MBUSRSP=8\r"
модуль → MCU:             ">\r\n"
MCU → модуль:             01 06 00 10 00 02 09 CE
модуль → MCU:             "OK"
GATT-notify (0xFFE2):     01 06 00 10 00 02 09 CE        — мастеру
```

Запись таблицы конфигуратором — серия таких транзакций (записи регистров
слотов + регистр «применить», п. 6); после «применить» MCU сохраняет таблицу
и выполняет одну `AT+MACSET` новым образом целиком.

## Принятые решения

1. **Фильтр по MAC вместо UUID**: MAC берётся из PDU рекламы автоматически,
   в payload не дублируется; фильтр — таблица модуля, которую MCU передаёт
   `MACSET` при каждом включении.
2. **Модуль не агрегирует** (пакетов-«списков» в протоколе нет): модуль хранит
   кэш «последний payload + RSSI + возраст» per-MAC; списки для LoRa собирает
   MCU по ответам `MSDGET`.
3. **В payload нет Header-байта** (типа/версии нет): устройство
   определяется **только по таблице MAC** (DevType → парсер); контроль — по
   длине payload. Первый байт пакета AVIS (`data_struct_ver`) — поле формата
   AVIS, а не идентификатор протокола.
4. **Заводские идентификаторы — 1 байт** (Serial метки СИЗ, Serial браслета);
   в LoRa-полях u16 (`ppe_descr_t.Serial`, `sub_descr_t.Serial`) старший байт = 0.
5. **Таблица MCU — 10 байт на запись**: `MAC[6] + DevType + Param +
   ShortID(u16)`; Slot и PpeType **объединены** в `Param` (СИЗ → PpeType,
   остальным → 0/резерв). **Серийников в таблице нет** — идентификаторы
   приходят из payload устройств; `ShortID` — исключение для маяков: 0 = взять
   из BID[4..5] (наши), ≠0 = назначен конфигуратором (сторонние). Позиция СИЗ
   в масках LoRa = порядковый номер записи СИЗ в таблице (пустые слоты
   пропускаются).
6. **Одна команда таблицы — `MACSET`, полная перезапись**: добавление/удаление/
   замена записи = новый полный образ таблицы; отдельных `MACADD`/`MACDEL`
   нет. **Каждая запись несёт тип** (`<mac>,<тип>`): при задании таблицы
   фильтров по индексу к слоту привязывается DevType — модулю тип нужен для
   нормализации Eddystone (маяки) и ожидания правильного AD. Нумерация слотов
   задаётся конфигуратором и не уплотняется: **незаполненный слот передаётся
   нулевым MAC с типом 0** (`000000000000,0`) — очередь не ломается; модуль
   такой слот не сканирует.
7. **Кэш модуля самоочищается при чтении**: `MSDGETALL`/`MSDGET` выдают
   последние данные слотов и сбрасывают их кэш; Status 1 = «вещало с прошлого
   опроса». Записи слотов самоограничивающие (TLV: `Slot + Len + тело`) —
   границы между слотами в bulk-ответе детерминированы при любой длине
   payload (в т.ч. переменной у AVIS); оба режима читаются одним парсером. Live-поток (URC на каждую рекламу) отклонён: до ~80 кадров/с по
   UART и постоянный парсинг на MCU не нужны при опросном ритме. Ручной
   `MSDCLR` не нужен.
8. **Таблица помещается в одну строку `MACSET`** (MAC+тип на слот): N=1 —
   27 символов, N=26 — 403, N=32 — 493; буфер передачи MCU 560, RX-буфер
   строки модуля ≥ 512.
9. **Лимит 256 байт — только для пакетов данных** (эфирный payload, кадр
   ответа, кадр Modbus); строки AT-команд ограничены буферами UART (п. 8).
10. **AT-набор — нормативная спецификация прошивки MK01**: внешней
    спецификации на модуль нет, сканерская прошивка реализуется строго по п. 4;
    сервисные команды наследуются из действующей прошивки MK01.
11. **Конфигуратор — Modbus RTU через прозрачный мост**: у Modbus свои рамки и
    CRC — дополнительное обрамление кадров не нужно; карта регистров вне рамок
    этого протокола. Транспорт: GATT (write = кадр целиком) → UART-идентификатор
    **`+MBUS:<len>`** (модуль → MCU, spontaneous, очередь ≥ 8) → ответ MCU
    **`AT+MBUSRSP=<len>`** + prompt `>` + raw → notify мастеру. MCU —
    Modbus-слейв; применение таблицы — по регистру «commit».
12. **Пакет AVIS — `str_ble_data_set_t`**: `active_sensors` (маска) +
    `sensors[7]`, запись канала 6 байт (ver 3: `Setting_channel` u16 —
    биты DEVICE_SETTING_CHAN + MEASURE_*; позиция записи = номер канала),
    максимум 48 байт; `Concentration` — `uint16_t` (2 байта LE на проводе).
    **`dev_id` — номер модели (тип прибора), НЕ серийный номер**; серийник
    legacy-пакет не несёт (несёт SUBDEV, п. 3.4a). Совместимость со старым
    форматом действующей прошивки AVIS (ver 2: 5 байт на канал, Setting u8) —
    трекер принимает ОБЕ версии, ver 2 конвертируется в ver 3 (решение автора,
    PLAN п.65). Целевой задел: `SensorIndex` в записи + `sensors[8]`.
13. **Все устройства connectable** (сервис/конфигурация — запись ShortID в маяк
    и т.п.), но телеметрия — только реклама; модуль трекера в рабочем режиме не
    подключается ни к кому, кроме конфигуратора (и только он — к трекеру).
14. **Присутствие СИЗ — двухуровневое**: нет свежих данных → бита маски нет
    («отсутствует»); есть → бит по `State.7`. Пороги заряда — на сервере.
15. **Сканирование непрерывное; опрос кэша — в двух равноправных режимах**:
    bulk `MSDGETALL` (по умолчанию каждые 5 с; все слоты, включая пустые —
    Status 0, одним сообщением ~612 символов hex ≈ 53 мс UART; буфер
    приёма MCU 640 байт; при ограничении буфера — диапазоном `=<от>,<кол-во>`) либо
    `MSDGET=<i>` по слотам — когда у устройств разная периодичность рекламы и
    критичность (AVIS учащённо, остальные реже). Свежесть — на MCU (TTL 5 мин):
    `last_seen` обновляется при Status 1; одиночные пропуски перекрываются.
16. **Несвежие данные в LoRa-пакет не входят**: не обновились / не готовы /
    устройство не отвечает → блок или секция исключается из состава пакета
    (бит СИЗ в маске = 0, маяк не входит в список, секция браслета/AVIS не
    включается, `SubCount` уменьшается) — п. 7.3.
17. **Маяки — Eddystone (UID + TLM), нормализация — в модуле** (решение
    автора: совместимость со сторонними маяками): САМИ маяки вещают Eddystone;
    **модуль трекера разбирает UID/TLM и упаковывает в наш формат** —
    нормализованная запись `ble_beacon_norm_t` {ShortID u16 LE (из BID[4..5],
    конверсия BE→LE в модуле), Vbatt u16 мВ LE}; MCU сырой Eddystone не видит.
    `0xFFFF` в части = «кадров этого типа с прошлого чтения не было» — MCU
    мержит части и хранит последнее известное значение. Наши маяки: BID[4..5] =
    ShortID (запись при монтаже) + TLM 1:10; сторонние: ShortID назначает
    конфигуратор в таблицу (приоритет над BID). Battery 0/1/2 — из Vbatt
    пороговой конверсией НА MCU (пороги в конфиге; Vbatt=0 → 2 «норма»);
    TLM не принят ни разу → 0xFF «неизвестно». URL/EID игнорируются.
    Собственный 3-байтовый эфирный формат маяка — отменён.

## Остаётся уточнить

- **Пороги Vbatt → Battery 0/1/2** — на MCU, под тип батареи маяка (дефолты в
  конфиге трекера); `Vbatt = 0` (питание без батареи) → 2 «норма».
- **Валидация «тип из MACSET ↔ фактическая реклама»**: для слота-маяка модуль
  ждёт Service Data 0xFEAA, для остальных — Manufacturer Data; несовпадение —
  счётчик/признак в ответе (защита от ошибок таблицы).
- **Соотношение TLM:UID и период у наших маяков** — рекомендуется 1:10 при
  UID 1000 мс (TLM ≈ раз в 10 с); подтверждается при разработке прошивки маяка.
- **Battery без принятого TLM** (старт / сторонний маяк без TLM) —
  предварительно `0xFF` «неизвестно»; семантику отразить в LoRa v4
  (`ble_beacon_t.Battery`).
- **Namespace (NID) наших маяков** — способ генерации по спеке Eddystone
  (хэш FQDN или elided UUID), назначается при производстве; значение — за
  автором.
- **Конфигурация наших маяков при монтаже** — стандартный Eddystone-Config
  (GATT) или свой конфигуратор; процедура записи NID/BID(ShortID)/периодов.
- **Сторонние браслеты** — единого рекламного формата пульса в BLE нет;
  стандарт (Heart Rate Service 0x180D + Battery 0x180F, SpO2 — PLX 0x1822)
  работает только ПО СОЕДИНЕНИЮ. Наши браслеты — своя реклама (п. 3.3);
  совместимость со сторонними — отдельная задача на режим соединения в
  прошивке модуля, сейчас не закладывается.
- **Внутренние параметры прошивки MK01**: параметры скана по умолчанию
  (`SCANPARAM`), счётчик потерянных кадров очереди моста.
- **CompanyID manufacturer data** — предварительно `0xFFFF` (внутренний);
  нужен ли зарегистрированный Bluetooth SIG идентификатор компании.
- **Формат пакета AVIS и парк приборов** — РЕШЕНО (автор, PLAN п.65):
  `data_struct_ver = 3`, запись канала 6 байт (`Setting_channel` u16),
  трекер принимает обе раскладки (ver 2 конвертируется). Целевой задел:
  `SensorIndex` в записи и `sensors[8]` (маска active_sensors — полный u8).
- **Реклама AVIS > 31 байта** — механизм передачи длинного пакета (до 58 байт
  AD): extended advertising / scan response; какой тип ADV-событий принимать
  сканеру (ADV_IND/ADV_NONCONN_IND/ADV_EXT_IND).
- **GATT конфигуратора**: UUID сервиса/характеристик (предварительно
  0xFFE0/E1/E2), безопасность (pairing/bonding, шифрование канала), MTU.
- **Сигнал подключения конфигуратора**: `CONNSTATE?` либо URC от модуля при
  подключении/отключении (например `+CONN:0/1` — удобнее для режима
  конфигурирования).
- **Тип адреса**: устройства с public MAC (принято); при random static —
  расширение записи таблицы байтом AddrType (и в `MACSET`, и в регистрах).
- **Запись ShortID в маяк и Serial в метку/браслет при монтаже** — процедура
  конфигуратора через соединение с устройством.
- **Serial браслета в payload** — нужен ли (если нет — поле убрать;
  `sub_descr_t.Serial` в LoRa останется незаполненным).
- **Серийник AVIS** — пакет его не несёт (`dev_id` — номер модели):
  способ передачи (обновление прошивки AVIS / запись на производстве /
  иной) — TBD.
- **Бит «надето» метки СИЗ и Flags браслета** — источник (датчик ношения);
  до его появления бит = видимость устройства.
- **SpO2 браслета** — реальные значения, когда датчик появится (сейчас 0 =
  нет данных, бит SubMask в LoRa не включается).
