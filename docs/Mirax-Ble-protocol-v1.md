# Протокол обмена MIRAX BLE v1

## 1. Общие положения

Протокол v1 (**MIRAX BLE**) описывает обмен по BLE между **трекером VECTOR**
(центральный носимый прибор, STM32U575 + модуль MK01 в роли хозяина/мастера)
и окружающими устройствами комплекта:

- **газоанализатор AVIS** — под-устройство (единственное подключаемое,
  решение автора); существующие приборы AVIS вещают legacy-пакет
  `str_ble_data_set_t` (Avis `Ble_mk01.h`, `DATA_STRUCT_VER = 2`) — он
  принимается **как есть**, перепрошивка парка AVIS не требуется;
- **инфраструктурные BLE-маяки** — наше оборудование, программируемое при
  монтаже: вещают общий UUID инфраструктуры + короткий идентификатор
  (`ShortID`, minor/instance) + состояние своего заряда;
- **метки СИЗ** (каска/привязь/маска/…) — наличие и заряд единиц СИЗ.

Назначение протокола — доставка на трекер данных, которые затем уходят в
LoRa v4 (`Mirax-Lora-protocol-v4.md`): блоки `BLEBeacons` (п. 4.7), `PPE`
(п. 4.6), секция под-устройства `SUB_TYPE_GAS` (п. 5.2) и состав
`TYPE_STATIC` (п. 6: `PPEEnabledMask`/`ppe_descr_t`, `sub_descr_t`).

**Основные принципы:**
- единый байт-заголовок (`Header`) у всех пакетов v1: старший nibble — тип,
  младший — версия протокола (как `Header` в LoRa v4, п. 2);
- совместимость с legacy Avis: пакет AVIS v2 начинается с байта `0x02`
  (тип 0, версия 2) и однозначно отличается от пакетов v1;
- желательно всё одним пакетом (AGG, п. 5.5), но каждый тип устройств может
  приходить и отдельным пакетом — приёмник разбирает оба варианта;
- **ограничение размера пакета — 256 байт** (решение автора); фактический
  бюджет даже полного агрегата ~160 байт (п. 8);
- все многобайтные поля — **little-endian**;
- трекер фильтрует эфир **по нашему общему UUID** (чужой BLE — телефоны,
  гарнитуры — игнорируется); значение UUID назначается при монтаже и в
  прошивку трекера не зашивается (его держит модуль MK01).

Единицы концентраций газа, коды газов (`Type_gas`/`GasID`) и маски `Setting`
— как в LoRa v3/v4 (приложение v4): трекер полученные от AVIS концентрации
**не масштабирует повторно** (отправитель уже применил
`Discreteness × conversion_factor_rf` в своём `Ble_CompleteDataSet`) и
передаёт в LoRa pass-through.

## 2. Транспорт (модуль MK01, UART AT-команды)

MCU ↔ свой модуль MK01: USART 115200 8N1, синхронный обмен AT-командами
(порт `Ble_mk01.c`: 4 попытки, контроль `OK`/`ERROR`, серия из 3 ошибок →
флаг ошибки BLE). Команды модуля (Avis + v27):

| Команда | Назначение |
|---------|------------|
| `AT` | проверка связи |
| `AT+MODINFO?` | информация о модуле |
| `AT+ADVBLENAMESET=<имя>` | имя модуля в сети (`BLE_Label` + `%04d%04d` серийника) |
| `AT+ADVMSDDATAGET` | **запрос принятых данных** (ответ — пакет(ы) протокола v1) |
| `AT+ADVSTART=0/1`, `AT+ADVPERIODMS=n`, `AT+ADVPOWER=n` | параметры рекламы |
| `AT+SLEEP`, `AT+SYSTEMOFF`, `AT+DFU`, `AT+BLEADDR?` | сервис |

Штатный ритм опроса `ADVMSDDATAGET` — `TIMER_RTC_BLE_DATA_SET` (60 с,
`Ble_Run`, Measure Task), как у Avis `Ble_MsdDataSet`.

**Формат ответа на `ADVMSDDATAGET` (допущение v27, уточнить — п. 10):**
`эхо(2 байта) + hex-ASCII данные пакета + "OK"`. Hex удваивает объём,
поэтому UART-буфер приёма 520 байт; после раскодирования пакет ≤ 256 байт.

Роль модуля в эфире — сканер/наблюдатель нашего UUID-сегмента: он принимает
рекламы маяков/меток/AVIS (п. 4) и отдаёт MCU готовые списки (п. 5).
Подключается при этом только AVIS (решение автора: «Avis будет только один
подключаться»); маяки и метки — только реклама, без соединения.

## 3. Заголовок пакета и типы

Первый байт ЛЮБОГО пакета:

| Биты | Назначение |
|------|------------|
| 7..4 | Тип пакета (`BLE_PKT_TYPE`) |
| 3..0 | Версия протокола (v1 = 1; legacy Avis = 2 при типе 0) |

```c
#define BLE_PROTO_VER  (1u)
#define BLE_PKT_HEADER(type)  (((type) << 4) | BLE_PROTO_VER)

enum BLE_PKT_TYPE {
    BLE_PKT_GAS_LEGACY = 0,   // пакет Avis v2 (str_ble_data_set_t, байт 0x02)
    BLE_PKT_BEACONS    = 1,   // список видимых маяков   (модуль -> MCU), 0x11
    BLE_PKT_PPE        = 2,   // список видимых СИЗ      (модуль -> MCU), 0x21
    BLE_PKT_SUBDEV     = 3,   // под-устройство с серийником (задел), 0x31
    BLE_PKT_BEACON_ADV = 4,   // реклама ОДНОГО маяка    (маяк -> модуль), 0x41
    BLE_PKT_PPE_ADV    = 5,   // реклама ОДНОЙ метки СИЗ (метка -> модуль), 0x51
    BLE_PKT_AGG        = 15   // агрегат: всё одним пакетом (модуль -> MCU), 0xF1
};
```

Тип 0 зарезервирован за legacy Avis: первый байт пакета AVIS —
`data_struct_ver = 2` → `0x02` (тип 0, версия 2). Пакеты v1 имеют версию 1
в младшем nibble, коллизия с legacy исключена (Avis `data_struct_ver`
больше 15 не бывает, а при типе 0 версия 2 отличима от версий v1).

## 4. Пакеты устройств в эфире (реклама, manufacturer data)

### 4.1 Маяк (`BLE_PKT_BEACON_ADV`, Header `0x41`)

Маяк вещает под общим UUID инфраструктуры этот пакет в manufacturer data:

```c
typedef struct {
    uint8_t  Header;     // 0x41
    uint16_t ShortID;    // короткий ID (minor/instance), LE — зашит при монтаже
    uint8_t  Battery;    // 0 разряжен, 1 предупреждение, 2 норма
} ble_pkt_beacon_adv_t;  // 4 байта
```

`ShortID → (координата/зона/этаж, MAC)` — в реестре маяков на сервере
(LoRa v4 п. 4.7); раздачи идентификаторов на трекеры нет, трекер только
ретранслирует ShortID + добавленный модулем RSSI.

### 4.2 Метка СИЗ (`BLE_PKT_PPE_ADV`, Header `0x51`)

```c
typedef struct {
    uint8_t  Header;     // 0x51
    uint8_t  PpeType;    // тип СИЗ (приложение LoRa v4: 0 каска, 1 привязь, ...)
    uint16_t Serial;     // заводской идентификатор единицы, LE
    uint8_t  State;      // биты 0..1 = заряд (0/1/2), бит 7 = надето/присутствует
} ble_pkt_ppe_adv_t;     // 5 байт
```

Признак «надето» (бит 7) определяет сама метка (датчик ношения — задел;
до его появления бит выставляется всегда, когда метка на человеке в зоне
приёма, см. п. 10).

### 4.3 Газоанализатор AVIS (legacy, байт `0x02`)

Существующая прошивка AVIS вещает `str_ble_data_set_t` (Avis `Ble_mk01.h`,
`ADVMSDDATASET`): шапка 6 байт + 5 байт на включённый канал — **без
изменений** (п. 5.1).

## 5. Пакеты модуль → MCU (ответ `ADVMSDDATAGET`)

### 5.1 Legacy AVIS (`BLE_PKT_GAS_LEGACY`) — байт-в-байт Avis

```c
typedef struct {                 // 5 байт, как sensor_data_t в Avis
    uint8_t Type_gas;            // код газа/канала (num_formula_gas)
    uint8_t Concentration[2];    // концентрация LE (единицы отправителя)
    uint8_t State_channel;       // StateErr & 0x7F отправителя
    uint8_t Setting_channel;     // DeviceSetting & (MEASURE_MASK|MEASURE_DISK)
} ble_sensor_data_t;

typedef struct {                 // как str_ble_data_set_t в Avis Ble_mk01.h
    uint8_t data_struct_ver;     // = 2 -> Header 0x02 (тип 0, версия 2)
    uint8_t dev_id;              // идентификатор МОДЕЛИ отправителя (DIVICE_ID_BLE)
    uint8_t dev_hw_ver;
    uint8_t dev_fw_ver;
    uint8_t charge;              // заряд батареи отправителя, %
    uint8_t sensors_enabled:5;   // маска включённых каналов (бит0 = канал0)
    uint8_t rfu:3;
    ble_sensor_data_t sensors[7];
} str_ble_data_set_t;            // максимум 6 + 5×7 = 41 байт
```

Отправитель передаёт `6 + 5×popcount(sensors_enabled)` байт. Шапка —
«базовая информация» отправителя (решение автора: шапка с базовой
информацией сохраняется). Серийный номер legacy-пакет НЕ несёт — для
`sub_descr_t.Serial` в LoRa TYPE_STATIC используется `dev_id` (TODO:
настоящий серийник — из пакета SUBDEV, п. 5.4).

### 5.2 Список маяков (`BLE_PKT_BEACONS`, Header `0x11`)

```c
typedef struct {                 // 4 байта = ble_beacon_t LoRa v4 п.4.7
    uint16_t ShortID;            // из рекламы маяка (п.4.1)
    int8_t   Rssi;               // измерен модулем-приёмником, дБм
    uint8_t  Battery;            // 0/1/2 (из рекламы маяка)
} ble_beacon_t;

typedef struct {
    uint8_t Header;              // 0x11
    uint8_t Count;               // ≤ 16 (BLE_BEACONS_MAX)
    ble_beacon_t Beacons[];      // Count записей
} ble_pkt_beacons_t;             // 2 + 4×Count
```

Раскладка записи совпадает с проводной в LoRa v4 (копия memcpy).

### 5.3 Список СИЗ (`BLE_PKT_PPE`, Header `0x21`)

```c
typedef struct {
    uint8_t  PpeType;            // тип СИЗ (п.4.2)
    uint16_t Serial;             // заводской идентификатор, LE
    uint8_t  Charge;             // 0/1/2
    int8_t   Rssi;               // дБм
    uint8_t  Flags;              // бит0 = надето/присутствует (Present)
} ble_ppe_wire_t;                // 6 байт

typedef struct {
    uint8_t Header;              // 0x21
    uint8_t Count;               // ≤ 8 (BLE_PPE_MAX = 8 позиций, LoRa v4 п.4.6)
    ble_ppe_wire_t Items[];
} ble_pkt_ppe_t;                 // 2 + 6×Count
```

Порядок записей = позиции комплекта: индекс записи k соответствует биту k
`PresenceMask`/`PPEEnabledMask` в LoRa v4 (стабильность порядка обеспечивает
модуль по Serial; при изменении состава комплекта сервер сверяется с
`TYPE_STATIC`).

### 5.4 Под-устройство расширенное (`BLE_PKT_SUBDEV`, Header `0x31`) — задел

То же, что legacy AVIS, ПЛЮС заводской серийник (для новой прошивки AVIS;
трекер принимает оба формата):

```c
typedef struct {
    uint8_t  Header;             // 0x31
    uint16_t SerialLo;           // заводской номер (младшая часть), LE
    uint16_t SerialHi;           // (старшая часть — задел 32 бит)
    uint8_t  dev_hw_ver;
    uint8_t  dev_fw_ver;
    uint8_t  charge;
    uint8_t  sensors_enabled:5;
    uint8_t  rfu:3;
    ble_sensor_data_t sensors[7];
} ble_pkt_subdev_t;              // шапка 9 байт, максимум 9 + 5×7 = 44 байта
```

### 5.5 Агрегат (`BLE_PKT_AGG`, Header `0xF1`) — предпочтительный вариант

«Всё одним пакетом» (решение автора): после `BlockMask` блоки идут **по
возрастанию битов**, внутренние Header-байты блоков BEACONS/PPE опускаются:

```c
typedef struct {
    uint8_t Header;              // 0xF1
    uint8_t BlockMask;           // бит0 GAS, бит1 BEACONS, бит2 PPE
    uint8_t Blocks[];
} ble_pkt_agg_t;
```

| Бит BlockMask | Блок | Содержимое |
|---------------|------|------------|
| 0 | GAS | `str_ble_data_set_t` ЦЕЛИКОМ (41 байт, неиспользованные слоты каналов — нули) |
| 1 | BEACONS | `Count + 4×Count` (без байта Header) |
| 2 | PPE | `Count + 6×Count` (без байта Header) |

## 6. Обработка на трекере

Разбор ответа `ADVMSDDATAGET` — `Ble_ParsePacket()` (`Ble_vector.c`,
Measure Task). Результаты раскладываются в два хранилища (`shared_types.h`,
экземпляры в `Vector_main.c`, вне `CONFIG_*` — LoRa v4 читает их при
`CONFIG_LORA` независимо от `CONFIG_BLE`):

- `Connected_device` (`SNS_Dev_Type`) — каналы/заряд/версии AVIS;
  невключённые каналы помечаются `channel = 0xFF`;
- `Ble_telemetry` (`BLE_TELEMETRY`) — `beacons[]`/`beacon_count`,
  `ppe[]`/`ppe_count`, `gas_online`, `gas_serial`, метки свежести `*_ms`
  (`GetTick()`).

**Свежесть (TTL):** потребитель (LoRa) считает данные действительными
`BLE_TELEMETRY_TTL_MS` = 5 минут (3 периода опроса + запас). Устарели —
блоки/секция в кадр не включаются (маска/счётчик остаются нулевыми).

Соответствие «BLE → LoRa v4»:

| Данные BLE | LoRa v4 |
|------------|---------|
| legacy GAS / SUBDEV: каналы | секция `SUB_TYPE_GAS`: `Sensors` (`StateErr` каналов), `Battery`; `TYPE_STATIC`: `sub_descr_t` (`SubID = 1`, `Cfg` = `SensorsEnabled` + `channel_cfg_t[]`) |
| legacy GAS / SUBDEV: Serial | `sub_descr_t.Serial` (legacy: `dev_id`, TODO) |
| BEACONS | контейнерный блок `BLEBeacons` (бит 8), байт-в-байт |
| PPE: Flags/Charge | контейнерный блок `PPE` (бит 7): `PresenceMask` + `Charge[]` |
| PPE: Type/Serial | `TYPE_STATIC`: `PPEEnabledMask` + `ppe_descr_t[]` |
| — | контейнерный `EventLog` (бит 9): события `0x20/0x21/0x22` по изменению маски СИЗ (пороги заряда считает сервер — LoRa v4, решение 3) |

## 7. Примеры кадров (hex)

### 7.1 Legacy AVIS, 2 канала (O₂ 20.9 %об.д. и канал 29 = 15.1)

```
02 01 03 07 50 03 44 D1 00 00 13 1D 97 00 00 10
```
**16 байт.** `02` — Header (тип 0, версия 2); dev_id 1; hw 3; fw 7; заряд
80 %; маска каналов `0x03`; канал 0: газ `0x44`=68 (O₂), концентрация
`0x00D1`=209, состояние 0, установки `0x13`; канал 1: газ `0x1D`=29,
концентрация `0x0097`=151, состояние 0, установки `0x10`.

### 7.2 Список из 2 маяков (BEACONS)

```
11 02 02 01 BA 02 07 00 AB 01
```
**10 байт.** `0x11` Header; Count 2; маяк 1: ShortID `0x0102`, RSSI −70
(`0xBA`), заряд 2 (норма); маяк 2: ShortID `0x0007`, RSSI −85 (`0xAB`),
заряд 1 (предупреждение).

### 7.3 Две единицы СИЗ (PPE)

```
21 02 00 01 01 02 C4 01 01 02 01 01 B5 01
```
**14 байт.** `0x21` Header; Count 2; СИЗ 0: каска (тип 0), Serial `0x0101`,
заряд 2, RSSI −60, надето (Flags `0x01`); СИЗ 1: привязь (тип 1), Serial
`0x0102`, заряд 1, RSSI −75, надета.

### 7.4 Агрегат (AGG: AVIS + 1 маяк + 1 СИЗ)

```
F1 07
02 01 03 07 50 03 44 D1 00 00 13 00 00 00 00 00  00×25            (GAS, 41 Б)
01 02 01 BA 02                                                        (BEACONS: Count 1)
01 00 01 01 02 C4 01                                                  (PPE: Count 1)
```
**55 байт** (2 + 41 + 5 + 7).

## 8. Бюджет размера (лимит 256 байт)

| Пакет | Максимум |
|-------|----------|
| legacy GAS | 41 |
| SUBDEV | 44 |
| BEACONS | 2 + 4×16 = 66 |
| PPE | 2 + 6×8 = 50 |
| AGG (всё вместе) | 2 + 41 + (1+4×16) + (1+6×8) = **157** |

Полный агрегат (16 маяков + 8 СИЗ + AVIS) — 157 байт, лимит 256 не
нарушается с большим запасом. По UART ответ приходит hex-ASCII (×2) —
буфер приёма модуля 520 байт.

## Принятые решения

1. **Legacy AVIS принимается как есть.** Пакет Avis v2 (6+5N) не меняется —
   существующий парк приборов работает с трекером без перепрошивки;
   тип 0/версия 2 в Header-байте не конфликтует с пакетами v1.
2. **Один пакет предпочтителен, но не обязателен.** AGG собирает всё вместе;
   отдельные пакеты BEACONS/PPE/GAS разбираются тем же диспетчером — модуль
   вправе отдавать данные как одним кадром, так и разными.
3. **Хранилище телеметрии вне CONFIG_*.** `Ble_telemetry`/`Connected_device`
   определены в `shared_types.h`/`Vector_main.c`, чтобы LoRa (CONFIG_LORA)
   читал их даже при выключенном CONFIG_BLE (данные просто устареют по TTL).
4. **Концентрации — pass-through.** Трекер не перемасштабирует концентрации
   AVIS (отправитель уже применил свою формулу); единицы описывает
   `Setting_channel` в `TYPE_STATIC` LoRa v4.
5. **RSSI добавляет приёмник.** В эфирных рекламах (BEACON_ADV/PPE_ADV)
   RSSI нет — его измеряет модуль трекера и кладёт в списки.
6. **Порядок позиций СИЗ = биты маски.** Индекс записи в пакете PPE
   соответствует биту `PresenceMask`/`PPEEnabledMask` LoRa v4.

## Остаётся уточнить

- **Скан/агрегация в прошивке MK01** — умеет ли модуль собирать списки
  реклам по UUID и отдавать их одним ответом `ADVMSDDATAGET` (протокол
  рассчитан на это; если модуль отдаёт по одному устройству за опрос — MCU
  копит списки сам в пределах TTL, структура пакетов не меняется).
- **Формат ответа `ADVMSDDATAGET`** — принято допущение v27: hex-ASCII
  начиная с 3-го байта ответа (как у `BLEADDR?`); подтвердить по
  документации модуля.
- **Общий UUID инфраструктуры** — значение назначается при монтаже
  (программируется в маяки/метки и в фильтр модуля трекера).
- **Бит «надето» у метки СИЗ** — источник признака (датчик ношения на метке
  или факт видимости); до появления датчика бит = видимость метки.
- **Серийник AVIS** — legacy-пакет его не несёт (`sub_descr_t.Serial` =
  `dev_id`, помечено TODO); полный серийник — с пакетом SUBDEV при обновлении
  прошивки AVIS.
- **Карта дискретности в `Setting_channel`** — биты 2..3 (предварительно
  0→1, 1→10, 2→100, 3→1000); сверить с Avis-Lora-protocol-v3/заголовками
  Avis (нужна только для мёртвой зоны O₂ 20.85..20.95 на трекере).
