# Протокол обмена MIRAX BLE v2

> **Статус:** рабочая спецификация (рев. 2 — правки по замечаниям автора:
> без Header-байта, заводские идентификаторы 1 байт, таблица без Serial,
> Slot/PpeType объединены, набор AT-команд управления модулем — предварительный).
> Заменяет `Mirax-Ble-protocol-v1.md` в части эфира и обмена MCU↔модуль
> (v1 остаётся в репозитории как история).
> LoRa здесь **не описывается** — только маппинг «данные BLE → блоки LoRa v4»
> (п. 7); сам LoRa — `Mirax-Lora-protocol-v4.md`.
> Код прошивки трекера под v2 **пока не правится** (v28 остаётся на v1) —
> документ опережает реализацию.

## 1. Общие положения

Протокол v2 описывает три уровня обмена комплекта **VECTOR**:

1. **Эфир (реклама)** — устройства комплекта (маяки, метки СИЗ, браслет,
   газоанализатор AVIS) вещают advertising-пакеты; полезная нагрузка — в
   manufacturer data. **MAC-адрес в payload НЕ передаётся** — он находится в
   PDU рекламы и читается приёмником автоматически;
2. **UART (MCU ↔ свой BLE-модуль MK01)** — AT-команды: передача таблицы
   MAC-фильтра модулю при каждой инициализации, чтение последних принятых
   данных **по MAC-адресу**, мост для внешнего конфигуратора;
3. **BLE конфигуратора** — внешний конфигуратор (приложение) подключается к
   модулю трекера и передаёт в MCU таблицу устройств комплекта.

**Главные отличия от v1:**

- фильтр эфира — **по MAC-адресам** из таблицы, а не по общему UUID
  инфраструктуры;
- в payload устройств **нет байта типа/версии (Header)** — что это за
  устройство, MCU определяет **по своей таблице MAC-адресов** (DevType) и по
  ней же выбирает парсер; контроль целостности — по длине payload;
- модуль **не агрегирует** списки (пакеты v1 BEACONS/PPE/AGG отменены): он
  хранит кэш «последняя реклама + RSSI + возраст» по каждому MAC из таблицы,
  а MCU читает кэш по MAC и **сам** собирает блоки LoRa v4.

**Основные принципы:**

- все многобайтные поля — **little-endian**;
- лимит одного пакета — **256 байт** (решение автора, сохраняется из v1);
- **заводские идентификаторы устройств — 1 байт** (Serial метки СИЗ, Serial
  браслета); пакет legacy AVIS принимается **как есть** — парк AVIS не
  перепрошивается;
- состав комплекта: **маяки 1..16**, **СИЗ ≤ 8** (может быть меньше; «не
  поймали — значит отсутствует»), **браслет ≤ 1**, **газоанализатор AVIS ≤ 1**;
  всего MAC-записей ≤ 26 (ёмкость таблицы — 32 с запасом);
- свежесть данных определяет **MCU** (TTL, п. 7.3), а не модуль: модуль хранит
  последний принятый пакет сколь угодно долго и сообщает его возраст;
- все устройства **могут подключаться** (соединение используется для сервиса/
  конфигурации — запись ShortID в маяк при монтаже и т.п.), но телеметрия
  ходит **только рекламой**; модуль трекера в рабочем режиме соединения с
  устройствами не устанавливает — только сканирует.

## 2. Состав и топология

```
 [ Маяк 1..16 ] ─┐
 [ СИЗ 1..8   ] ─┤  BLE-реклама (advertising)
 [ Браслет    ] ─┤  (MAC в PDU, manufacturer data — payload)
 [ AVIS       ] ─┘
        │
        ▼
 ┌──────────────────────┐      [ Конфигуратор ]  (внешнее приложение)
 │   BLE-модуль (MK01)  │◄─────── BLE GATT ───────  передача таблицы устройств
 │   - сканер/приёмник  │      (соединение)
 │   - MAC-фильтр       │
 │   - кэш: payload+    │
 │     RSSI+возраст     │
 │   - реклама (имя     │
 │     VEC…, для        │
 │     конфигуратора)   │
 └──────────┬───────────┘
            │ UART 115200 8N1 (AT-команды, п. 4)
            ▼
 ┌──────────────────────┐
 │   MCU (STM32U575)    │   трекер VECTOR
 │   - таблица MAC →    │   ← хранится в CONFIG на внешней flash,
 │     DevType+Param    │     при КАЖДОМ включении передаётся модулю (MACSET)
 │   - кэш данных       │   ← Ble_telemetry / Connected_device
 │   - LoRa v4 пакеты   │   ← формирование uplink (вне этого документа)
 └──────────┬───────────┘
            │ UART (LoRa-модуль S7678S)
            ▼
      [ Сервер LoRaWAN ]
```

| Устройство | Кол-во | DevType (п. 5) | Телеметрия (payload, п. 3) | Что нужно LoRa v4 |
|---|---|---|---|---|
| Маяк | 1..16 | 1 | ShortID + Battery, 3 байта | `BLEBeacons`: ShortID + Rssi + Battery |
| Метка СИЗ | 0..8 | 2 | PpeType + Serial + State, 3 байта | `PPE`: присутствие + заряд; `TYPE_STATIC`: Type + Serial |
| Браслет (пульсометр) | 0..1 | 3 | Serial + заряд % + пульс + SpO2 + Flags, 5 байт | секция `SUB_TYPE_PULSE`: заряд %, пульс, SpO2 (задел) |
| Газоанализатор AVIS | 0..1 | 4 | legacy `str_ble_data_set_t`, 6+5N ≤ 41 байт | секция `SUB_TYPE_GAS`: заряд, каналы (концентрация/StateErr/Setting) |

## 3. Эфир: реклама устройств

### 3.0 Общие правила

Каждое устройство вещает connectable-рекламу (ADV_IND); телеметрия — в
Manufacturer Specific Data. Раскладка AD-структуры (формат Bluetooth Core
Spec, не наша выдумка):

```
┌──────┬────────────┬─────────────────────┬────────────────────────────┐
│ Len  │ AD Type    │ CompanyID (2 байта) │ payload (наши данные, п.3.1+)│
│ 1 Б  │ = 0xFF     │ little-endian       │                            │
└──────┴────────────┴─────────────────────┴────────────────────────────┘
 Len = число байтов, следующих за Len (1 + 2 + длина payload)
```

**CompanyID** — обязательный по формату рекламы двухбайтовый код производителя,
которым Bluetooth SIG наделяет компании (например, у STMicroelectronics —
`0x0483`). Он ставится ПЕРЕД нашими данными и к логике протокола отношения не
имеет: у всех устройств комплекта значение одно, согласуется один раз при
производстве (предварительно — внутренний/тестовый `0xFFFF`, п. 11). Модуль-
сканер фильтрует эфир **только по MAC**, CompanyID вырезает и отдаёт MCU один
payload.

Прочие правила:

- **в payload нет ни MAC, ни байта типа/версии (Header)**: что это за
  устройство, MCU знает из таблицы MAC-адресов (DevType, п. 5) — по нему и
  выбирается парсер. Контроль — по длине payload: у каждого типа она фиксирована
  (маяк 3, СИЗ 3, браслет 5) либо вычислима (AVIS: 6+5N по маске каналов);
  длина не сошлась с DevType записи → пакет отбрасывается, счётчик ошибок
  (защита от перепутанных записей таблицы);
- устройства вещают **публичными (public) MAC-адресами**, назначаемыми при
  производстве; если понадобится random static — запись таблицы расширяется
  байтом типа адреса (п. 11);
- периоды рекламы (рекомендации, настраиваются при производстве/монтаже):
  маяк — 1000 мс, метка СИЗ — 1000 мс, браслет — 500 мс, AVIS — 300 мс (как в
  Avis `Ble_AdvPeriodms(300)`).

### 3.1 Маяк

```c
typedef struct {
    uint16_t ShortID;    // короткий ID (minor/instance), LE — зашит при монтаже
    uint8_t  Battery;    // 0 разряжен, 1 предупреждение, 2 норма
} ble_pkt_beacon_adv_t;  // 3 байта
```

`ShortID` трекер получает **от самого маяка по BLE** (из этого пакета) и
ретранслирует в LoRa `BLEBeacons` вместе с RSSI, измеренным модулем. Реестр
`ShortID → (координата/зона/этаж, MAC)` ведёт сервер; запись ShortID в маяк
при монтаже — через соединение конфигуратором (п. 11). Состав полей совпадает
с `ble_beacon_t` LoRa v4 п. 4.7 минус Rssi (его добавляет приёмник).

### 3.2 Метка СИЗ

```c
typedef struct {
    uint8_t  PpeType;    // тип СИЗ (приложение LoRa v4: 0 каска, 1 привязь, ...)
    uint8_t  Serial;     // заводской идентификатор единицы, 1 байт
    uint8_t  State;      // биты 0..1 = заряд (0/1/2), бит 7 = надето/присутствует,
                         // биты 2..6 — резерв (0)
} ble_pkt_ppe_adv_t;     // 3 байта
```

Присутствие СИЗ для LoRa определяется **двумя уровнями**: метка не поймана
(нет в кэше / устарела по TTL) → бита в `PresenceMask` нет вообще («отсут-
ствует»); поймана → бит выставляется по `State.7` (признак «надето» от датчика
ношения — задел; до его появления метка ставит бит 7 всегда, когда она на
человеке в зоне приёма, см. п. 11). Позиция бита (0..7) — порядковый номер
записи СИЗ в таблице MCU (п. 5), не из payload.

### 3.3 Браслет / пульсометр

```c
typedef struct {
    uint8_t  Serial;     // заводской идентификатор, 1 байт
    uint8_t  Battery;    // заряд браслета, % (0..100)
    uint8_t  HeartRate;  // пульс, уд/мин (0 = нет измерения)
    uint8_t  SpO2;       // сатурация, % (0 = нет измерения; задел)
    uint8_t  Flags;      // бит 0 = надет (задел, датчик ношения), биты 1..7 — 0
} ble_pkt_bracelet_adv_t;// 5 байт
```

Соответствие LoRa v4 `SUB_TYPE_PULSE`: `Battery` → блок Battery (%),
`HeartRate` → блок HeartRate, `SpO2` → блок SpO2 (опциональный бит SubMask —
включается, когда `SpO2 ≠ 0`). `Serial` → `sub_descr_t.Serial` в `TYPE_STATIC`
(старший байт u16 = 0).

### 3.4 Газоанализатор AVIS (legacy)

Существующая прошивка AVIS вещает `str_ble_data_set_t` (Avis `Ble_mk01.h`,
команда `ADVMSDDATASET` своего модуля) **без изменений** — байт-в-байт как в
v1 п. 5.1:

```c
typedef struct {                 // 5 байт, провод как sensor_data_t Avis
    uint8_t  Type_gas;           // код газа/канала (num_formula_gas)
    uint16_t Concentration;      // концентрация LE (единицы отправителя);
                                 // на проводе 2 байта — байт-в-байт
                                 // uint8_t Concentration[2] из Avis Ble_mk01.h
    uint8_t  State_channel;      // StateErr & 0x7F отправителя
    uint8_t  Setting_channel;    // DeviceSetting & (MEASURE_MASK|MEASURE_DISK)
} __attribute__((packed)) ble_sensor_data_t;

typedef struct {                 // как str_ble_data_set_t в Avis Ble_mk01.h
    uint8_t data_struct_ver;     // = 2 — часть формата Avis (НЕ идентификатор
                                 // протокола v2 — типа в payload у нас нет)
    uint8_t dev_id;              // идентификатор МОДЕЛИ отправителя (DIVICE_ID_BLE)
    uint8_t dev_hw_ver;
    uint8_t dev_fw_ver;
    uint8_t charge;              // заряд батареи отправителя, %
    uint8_t sensors_enabled:5;   // битовая маска включённых каналов (бит0 = канал0)
    uint8_t rfu:3;               // резерв
    ble_sensor_data_t sensors[7];// COUNT_CHAN_BLE = 7
} __attribute__((packed)) str_ble_data_set_t;
                                 // шапка 6 байт; передаётся
                                 // 6 + 5×popcount(sensors_enabled), макс. 41
```

MCU знает по таблице, что источник — AVIS, и читает структуру как есть;
первый байт `data_struct_ver` ничего не диспетчеризует. Концентрации —
**pass-through** (отправитель уже применил `Discreteness × conversion_factor_rf`),
трекер повторно не масштабирует. Серийный номер legacy-пакет не несёт: для
`sub_descr_t.Serial` в LoRa `TYPE_STATIC` используется `dev_id` (TODO — способ
передачи настоящего серийника AVIS будет определён отдельно).

## 4. UART-протокол MCU ↔ модуль MK01 (AT-команды)

**Транспорт:** USART 115200 8N1, обмен синхронный (порт `Ble_vector.c`:
команда завершается `0x0D`, 4 попытки, контроль `OK`/`ERROR`, серия из 3
ошибок → флаг ошибки BLE `ST_COMMON_BIT_ERR_BLE`).

> **Статус набора команд.** Информации по управлению BLE-модулем трекера с MCU
> пока нет (документации сканерского AT-набора MK01 не существует — прошивка
> модуля не реализована). Поэтому в протоколе **закреплены (заложены)** только:
> **(а)** передача таблицы MAC-фильтра модулю при каждой инициализации —
> `AT+MACSET` (п. 4.1) и **(б)** прозрачный мост для кадров конфигуратора
> (п. 4.4) вместе с самим протоколом конфигуратора (п. 6). Остальные команды
> (п. 4.2–4.3) — **предварительные (черновик)**, будут уточнены, когда появится
> информация по модулю; при этом **структуры кадров** (`msdget_resp_t`, таблица
> п. 5, кадры конфигуратора п. 6) остаются требованием независимо от того, как
> в итоге будут называться команды.

**Форматы ответов:**

- без данных: `OK` / `ERROR`;
- с данными (hex-вариант, как у `BLEADDR?` в Avis): `эхо(2 байта) + hex-ASCII
  двоичного кадра + "OK"` — hex удваивает объём, буфер приёма 520 байт;
- с данными (raw-вариант, только мост конфигуратора `CFGGET?`/`CFGSEND=` —
  п. 4.4): двоичные байты без hex-удвоения, чтобы большие кадры не раздувались.

**MAC-адрес в командах** — 12 hex-символов, старший байт первым (порядок
отображения, как в ответе `BLEADDR?`), регистр не важен: `AABBCCDDEEFF`.

### 4.0 Сводка команд

| Команда | Ответ | Назначение | Статус |
|---------|-------|------------|--------|
| `AT` | `OK` | проверка связи | база MK01 |
| `AT+MODINFO?` | hex(ModInfo) | информация о модуле | база MK01 |
| `AT+BLEADDR?` | hex(MAC[6]) | MAC своего модуля | база MK01 |
| `AT+ADVBLENAMESET=<имя>` | `OK` | имя модуля (`VEC` + `%04d%04d` серийника) | база MK01 |
| `AT+ADVSTART=0/1`, `AT+ADVPERIODMS=n`, `AT+ADVPOWER=n` | `OK` | своя реклама (видимость для конфигуратора) | база MK01 |
| `AT+SLEEP`, `AT+SYSTEMOFF`, `AT+DFU` | `OK` | сервис | база MK01 |
| `AT+MACSET=<N>,<mac1>,...,<macN>` | `OK` | **записать всю таблицу MAC-фильтра** (N=0 — очистить) | **закреплена** |
| `AT+CONNSTATE?` | hex(1 байт: 0/1) | есть ли подключение конфигуратора | **закреплена** (мост) |
| `AT+CFGGET?` | raw-кадр / пусто | взять кадр конфигуратора из очереди (п. 4.4) | **закреплена** (мост) |
| `AT+CFGSEND=<len>` + raw | `>` … `OK` | передать кадр конфигуратору (п. 4.4) | **закреплена** (мост) |
| `AT+SCANSTART=0/1` | `OK` | включить/выключить сканирование | черновик |
| `AT+SCANPARAM=<int_ms>,<win_ms>` | `OK` | параметры скана (дефолт в прошивке модуля) | черновик |
| `AT+MACADD=<mac>` / `AT+MACDEL=<mac>` | `OK` | добавить/удалить один MAC | черновик |
| `AT+MACGET?` | hex(кадр таблицы) | прочитать таблицу модуля (сверка после записи) | черновик |
| `AT+MSDGET=<mac>` | hex(кадр данных) | **прочитать кэш по MAC** (п. 4.3) | черновик |
| `AT+MSDCLR=<mac>` / `AT+MSDCLR` | `OK` | очистить кэш одного MAC / весь | черновик |

Требование к прошивке модуля: **одновременная работа сканера и рекламы**
(приём устройств комплекта + видимость для конфигуратора).

### 4.1 Таблица MAC-фильтра (запись при инициализации) — закреплена

Таблица модуля — только список MAC (DevType модулю не нужен — парсинг на MCU).
Ёмкость — **≥ 32 записи** (рабочий максимум комплекта 26: 16 маяков + 8 СИЗ +
браслет + AVIS).

```
AT+MACSET=<N>,<mac1>,<mac2>,...,<macN>\r        N = 0..32
```

- MCU передаёт команду **при каждой инициализации** (каждое включение
  трекера, п. 4.5) — таблица модуля энергонезависимой НЕ предполагается;
- полностью **замещает** прежнюю таблицу; `N=0` — очистить;
- кэш данных при `MACSET` **очищается целиком**; `MACADD` добавляет пустую
  запись; `MACDEL` удаляет запись вместе с её кэшем;
- модуль принимает рекламу (любые ADV-события) только от MAC из таблицы и
  складывает в кэш: payload manufacturer data (без CompanyID) + RSSI + метка
  времени; повторная реклама того же MAC **перезаписывает** кэш;
- дубликат MAC в списке — `ERROR`; MAC вне таблицы в `MSDGET`/`MACDEL` —
  `ERROR`.

Максимальная длина строки `MACSET` (32 записи): 13 + 32×12 + 31 + 1 ≈ 429
символов — буфер передачи 560 байт не превышается.

Ответ `MACGET?` (hex-кадр): `[Count u8][Count × MAC[6]]`.

### 4.2 Сканирование — черновик

```
AT+SCANSTART=1\r        — запуск сканера (после записи таблицы)
AT+SCANPARAM=<interval_ms>,<window_ms>\r   — опционально
```

Рекомендация: duty скана ≥ 50 % (например, interval 200 мс / window 100 мс) —
при периодах рекламы устройств 300..1000 мс каждый пакет принимается
устойчиво. Точные значения/ограничения — за прошивкой модуля.

### 4.3 Чтение данных по MAC — черновик (структура кадра закреплена)

```
AT+MSDGET=<mac>\r
```

Ответ — hex-кадр:

```c
typedef struct {
    uint8_t  Status;     // 0 = данных нет (MAC в таблице, но реклама не
                         //     принималась / кэш очищен),
                         // 1 = в кэше есть данные
    int8_t   Rssi;       // RSSI последней принятой рекламы, дБм
                         // (0x7F — нет значения)
    uint16_t AgeSec;     // возраст данных, секунд от последнего приёма;
                         // 0xFFFF — насыщение (>= ~18 ч); LE
    uint8_t  Len;        // длина Payload (0 при Status=0)
    uint8_t  Payload[];  // manufacturer data КАК ЕСТЬ (без CompanyID)
} msdget_resp_t;         // 5 + Len байт, максимум 5 + 41 = 46 (legacy AVIS)
```

Свежесть по `AgeSec` оценивает MCU (TTL, п. 7.3) — модуль данные по возрасту
не бракует и кэш сам не стирает (кроме `MSDCLR`/`MACSET`/`MACDEL`).
MAC отсутствует в таблице → `ERROR`.

Опрос штатно циклический: MCU проходит всю свою таблицу и делает `MSDGET` по
каждой записи (п. 4.6). Заделом возможна bulk-команда `AT+MSDGETALL?`
(последовательность кадров `msdget_resp_t` + MAC перед каждым) — в базовый
набор не входит, см. п. 11.

### 4.4 Мост конфигуратора (raw-канал) — закреплён

Модуль обеспечивает **прозрачный мост** между подключённым конфигуратором
(GATT-характеристики п. 6) и MCU; содержимое кадров модуль не интерпретирует.

**Входящее направление (конфигуратор → MCU):** каждое GATT-write = один кадр
(п. 6) целиком; модуль хранит очередь **≥ 8 кадров** (переполнение — теряется
старейший, счётчик отдаётся по запросу — задел). MCU забирает:

```
AT+CFGGET?\r
  → "+CFG:<len>\r\n" + <len raw-байтов> + "\r\nOK"    — есть кадр
  → "+CFG:0\r\nOK"                                   — очередь пуста
```

**Исходящее направление (MCU → конфигуратор):**

```
AT+CFGSEND=<len>\r
  → ">" \r\n            — модуль готов принять len байт
  → MCU шлёт len raw-байтов
  → "OK"                — отправлено notify (при необходимости модуль дробит
                          по MTU; приложение собирает кадр по п. 6)
  → "ERROR"             — конфигуратор не подключён / ошибка
```

Подключение конфигуратора MCU определяет опросом `AT+CONNSTATE?` (ответ —
hex 1 байт: 0/1); вариант «модуль сам шлёт URC / дёргает GPIO» — п. 11.

### 4.5 Инициализация (каждое включение трекера)

Порядок `Ble_Init()` — как в порте Avis, дополненный таблицей:

```
1. AT ×2                        — проверка связи
2. AT+ADVBLENAMESET=VEC%04d%04d — имя модуля (метка VECTOR + серийник)
3. AT+BLEADDR?                  — MAC своего модуля (лог/индикация)
4. AT+MACSET=<N>,...            — ВСЯ таблица из CONFIG внешней flash (п. 5)
5. AT+SCANSTART=1               — запуск сканера (черновик)
6. AT+ADVPERIODMS=300, AT+ADVPOWER=8, AT+ADVSTART=1
                                  — своя реклама: видимость для конфигуратора
```

При N=0 шаги 4–5 выполняются формально (пустая таблица) — трекер остаётся
видимым для конфигуратора, который и заполнит таблицу.

### 4.6 Штатный ритм обмена

| Таймер | Действия |
|--------|----------|
| 60 с (`TIMER_RTC_BLE_DATA_SET`) | полный опрос данных: `MSDGET` по каждой записи таблицы → разбор payload по DevType → кэш MCU (п. 7) |
| 1 с | `CONNSTATE?`; при `1` — вычитывать `CFGGET?` до пустой очереди, обрабатывать кадры конфигуратора (п. 6), отвечать `CFGSEND` |
| 30 с бездействия (`SLEEP`, как Avis) | по решению автора — `AT+SLEEP` до следующего цикла (поведение сканера во сне модуля — п. 11) |

Обработка ошибок — как в существующем порте: 4 попытки на команду, 3 серии
ошибок подряд → `ST_COMMON_BIT_ERR_BLE`.

## 5. Таблица устройств на MCU

MCU хранит **свою** таблицу «MAC → что за устройство» в CONFIG внешней flash
(`Config_save_read.c`, страница CONFIG 0x400000; структура — задел кода):

```c
#define BLE_MAC_TABLE_MAX   (32u)   // ёмкость (рабочий максимум 26)

typedef enum {
    DEV_TYPE_NONE     = 0,          // пустая запись
    DEV_TYPE_BEACON   = 1,          // маяк
    DEV_TYPE_PPE      = 2,          // метка СИЗ
    DEV_TYPE_BRACELET = 3,          // браслет (пульсометр)
    DEV_TYPE_GAS      = 4           // газоанализатор AVIS
} ble_dev_type_t;

typedef struct {
    uint8_t  Mac[6];    // MAC устройства, старший байт первым
    uint8_t  DevType;   // ble_dev_type_t — определяет ПАРСЕР payload (п. 3)
    uint8_t  Param;     // смысл ЗАВИСИТ ОТ DevType (Slot и PpeType объединены
                        // в один байт — они применяются к разным типам):
                        //   СИЗ     → PpeType (0 каска, 1 привязь, ...);
                        //   маяк    → Slot 0..15 (необязательный порядок в
                        //             списке BLEBeacons; 0 = порядок таблицы);
                        //   браслет/AVIS → 0 (не используется)
} __attribute__((packed)) ble_mac_entry_t;   // 8 байт
```

Правила:

- **DevType выбирает парсер** payload из `MSDGET`: 1 → маяк (3 байта),
  2 → метка СИЗ (3 байта), 3 → браслет (5 байт), 4 → legacy AVIS (6+5N).
  Контроль — по длине payload (п. 3.0): не сошлась → пакет отбрасывается,
  счётчик ошибок;
- **позиция СИЗ в масках LoRa** (бит `PresenceMask`/`PPEEnabledMask`, порядок
  `ppe_descr_t[]` в `TYPE_STATIC`) = **порядковый номер записи СИЗ в таблице**
  (k-я запись СИЗ = бит k). Таблица пишется конфигуратором атомарно (COMMIT,
  п. 6), порядок стабилен; отдельного поля Slot для СИЗ не нужно — байт
  `Param` у СИЗ несёт PpeType;
- **серийников в таблице нет**: заводские идентификаторы приходят из payload
  устройств (Serial метки СИЗ, Serial браслета, dev_id AVIS). `PpeType` для
  `TYPE_STATIC` — из `Param` (известен сразу) и сверяется с payload при приёме;
  `Serial` для `TYPE_STATIC` — из payload: до первого приёма устройства = 0
  (неизвестен), сервер уточнит после `TYPE_STATIC` со свежими данными;
- запись таблицы меняется только конфигуратором (п. 6); после изменения MCU
  сохраняет CONFIG и **немедленно** перезаписывает таблицу модуля (`MACSET`);
- фиксированные SubID LoRa v4: браслет = 1 (`SUB_TYPE_PULSE`), AVIS = 2
  (`SUB_TYPE_GAS`) — как в примере v4 п. 8.2.

## 6. Внешний конфигуратор (BLE) — передача таблицы

Конфигуратор (приложение на телефоне/планшете) подключается к модулю трекера
по имени рекламы `VEC%04d%04d` и обменивается с MCU кадрами через прозрачный
мост (п. 4.4). Модуль кадр не понимает — разбирает MCU. Протокол закреплён;
управление трекером по BLE с МК сверх передачи таблицы пока не планируется —
ждём вводных (п. 11).

**GATT (значения предварительные, п. 11):** сервис `0xFFE0`; характеристика
`0xFFE1` (Write / Write w/o response) — приложение → MCU; `0xFFE2` (Notify) —
MCU → приложение. Один GATT-write = один кадр.

**Кадр:**

```
[0xA5][CMD u8][LEN u8][DATA (LEN байт)][CRC16 LE]
```

CRC16-CCITT (полином 0x1021, init 0xFFFF) по байтам CMD..DATA — тот же
вариант, что используется в проекте (`LOG_PTR`).

| CMD | Имя | DATA | Ответ MCU |
|-----|-----|------|-----------|
| `0x01` | TABLE_CLEAR | — | ACK |
| `0x02` | ENTRY_ADD | запись 8 байт: `MAC[6] + DevType + Param` (как `ble_mac_entry_t`, п. 5) | ACK |
| `0x03` | ENTRY_DEL | `MAC[6]` | ACK |
| `0x04` | COMMIT | — | ACK + действия (см. ниже) |
| `0x05` | TABLE_READ | — | серия `0x06` + `0x07` |
| `0x06` | ENTRY_INFO | как ENTRY_ADD | — (ответ) |
| `0x07` | TABLE_END | — | — (конец ответа TABLE_READ) |
| `0x81` | ACK | `EchoCmd u8 + Status u8` | — |

Коды Status в ACK: `0` OK; `1` ошибка CRC; `2` переполнение таблицы;
`3` ошибка записи flash; `4` дубликат MAC; `5` нет такой записи; `6` неверный
параметр. Прочие — резерв.

**Сценарий записи таблицы:**

```
конфигуратор: TABLE_CLEAR → ENTRY_ADD × N → COMMIT
MCU:          кадры копятся во временной копии таблицы (RAM);
              COMMIT → валидация → запись CONFIG (внешняя flash) →
              AT+MACSET=<N>,... модулю → ACK(0x04, 0)
```

До COMMIT изменения не действуют (ни flash, ни модуль) — сессия атомарна;
обрыв связи оставляет прежнюю таблицу. Контроль — `TABLE_READ` после COMMIT.
Состав комплекта (какие MAC, типы, PpeType) знает монтажная организация;
ShortID маяков и Serial устройств в таблицу НЕ входят — они приходят из эфира
(п. 3.1–3.3).

## 7. Кэш данных MCU и маппинг в LoRa v4

### 7.1 Разбор ответа MSDGET

`Ble_ParsePacket()` разбирает `Payload` кадра `msdget_resp_t` по DevType
записи таблицы (контроль — по длине, п. 3.0) и обновляет хранилища (уже
определены в `shared_types.h`, вне `CONFIG_*` — LoRa читает их при
`CONFIG_LORA` независимо от `CONFIG_BLE`):

- `Ble_telemetry` (`BLE_TELEMETRY`): `beacons[]`/`beacon_count` (маяки),
  `ppe[]`/`ppe_count` (СИЗ в порядке записей таблицы = порядок битов маски),
  `gas_online`/`gas_serial`; метки свежести `*_ms` (`GetTick()`) — по каждому
  устройству;
- `Connected_device` (`SNS_Dev_Type`): каналы/заряд/версии AVIS; невключённые
  каналы — `channel = 0xFF`.

Добавление v2 (задел кода): в кэше каждому MAC нужна индивидуальная метка
`last_seen_ms` (сейчас метки общие на группу) — «не поймали» определяется
per-MAC.

### 7.2 Соответствие «BLE → LoRa v4»

| Источник | Из payload | Из ответа MSDGET | Из таблицы MCU | Блоки LoRa v4 |
|----------|-----------|------------------|----------------|----------------|
| Маяк (DevType 1) | ShortID, Battery | Rssi, AgeSec | Param/порядок → порядок списка | `BLEBeacons` (бит 8): `ble_beacon_t` байт-в-байт |
| Метка СИЗ (2) | PpeType, Serial (u8), State.7 (надето), State.0..1 (заряд) | AgeSec | № записи среди СИЗ → бит маски; Param → PpeType (до приёма) | `PPE` (бит 7): `PresenceMask` + `Charge[]`; `TYPE_STATIC`: `PPEEnabledMask` + `ppe_descr_t{Type, Serial}` (Serial u16: старший байт 0) |
| Браслет (3) | Serial (u8), Battery %, HeartRate, SpO2 | AgeSec | SubID = 1 (фикс.) | секция `SUB_TYPE_PULSE`: Battery / HeartRate / SpO2; `TYPE_STATIC`: `sub_descr_t.Serial` |
| AVIS (4) | charge, каналы (Type_gas/Concentration/State_channel/Setting_channel), версии, dev_id | AgeSec | SubID = 2 (фикс.) | секция `SUB_TYPE_GAS`: Battery + Sensors (`StateErr`); `TYPE_STATIC`: `sub_descr_t` (Serial = dev_id, TODO) + `channel_cfg_t[]` |

Сборка списков для LoRa — на MCU: `BLEBeacons.Count` и биты `PresenceMask`
формируются из **свежих** записей кэша (п. 7.3); контейнерный `EventLog`
(события `0x20/0x21/0x22` по маске СИЗ) — как в v1 п. 6, без изменений.

### 7.3 Свежесть (TTL) и «отсутствие»

Данные MAC считаются действительными `BLE_TELEMETRY_TTL_MS` = **5 минут**
(3 периода опроса 60 с + запас); критерий — минимум из возраста по
`AgeSec` ответа и метки `last_seen_ms` кэша. Устарело / `Status = 0`:

- **СИЗ** → бит позиции в `PresenceMask` = 0 («отсутствует» — ровно то, что
  ждёт LoRa v4: не поймали — нету);
- **маяк** → не включается в список `BLEBeacons`;
- **браслет / AVIS** → секция под-устройства в кадр не включается
  (`SubCount` уменьшается); `TYPE_STATIC` состав комплекта описывает всегда
  (из таблицы MCU), независимо от приёма.

## 8. Бюджет размера (лимит 256 байт)

| Пакет/строка | Максимум |
|-------|----------|
| payload маяка (эфир) | 3 |
| payload метки СИЗ (эфир) | 3 |
| payload браслета (эфир) | 5 |
| legacy AVIS (эфир) | 41 (6 + 5×7) |
| кадр `msdget_resp_t` | 46 (5 + 41) → hex-ответ ≤ 2 + 92 + 2 = 96 байт UART |
| строка `MACSET` (32 записи) | ≈ 429 байт UART (< буфера 560) |
| кадр конфигуратора ENTRY_ADD | 13 (8 DATA) |
| таблица MCU в CONFIG | 32 × 8 = 256 байт |
| кэш всех устройств на MCU | 26 × 46 ≈ 1.2 КБ RAM (задел кода) |

AD-структура маяка/СИЗ — 7 байт, браслета — 9: влезает в legacy advertising
31 байт. Legacy AVIS с полным набором каналов — до 2 + 2 + 41 = 45 байт AD:
требуется extended advertising либо scan response на стороне прибора/модуля
(существующий MK01 как-то передаёт `ADVMSDDATASET` больше 26 байт payload —
механизм уточнить, п. 11).

## 9. Примеры (hex)

### 9.1 Manufacturer data в эфире (AD-структура `[Len][FF][CID][payload]`)

| Устройство | Байты AD | Разбор payload |
|---|---|---|
| Маяк ShortID 0x0207, заряд норма | `06 FF FF FF 07 02 02` | ShortID `07 02` = 0x0207 (LE); Battery 2 |
| СИЗ каска, Serial 0x11, надета, заряд норма | `06 FF FF FF 00 11 82` | PpeType 0 (каска); Serial 0x11; State `0x82` = бит7 (надето) + заряд 2 |
| Браслет Serial 0x21, 90 %, пульс 78 | `08 FF FF FF 21 5A 4E 00 00` | Serial 0x21; Battery 90; HR 78; SpO2 0 (нет); Flags 0 |
| AVIS 2 канала (O₂ 20.9 %об.д., канал 29 = 15.1) | `13 FF FF FF 02 01 03 07 50 03 44 D1 00 00 13 1D 97 00 00 10` | `02` — data_struct_ver (формат Avis); dev_id 1; hw 3; fw 7; заряд 80 %; маска каналов `0x03`; канал 0: газ `0x44`=68 (O₂), `0x00D1`=209, состояние 0, установки `0x13`; канал 1: газ `0x1D`=29, `0x0097`=151, состояние 0, установки `0x10` |

### 9.2 Запись таблицы модулю (маяк + СИЗ + AVIS)

```
→ AT+MACSET=3,112233445566,AABBCCDDEEFF,010203040506\r
← OK
→ AT+SCANSTART=1\r
← OK
→ AT+MACGET?\r
← \r\n + "03112233445566AABBCCDDEEFF010203040506" + OK
```

### 9.3 Чтение данных по MAC

Маяк принят 3 с назад, RSSI −60 дБм:

```
→ AT+MSDGET=112233445566\r
← \r\n + "01C4030003070202" + OK
   кадр: Status 1; Rssi 0xC4 = −60; AgeSec 0x0003; Len 3; Payload 07 02 02
   (по таблице MAC — маяк: ShortID 0x0207, Battery 2)
```

СИЗ не принят ни разу:

```
→ AT+MSDGET=AABBCCDDEEFF\r
← \r\n + "007FFFFF00" + OK
   кадр: Status 0; Rssi 0x7F (нет); AgeSec 0xFFFF; Len 0
```

### 9.4 Сессия конфигуратора (один кадр в GATT-write)

Добавить СИЗ: MAC `11:22:33:44:55:66`, DevType 2, Param = PpeType 0 (каска),
затем COMMIT:

```
ENTRY_ADD: A5 02 08 11 22 33 44 55 66 02 00 EB 9D
           │  │  │  └───────MAC──────┘ │  │  └CRC (LE)
           │  │  └ LEN=8               │  └ Param: PpeType 0 (каска)
           │  └ CMD=ENTRY_ADD          └ DevType=2 (СИЗ)
           └ маркер
COMMIT:    A5 04 00 CB D1
ACK MCU:   A5 81 02 04 00 E8 8D        — EchoCmd 0x04, Status 0 (OK)
```

После ACK MCU уже сохранил CONFIG и выполнил `AT+MACSET` новой таблицей.

## Принятые решения

1. **Фильтр по MAC вместо UUID** (вводные v2): MAC берётся из PDU рекламы
   автоматически, в payload не дублируется; фильтр — таблица модуля, которую
   MCU передаёт `MACSET` при каждом включении.
2. **Модуль не агрегирует.** Пакеты v1 BEACONS/PPE/AGG отменены: модуль хранит
   кэш «последний payload + RSSI + возраст» per-MAC; списки для LoRa собирает
   MCU по ответам `MSDGET`.
3. **В payload нет Header-байта** (тип/версия v1 отменены): устройство
   определяется **только по таблице MAC** (DevType → парсер); контроль — по
   длине payload. Первый байт legacy AVIS (`data_struct_ver`) — часть формата
   Avis, а не идентификатор протокола.
4. **Заводские идентификаторы — 1 байт** (Serial метки СИЗ, Serial браслета);
   в LoRa-полях u16 (`ppe_descr_t.Serial`, `sub_descr_t.Serial`) старший байт = 0.
5. **Таблица MCU — 8 байт на запись**: `MAC[6] + DevType + Param`; Slot и
   PpeType **объединены** в `Param` (применяются к разным DevType: маяк →
   Slot, СИЗ → PpeType). **Серийников в таблице нет** — идентификаторы
   приходят из payload устройств. Позиция СИЗ в масках LoRa = порядковый номер
   записи СИЗ в таблице.
6. **AT-набор управления модулем — предварительный**: информации по управлению
   BLE трекера с MCU пока нет; закреплены только `MACSET` (передача фильтров
   модулю при каждой инициализации) и мост конфигуратора — остальные команды
   ждём/уточняем. Структуры кадров при этом зафиксированы.
7. **Legacy AVIS принимается как есть** (6+5N) — парк не перепрошивается;
   `Concentration` в C-представлении — `uint16_t` (провод не меняется:
   2 байта LE, байт-в-байт `uint8_t[2]` из Avis); серийник для `TYPE_STATIC` —
   `dev_id` (TODO). Пакет SUBDEV из v1 — отменён.
8. **Конфигуратор** передаёт таблицу через BLE-мост модуля кадрами
   `[0xA5][CMD][LEN][DATA][CRC16]`; сессия атомарна (COMMIT → CONFIG flash →
   `MACSET`); хранение таблицы — CONFIG внешней flash.
9. **Все устройства connectable** (сервис/конфигурация — запись ShortID в маяк
   и т.п.), но телеметрия — только реклама; модуль трекера в рабочем режиме не
   подключается ни к кому, кроме конфигуратора (и только он — к трекеру).
10. **Присутствие СИЗ — двухуровневое**: нет свежих данных → бита маски нет
   («отсутствует»); есть → бит по `State.7`. Пороги заряда — на сервере
   (решение 3 LoRa v4).
11. **Свежесть — на MCU** (TTL 5 мин): модуль кэш по времени не чистит, отдаёт
   `AgeSec`.
12. **Мост конфигуратора — raw-двоичный** (`CFGGET?`/`CFGSEND=` с prompt `>`),
   без hex-удвоения: кадры таблицы не раздувают буферы UART.

## Остаётся уточнить

- **Управление BLE-модулем с MCU — ждём информацию**: окончательный AT-набор
  сканера (п. 4.2–4.3 — черновик); ёмкость таблицы/кэша модуля (требуем ≥ 32
  записи и ≥ 8 кадров очереди конфигуратора); одновременный скан + реклама;
  параметры скана; поведение `AT+SLEEP` при активном сканере; bulk-чтение
  `MSDGETALL?` (вводить или нет).
- **CompanyID manufacturer data** — предварительно `0xFFFF` (внутренний);
  нужен ли зарегистрированный Bluetooth SIG идентификатор компании.
- **Реклама AVIS > 31 байта** — как существующий MK01 передаёт длинный
  `ADVMSDDATASET` (extended advertising / scan response / собственный формат);
  для сканерской прошивки — какой тип ADV-событий принимать (ADV_IND/
  ADV_NONCONN_IND/ADV_EXT_IND).
- **GATT конфигуратора**: UUID сервиса/характеристик (предварительно
  0xFFE0/E1/E2), безопасность (pairing/bonding, шифрование канала записи
  таблицы), MTU/long-write.
- **Сигнал подключения конфигуратора**: опрос `CONNSTATE?` (принято) либо
  URC/GPIO от модуля (быстрее, требует линии).
- **Тип адреса**: устройства с public MAC (принято); при random static —
  расширение записи таблицы байтом AddrType (и в `MACSET`, и в конфигураторе).
- **Запись ShortID в маяк и Serial в метку/браслет при монтаже** — процедура
  конфигуратора через соединение с устройством (отдельный документ/раздел).
- **Serial браслета в payload** — добавлен как следствие решения 5 (серийников
  в таблице MCU нет, а `sub_descr_t.Serial` в LoRa заполнять надо); если
  серийник браслета не нужен — поле убрать.
- **Настоящий серийник AVIS** — legacy несёт только `dev_id`; способ передачи
  (обновление прошивки AVIS / запись на производстве) — TBD (пакет SUBDEV
  отменён решением 7).
- **Бит «надето» метки СИЗ и Flags браслета** — источник (датчик ношения);
  до его появления бит = видимость устройства.
- **Сон/энергосбережение** сканера между опросами (ритм 60 с) — стратегия
  прошивки модуля.
- **SpO2 браслета** — реальные значения, когда датчик появится (сейчас 0 =
  нет данных, бит SubMask в LoRa не включается).
