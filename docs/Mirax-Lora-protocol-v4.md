# Протокол обмена MIRAX LoRaWAN v4

## 1. Общие положения

Протокол v4 (**MIRAX**) развивает AVIS v3 (`Avis-Lora-protocol-v3.md`) от модели
«один прибор одного типа» к модели **носимого комплекта**: один LoRa-узел —
**центральное устройство (трекер)** — агрегирует и передаёт данные нескольких
под-устройств (пульсометр, газоанализатор AVIS) и собственную телеметрию
(координата, окружающая среда, положение, активность, наличие и заряд СИЗ,
BLE-маяки).

**Основные цели версии 4:**
- адресация **под-устройств** внутри одного LoRa-узла (один DevAddr на комплект);
- перенос GPS и радио на трекер — единая опорная координата и время для всего комплекта;
- новые величины носимого контроля: пульс, положение/падение/удар, активность,
  окружающая среда (качество воздуха, температура, влажность, давление, высота),
  наличие и заряд СИЗ, видимые BLE-маяки;
- **сосуществование с v3**: газоанализаторы AVIS v3 остаются в эфире без изменений,
  сервер различает раскладки по полю версии в `Header` (п. 2);
- сохранение всех механизмов восстановления данных v3 (события, прореженная история,
  квитирование конфигурации, синхронизация RTC) — они переиспользуются как есть.

Как и в v3, после Join штатная передача идёт в ручном модемном режиме (`no_cycle`),
периоды динамические. По умолчанию штатный период — **60 с**, аварийный — **30 с**.

Все многобайтовые поля передаются в порядке **little-endian**.

## 2. Типы пакетов и диспетчеризация версий

Поле `Header` совпадает по раскладке с v3:

| Биты | Назначение |
|------|------------|
| 7..6 | Тип пакета |
| 5..4 | зарезервировано |
| 3..0 | Версия структуры |

**Типы пакетов** (как в v3): `0x00` `TYPE_DYNAMIC`, `0x40` `TYPE_ACK`,
`0x80` `TYPE_STATIC`, `0xC0` `TYPE_TURN_OFF`.

**Версия протокола:** `Version = 4`.

Сервер читает **nibble версии первым** и выбирает раскладку:
`Version = 3` → парсер AVIS v3; `Version = 4` → парсер MIRAX v4. Парк v3-приборов
работает параллельно и этой спецификацией не затрагивается. Пространство `FieldMask`
в v4 определяется заново — дефицит свободных битов v3 на v4 не распространяется.

## 3. Общая структура пакета (Uplink)

Пакет v4 состоит из **контейнерной части** (телеметрия трекера) и секций
**под-устройств**.

```c
typedef struct {
    uint8_t  Header;         // тип + версия = 4
    uint16_t ContainerMask;  // состав контейнерной части (блоки трекера)
    uint8_t  Payload[];      // контейнерные блоки, затем SubCount и секции под-устройств
} __attribute__((packed)) mirax_packet_t;
```

Структура Payload:

```
[ контейнерные блоки по возрастанию битов ContainerMask ]
SubCount (uint8)                      — число секций под-устройств в кадре
repeat SubCount:
    SubID    (uint8)                  — локальный индекс под-устройства (маппинг — в TYPE_STATIC)
    SubMask  (uint8)                  — состав секции (блоки этого под-устройства)
    [ блоки под-устройства по возрастанию битов SubMask ]
```

`SubID` — локальный индекс устройства в пределах комплекта; соответствие
«SubID → тип, заводской серийник» задаётся один раз в `TYPE_STATIC` (п. 6). По эфиру
в каждом `TYPE_DYNAMIC` ходит только 1-байтовый `SubID`.

`SubCount = 0` допустим — кадр несёт только контейнерную телеметрию трекера.

### 3.1 ContainerMask (uint16)

| Бит | Блок | Описание | Размер |
|-----|------|----------|--------|
| 0 | Battery | Заряд трекера | 1 |
| 1 | GPS | Полная координата трекера | 8 |
| 2 | GPSTrack | Текущий трек с прошлой отправки (относительно) | 1+2N |
| 3 | TimeRef | Опора абсолютного времени кадра | 4 |
| 4 | DeviceStatus | Статус комплекта (`ControlLora16`) | 2 |
| 5 | Environment | Качество воздуха / температура / влажность / давление / высота | 9 |
| 6 | Motion | Положение, падение, удар, активность | 2 |
| 7 | PPE | Наличие и заряд СИЗ (до 8) | 1+K |
| 8 | BLEBeacons | Видимые BLE-маяки | 1+4K |
| 9 | EventLog | Журнал событий комплекта за время потери связи | перем. |
| 10 | GPSHistory | История GPS за время потери связи | 6+2N |
| 11 | ConfigAck | Версия применённой конфигурации (`uint8 AppliedRev`, v3 п. 4.10) | 1 |
| 12 | MsgAck | Квитирование доставки текстового сообщения (`uint8 MsgSeq`, п. 7.1) | 1 |
| 13–15 | Reserved | Зарезервировано | — |

Правила для GPS/GPSTrack/GPSHistory/EventLog и их опорных координат — **полностью
как в v3** (пп. 3, 4.4–4.9): блок `GPS` обязателен при наличии `GPSTrack`, `EventLog`
или `GPSHistory` и служит опорой (новейшая точка для `GPSTrack`, старейшая — для
исторических блоков); `GPSTrack` и исторические блоки в одном кадре не сочетаются;
`TimeRef` обязателен при наличии `EventLog`/`GPSHistory`. Отличие v4: владелец
координаты — трекер, и опора общая для событий всех под-устройств (включая
газоанализатор, у которого в v4 собственного GPS нет).

`Payload` формируется строго по возрастанию битов — указателей смещений нет.

## 4. Контейнерные блоки (телеметрия трекера)

### 4.1 Battery (бит 0)

```c
typedef struct { uint8_t Charge; } battery_block_t;   // заряд трекера, %
```
**Размер:** 1 байт.

### 4.2 DeviceStatus — `ControlLora16` (бит 4)

Статус комплекта расширен до **16 бит** (в v3 был 8-битным и исчерпан).

```c
typedef struct { uint16_t ControlLora; } status16_block_t;
```
**Размер:** 2 байта.

```c
enum STATUS_LORA_V4 {
    ST_LORA_BIT_GROUP       = 0,  // Авария от сервера «Группа»
    ST_LORA_BIT_BACK_GROUP  = 1,  // Авария от сервера «Группа назад»
    ST_LORA_BIT_SOS_GROUP   = 2,  // Флаг от сервера «Группа SOS»
    ST_LORA_BIT_ACTIVE_MODE = 3,  // 1 — частый период, 0 — штатный
    ST_LORA_BIT_ZONE        = 4,  // Флаг от сервера «Зона»
    ST_LORA_BIT_SOS         = 5,  // Сигнал SOS от устройства (сервер не сбрасывает)
    ST_LORA_BIT_ECHO        = 6,  // Эхо-бит, сервер зеркалит без изменений
    ST_LORA_BIT_CURRENT_C   = 7,  // 1 — Класс C, 0 — Класс A
    ST_LORA_BIT_EVACUATION  = 8,  // Сигнал «Всем на выход» (эвакуация), RW от сервера
    // биты 9..15 — зарезервировано
};
```

Биты 0–7 совпадают с v3. Бит 8 `EVACUATION` — команда эвакуации («Всем на выход» из
каталога PTS), задаётся сервером, подтверждается наблюдением в ответных uplink.
Защита бита `SOS` от перезаписи сервером сохраняется.

### 4.3 GPS (бит 1), GPSTrack (бит 2), TimeRef (бит 3), GPSHistory (бит 10)

Структуры и семантика **идентичны v3**:
- `GPS` — `int32 Latitude, int32 Longitude` (градусы ×1e7), `(0,0)` = нет фикса (v3 п. 4.4);
- `GPSTrack` — `Count + point_delta_t[]` (`int8` метры, цепочка назад от новейшей точки, v3 п. 4.5–4.6);
- `TimeRef` — `uint32 UnixTime` старейшей точки кадра (v3 п. 4.7);
- `GPSHistory` — `Count + Dt0 + Step + Scale + history_point_t[]` (v3 п. 4.9).

### 4.4 Environment (бит 5) — окружающая среда

Фиксированный блок (без `FieldMask`), 9 байт.

```c
typedef struct {
    uint16_t AirQualityIndex;  // индекс качества воздуха (0..65535)
    int16_t  Temperature;      // °C × 10   (−3276.8 … +3276.7)
    uint8_t  Humidity;         // %         (0..100)
    uint16_t Pressure;         // гПа × 10  (напр. 1013.2 → 10132)
    int16_t  Altitude;         // метры, барометрическая высота (−32768 … +32767)
} environment_block_t;
```
**Размер:** 9 байт.

Высота — барометрическая (из датчика давления трекера), самостоятельная величина со
своими порогами, не выводится сервером из `Pressure`.

### 4.5 Motion (бит 6) — положение и активность

```c
typedef struct {
    uint8_t StatusBits;     // биты состояния (см. ниже)
    uint8_t ActivityLevel;  // уровень активности, 0..255
} motion_block_t;
```
**Размер:** 2 байта.

```c
enum MOTION_BITS {
    MOTION_POSTURE_MASK = 0x03,  // биты 0–1: поза
                                 //   0 = неизвестно, 1 = вертикальное, 2 = горизонтальное
    MOTION_BIT_FALL     = 2,     // зафиксировано падение
    MOTION_BIT_IMPACT   = 3,     // зафиксирован удар (факт события)
    MOTION_BIT_INACTIVE = 4,     // прибор неподвижен (отсутствие активности)
    // биты 5–7 — зарезервировано
};
```

`ActivityLevel` — числовой уровень активности; порог события «Отсутствие активности»
(в пакетах) считает сервер по последовательности значений. «Горизонтальное/вертикальное
положение», «падение», «удар» из каталога PTS — через `StatusBits`.

### 4.6 PPE (бит 7) — наличие и заряд СИЗ

До **8** единиц СИЗ. Соответствие «бит → тип и серийник единицы» — в `TYPE_STATIC` (п. 6).

```c
typedef struct {
    uint8_t PresenceMask;   // бит i = СИЗ i надето/присутствует
    uint8_t Charge[];       // заряд по каждой присутствующей единице, в порядке битов
} ppe_block_t;
```
**Размер:** 1 + `popcount(PresenceMask)` байт.

```c
enum PPE_CHARGE_STATE {   // значение байта Charge[k]
    PPE_CHARGE_LOW     = 0,  // разряжен
    PPE_CHARGE_WARNING = 1,  // предупреждение
    PPE_CHARGE_OK      = 2,  // в норме
    // 3..255 — зарезервировано
};
```

Массив `Charge[]` содержит по одному байту на **установленный** бит `PresenceMask`, в
порядке возрастания номеров бит. Наличие СИЗ (`СИЗ не надеты`/`в норме` из PTS) — из
маски; заряд (`зарядка СИЗ`) — из массива.

### 4.7 BLEBeacons (бит 8) — видимые BLE-маяки

Маяки — наше оборудование, программируемое при монтаже: вещают общий `UUID`
инфраструктуры и 2-байтовый короткий идентификатор (`minor`/`instance`), а также
состояние своего заряда. Трекер фильтрует эфир **по нашему `UUID`** (чужой BLE —
телефоны, гарнитуры — игнорирует) и репортит только инфраструктурные маяки.

```c
typedef struct {
    uint8_t     Count;        // число маяков в блоке
    ble_beacon_t Beacons[];
} blebeacons_block_t;

typedef struct {
    uint16_t ShortID;   // короткий ID из advertisement (minor/instance)
    int8_t   Rssi;      // уровень сигнала, дБм
    uint8_t  Battery;   // состояние заряда маяка: 0 разряжен, 1 предупреждение, 2 норма
} ble_beacon_t;         // 4 байта
```
**Размер:** 1 + 4×`Count` байт.

Маппинг `ShortID → (координата/зона/этаж, MAC)` сервер держит в реестре маяков,
заполняемом при вводе маяка в эксплуатацию. Раздачи идентификаторов на трекеры нет —
короткий ID зашит в сам маяк, трекер его только ретранслирует.

### 4.8 EventLog (бит 9) — журнал событий комплекта

Приоритетный канал восстановления данных трекера за время потери связи. В отличие от
газового `EventLog` (п. 5.3, канально-концентрационный), контейнерный журнал
**типизирован**: каждая запись — изменение состояния одной отслеживаемой величины или
дискретное событие (падение, удар, SOS, снятие СИЗ, пороги среды/пульса/высоты).

```c
typedef struct {
    uint8_t Count;                 // число событий
    container_event_t Events[];    // фиксированной длины, 10 байт каждое
} container_eventlog_block_t;

typedef struct {
    uint16_t Dt;         // секунд ВПЕРЁД от TimeRef (0..65535)
    int16_t  Dx;         // смещение широты от опорной координаты, м (0x8000 — нет фикса)
    int16_t  Dy;         // смещение долготы от опорной координаты, м (0x8000 — нет фикса)
    uint8_t  EventType;  // тип события (см. таблицу)
    uint8_t  Severity;   // 0 = инфо, 1 = предупреждение, 2 = критическое
    int16_t  Value;      // значение величины в момент события (0x8000 — неприменимо)
} container_event_t;     // 10 байт
```
**Размер:** 1 + 10×`Count` байт.

Опора времени (`TimeRef`), опорная координата (`GPS`), признак отсутствия фикса
(`Dx=Dy=0x8000`) и поведение при полном отсутствии опоры — **как в v3 п. 4.7–4.8**.
Записи упорядочены хронологически; событие фиксируется и на взведение, и на снятие
состояния.

Тип источника не кодируется отдельным полем: `EventType` однозначно определяет
измеряемую величину (и, следовательно, источник). `Value` масштабируется в тех же
единицах, что и соответствующая величина контейнерного блока (температура — ×10 и т.д.);
для бинарных событий (падение/удар/SOS/СИЗ) `Value = 0x8000`.

| `EventType` | Событие | `Value` |
|-------------|---------|---------|
| 0x01 | Качество воздуха (порог) | индекс |
| 0x02 | Влажность (порог) | % |
| 0x03 | Температура (порог) | °C ×10 |
| 0x04 | Пульс (порог) | уд/мин |
| 0x05 | Высота (порог) | м |
| 0x10 | Отсутствие активности | 0x8000 |
| 0x11 | Горизонтальное положение | 0x8000 |
| 0x12 | Вертикальное положение | 0x8000 |
| 0x13 | Зафиксировано падение | 0x8000 |
| 0x14 | Зафиксирован удар | 0x8000 |
| 0x15 | Сигнал SOS | 0x8000 |
| 0x20 | СИЗ не надеты | маска снятых |
| 0x21 | СИЗ в норме | 0x8000 |
| 0x22 | Заряд СИЗ (порог) | индекс единицы |
| прочие | Зарезервировано | — |

**Коды `EventType` предварительные — не зафиксированы.** Конкретный перечень
офлайн-событий комплекта пока не определён; таблица — каркас, коды проставятся при
согласовании списка с прошивкой.

**Что в контейнерный EventLog НЕ входит:**
- **Газовые пороги** (кислород, H₂S, CO, метан, ΣУВ и т.д.) — это событие **газовой
  секции**: они едут в `StateErr` записей `Sensors`/`EventLog` под-устройства AVIS
  (п. 5.2–5.3) и в контейнер не дублируются.
- **Пороги заряда** (трекер/пульсометр/газоанализатор) — сервер вычисляет сам из полей
  `Battery` соответствующих блоков; отдельных событий заряда прибор не шлёт.

`Severity` соответствует разделению PTS «информационные / предупреждения /
критические значения». Направление порога (больше/меньше) различается по знаку
отклонения `Value` от действующей границы — сервер знает границы из своей конфигурации.

## 5. Под-устройства

После контейнерных блоков идёт `SubCount` и далее — секции под-устройств
(`SubID + SubMask + блоки`, п. 3). Каждый тип под-устройства имеет собственный словарь
блоков и собственную маску.

```c
enum SUB_TYPE {
    SUB_TYPE_GAS   = 0,   // газоанализатор AVIS
    SUB_TYPE_PULSE = 1,   // пульсометр (браслет)
    // 2..255 — зарезервировано (новые носимые устройства)
};
```

### 5.1 Пульсометр (`SUB_TYPE_PULSE`)

| Бит SubMask | Блок | Структура | Размер |
|-------------|------|-----------|--------|
| 0 | Battery | `uint8` заряд браслета, % | 1 |
| 1 | HeartRate | `uint8` пульс, уд/мин | 1 |
| 2 | SpO2 | `uint8` сатурация, % *(задел, опционально)* | 1 |
| 3–7 | Reserved | | |

### 5.2 Газоанализатор AVIS (`SUB_TYPE_GAS`)

Переиспользует блоки v3 **кроме GPS/GPSTrack/GPSHistory** — координату его событиям
даёт контейнерный блок `GPS` трекера (общий якорь).

| Бит SubMask | Блок | Структура | Размер |
|-------------|------|-----------|--------|
| 0 | Battery | `uint8` заряд газоанализатора, % | 1 |
| 1 | Sensors | `Count + sensor_data_t[]` (v3 п. 4.3) | 1+4N |
| 2 | EventLog | `Count + event_record_t[]` (v3 п. 4.8, канальный) | перем. |
| 3–7 | Reserved | | |

Отдельного `ControlLora` у секции AVIS нет: носитель один, и весь статус комплекта
(SOS, группа, зона, класс, эвакуация) несёт контейнерный `ControlLora16` (п. 4.2).
Пороговые состояния газовых каналов едут в `StateErr` каждой записи `Sensors`.

### 5.3 Газовые блоки Sensors и EventLog

Структуры `sensor_data_t` (`SensorIndex + int16 Concentration + StateErr`), фиксированная
точка концентрации (`valueNumAfterPoint`), признаки `0x8000`, группировка каналов в
событии (`event_record_t` с `ChannelCount`) — **идентичны v3 пп. 4.3, 4.8**. Разбор
канала требует конфигурации каналов из `TYPE_STATIC` этого под-устройства (п. 6).

**Count блока Sensors (уточнение автора, PLAN п.64/65)**: уходят **ВСЕ активные каналы
«как прислал BLE»** (Count = число каналов AVIS), `SensorIndex` — СОБСТВЕННЫЙ индекс
канала (тот же бит `SensorsEnabled` в TYPE_STATIC): при изменении состава каналов
нумерация не съезжает, новый канал встаёт в своё место по порядку. Тревожность — в
`StateErr` записи, на состав блока не влияет.

Координатный и временной якорь газовых событий — контейнерные `GPS` и `TimeRef` кадра;
собственного `TimeRef` у секции нет.

## 6. Пакет TYPE_STATIC v4 — конфигурация комплекта

Структура фиксированная (без `FieldMask`). Передаётся после Join, при каждом рестарте
трекера и по запросу сервера (`REQ_STATIC`, п. 7). Описывает паспорт трекера,
фактические радиопараметры, состав СИЗ и перечень под-устройств с их идентификаторами
и конфигурацией.

```c
typedef struct {
    uint8_t  Header;          // TYPE_STATIC + версия = 4
    uint16_t DeviceID;        // заводской идентификатор трекера
    uint8_t  HwVersion;       // версия аппаратуры трекера
    uint8_t  FwVersion;       // версия прошивки трекера
    radio_cfg_t Radio;        // фактические радиопараметры (ground truth, v3 п. 4.11.1)

    uint8_t  PPEEnabledMask;  // какие из 8 позиций СИЗ заведены в комплекте
    ppe_descr_t PPE[];        // описание заведённых позиций, popcount(PPEEnabledMask) штук

    uint8_t  SubCount;        // число под-устройств
    sub_descr_t Subs[];       // дескрипторы под-устройств, подряд
} __attribute__((packed)) mirax_static_t;

typedef struct {              // radio_cfg_t — как в v3 п. 4.11.1, 9 байт
    uint8_t  Rx1DrOffset;
    uint8_t  Rx2DataRate;
    uint32_t Rx2FrequencyHz;
    uint8_t  Rx1DelaySec;
    uint8_t  TxPower;
    uint8_t  MaxDutyCycle;
} __attribute__((packed)) radio_cfg_t;

typedef struct {              // описание единицы СИЗ (в порядке битов PPEEnabledMask)
    uint8_t  Type;            // тип СИЗ (каска/привязь/маска/…; приложение)
    uint16_t Serial;          // заводской идентификатор единицы
} __attribute__((packed)) ppe_descr_t;

typedef struct {              // дескриптор под-устройства
    uint8_t  SubID;           // локальный индекс (ключ для TYPE_DYNAMIC)
    uint8_t  SubType;         // SUB_TYPE
    uint16_t Serial;          // заводской идентификатор под-устройства
    uint8_t  CfgLen;          // длина type-config в байтах (0 — нет)
    uint8_t  Cfg[];           // конфигурация, зависящая от SubType (см. ниже)
} __attribute__((packed)) sub_descr_t;
```

`CfgLen` делает дескриптор самоописываемым: сервер пропускает незнакомую конфигурацию
нового типа под-устройства, не ломая разбор остальных.

**Type-config по типам:**

- `SUB_TYPE_GAS`: `uint8 SensorsEnabled` (битовая маска каналов, ≤ 8) + `channel_cfg_t[]`
  (`uint16 GasID + uint16 Setting`, по 4 байта; **ревизия автора, PLAN п.65**: Setting
  расширен до 2 байт — биты `DEVICE_SETTING_CHAN` 8..12 (EC/OXYGEN/FID/UART/TK) и маски
  `MEASURE_*` нужны серверу для разбора канала). Число каналов = `popcount(SensorsEnabled)`
  и подтверждается `CfgLen = 1 + 4×N`.
- `SUB_TYPE_PULSE`: `CfgLen = 0` (конфигурации нет).

**Радиопараметры (`radio_cfg_t`)** — фактические действующие настройки LoRaWAN трекера,
пишутся в reported-слой безусловно и служат опорой сверки с желаемым слоем. Семантика и
обоснование — v3 п. 4.11.1.

**Совместимость раскладок:** раскладка v4 выбирается по версии в `Header` (п. 2),
поэтому по длине со статикой v3 не конфликтует. Внутри v4 статика самоописываема через
`PPEEnabledMask`, `SubCount` и `CfgLen`.

## 7. Downlink (Сервер → Прибор)

Архитектура и правила — **как в v3 п. 5**: `Header + FieldMask + блоки по возрастанию
битов`, «блок отсутствует в маске — параметр не меняется». Тип — `TYPE_CONFIG`
(`0x00`), `Header = 0x04` (версия 4).

| Бит | Блок | Размер | Назначение |
|-----|------|--------|------------|
| 0 | Control | 4 | Запись флагов `ControlLora16` по маске: `Mask(2) + Value(2)` |
| 1 | Mode | 2 | Запись флагов `ControlLora2` по маске (`REQ_STATIC`, `SET_CLASS_C`), v3 п. 5.3 |
| 2 | PeriodNormal | 1 | Штатный период, ед. 10 с |
| 3 | PeriodActive | 1 | Аварийный период, ед. 10 с |
| 4 | GPSFixInterval | 1 | Интервал фиксации GPS, ед. 10 с (0 — не фиксировать) |
| 5 | ConfigSeq | 1 | Версия конфигурации для квитирования (v3 п. 6.2) |
| 6 | Time | 4 | Unix-время синхронизации RTC (v3 п. 6.7) |
| 7 | Message | 2+L | Текстовое сообщение оператора на дисплей прибора (п. 7.1) |
| 8–15 | Reserved | — | Зарезервировано |

Отличие от v3 — блок **Control** расширен до `Mask(2)+Value(2)` под 16-битный
`ControlLora16` (запись атомарна по маске: `reg = (reg & ~Mask) | (Value & Mask)`).
Бит `EVACUATION` (8) пишется старшим байтом маски. Блоки `Period*`/`GPSFixInterval`/`Mode`
требуют `ConfigSeq`, как в v3.

Квитирование конфигурации (`ConfigSeq`/`ConfigAck`), хендшейк `REQ_STATIC`,
эхо-квитирование аварий, управление классами, синхронизация RTC и восстановление данных
после потери связи — **без изменений относительно v3** (пп. 6.1–6.8). Downlink в v4
адресует трекер; конфигурация газовых каналов под-устройства приходит в его `TYPE_STATIC`
и меняется локальным конфигуратором прибора (как радиопараметры в v3).

Квитирование `ConfigAck` (uplink) в v4 — контейнерный блок (бит 11 `ContainerMask`,
п. 3.1; в v3 это был бит 8 `FieldMask`), структура прежняя — `uint8 AppliedRev`.
Относится ко всему комплекту, а не к отдельному под-устройству.

### 7.1 Блок Message — текстовое сообщение на дисплей

Сервер передаёт оператору **свободный текст** для показа на дисплее прибора (рассылка
уведомлений об инцидентах на трекеры из каталога PTS). Комплекс работает с
**выключенным duty cycle**, поэтому ограничение одно — лимит payload текущего DR;
фрагментация не используется, сообщение обязано поместиться в один кадр.

```c
typedef struct {
    uint8_t  MsgSeq;        // идентификатор сообщения для квитирования доставки
    uint8_t  Length;        // длина текста, байт (= символов)
    uint8_t  Text[Length];  // текст, однобайтовая кодировка (CP1251)
} message_block_t;
```
**Размер:** 2 + `Length` байт.

**Кодировка — однобайтовая (CP1251):** один байт на символ, кириллица и латиница
укладываются без расширения. Поля выбора кодировки нет — она фиксирована.

**Максимальная длина текста** = `payload_limit(DR) − overhead`, где накладные расходы
кадра с единственным блоком Message:
`Header(1) + FieldMask(2) + MsgSeq(1) + Length(1) = 5 байт`.

| DR | Лимит payload | Макс. символов текста |
|----|---------------|-----------------------|
| DR0–DR2 (SF12–SF10) | 51 | 46 |
| DR3 (SF9) | 115 | 110 |
| DR4–DR5 (SF8/SF7) | 242 | 237 |

Если в том же кадре присутствуют другие downlink-блоки, их размер вычитается
дополнительно. UI показывает оператору действующий лимит символов с учётом DR и
прочих блоков кадра.

**Квитирование доставки.** Прибор подтверждает приём сообщения, возвращая принятый
`MsgSeq` в контейнерном блоке `MsgAck` (uplink, `ContainerMask` бит 12, `uint8`),
симметрично `ConfigAck`. Сервер сверяет `MsgAck` с `MsgSeq` последнего отправленного
сообщения: совпало — доставлено, очередь сообщений очищается; не совпало — повтор в
следующем downlink. `MsgSeq` инкрементируется по модулю 256 на каждое **новое**
сообщение; повтор того же сообщения счётчик не меняет, и прибор идемпотентно
не показывает дубль повторно.

## 8. Пример кадра TYPE_DYNAMIC v4

Штатный кадр комплекта: заряд трекера, координата, окружающая среда, положение,
статус; плюс две секции под-устройств — пульсометр (пульс + заряд) и газоанализатор
(2 канала + заряд).

```
04 73 00 55 60 C6 3A 21 40 5B 6C 16 80 00 23 00 EB 00 2D 94 27 78 00
01 3C 02 01 03 5A 4E 02 03 50 02 00 D1 00 00 01 97 00 00
```

**Длина: 42 байта.** `ContainerMask = 0x0073` = Battery | GPS | DeviceStatus |
Environment | Motion (биты 0,1,4,5,6).

| Смещ. | Байты | Блок | Значение |
|-------|-------|------|----------|
| 0 | `04` | Header | `TYPE_DYNAMIC`, версия 4 |
| 1–2 | `73 00` | ContainerMask | `0x0073` |
| 3 | `55` | Battery | заряд трекера 85 % |
| 4–11 | `60 C6 3A 21 40 5B 6C 16` | GPS | 55.7500000°, 37.6200000° |
| 12–13 | `80 00` | DeviceStatus | `ControlLora16 = 0x0080` → Класс C (`CURRENT_C`), аварий нет |
| 14–22 | `23 00 EB 00 2D 94 27 78 00` | Environment | AQI 35; темп 23.5 °C; влажн 45 %; давл 1013.2 гПа; высота 120 м |
| 23–24 | `01 3C` | Motion | поза вертикальная (StatusBits `0x01`); активность 60 |
| 25 | `02` | SubCount | 2 под-устройства |
| 26–29 | `01 03 5A 4E` | Sub 0 (пульсометр) | SubID 1; SubMask `0x03`; заряд браслета 90 %; пульс 78 уд/мин |
| 30–41 | `02 03 50 02 00 D1 00 00 01 97 00 00` | Sub 1 (газоанализатор) | см. ниже |

| Байты | Поле | Значение |

| `02` | SubID | 2 |

## 9. Сообщения ACK и выключения

`TYPE_MSG_ACK` (`0x40`) и `TYPE_MSG_TURN_OFF` (`0xC0`) — как в v3 п. 7, но поле статуса
расширяется до `uint16 ControlLora16` (2 байта), согласованно с п. 4.2. `TYPE_TURN_OFF`
соответствует событию PTS «Трекер выключен сотрудником».

Пример `TYPE_MSG_ACK` в Классе C без аварий: `44 80 00` — Header `0x44` (`TYPE_ACK`,
версия 4) + `ControlLora16 = 0x0080` (`CURRENT_C`).

## Приложение

### Единицы измерений газовых каналов — как в v3 (0 PPM, 1 мг/м³, 2 % НКПР, 3 % об.д.),
маски `Setting` — как в v3.

### Типы СИЗ (`ppe_descr_t.Type`) — предварительно, расширяемо
| Значение | Тип СИЗ |
|----------|---------|
| 0 | каска |
| 1 | страховочная привязь |
| 2 | маска / респиратор |
| 3 | перчатки |
| 4 | защитные очки |
| 5 | защитная обувь |
| 6..255 | зарезервировано |

---

## Принятые решения

1. **Статус — только у трекера.** Отдельного `ControlLora` у секции AVIS нет; весь
   статус комплекта несёт контейнерный `ControlLora16` (п. 4.2). Газовые пороги — в
   `StateErr` каналов.
2. **Severity оставлен.** Контейнерное событие несёт `Severity` (инфо/предупреждение/
   критическое) + знак отклонения `Value`; раздельные биты порогов не вводятся.
3. **Газовые пороги — только в газовой секции** (`StateErr`), в контейнер не выносятся.
   **Пороги заряда считает сервер** из полей `Battery`; событий заряда прибор не шлёт.
4. **Удалённой настройки под-устройств нет.** Пороги пульсометра и каналы газоанализатора
   по downlink не меняются (только локальный конфигуратор); `SubConfig`-механизм в v4 не
   вводится.
